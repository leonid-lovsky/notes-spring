# google-docs-full-model.md

> Создан 2026-07-23 по вопросу пользователя «что требуется для реализации полной модели Google Docs в хексагональной архитектуре» (Gradle/Spring Boot/Spring Cloud/Spring Security/OAuth). Это набросок идеи, а не принятое решение — статус аналогичен «Открытые решения» в `CLAUDE.md`, не реализовывать без отдельного запроса. Задача не входит в текущий приоритет (см. `CLAUDE.md` → «Задачи» → текущий приоритет на дату чтения).

## Постановка задачи

«Полная модель Google Docs» — не CRUD-сервис поверх заметок, а движок совместного редактирования: документ с богатым форматированием, множество одновременных редакторов, история версий, права доступа и комментарии. Существующий проект (`note/`/`user/`/`user-note/`) даёт готовый паттерн для CRUD-части (domain/contract/contract-reactive/webmvc/webflux/data-*/application-*), но не для конкурентного редактирования в реальном времени — это отдельный, не решённый в текущей архитектуре пласт.

## Доменная модель (могла бы лечь в `domain/`, чистая Java)

- **Document** — метаданные документа (владелец, заголовок, дата создания/изменения); содержимое — отдельно от метаданных
- **Revision / Operation** — атомарная правка содержимого; при выборе CRDT/OT это основная единица хранения и передачи, не сам документ целиком
- **Permission** — роль пользователя на документе: owner/editor/commenter/viewer
- **Comment** — привязан к диапазону в документе, независим от Revision

## Слои hexagonal architecture — по аналогии с `note/`

- `contract`/`contract-reactive` — порты синхронного и реактивного доступа, как у существующих сервисов
- `webmvc`/`webflux` — HTTP driving-адаптеры для CRUD части (создание документа, права, комментарии); для real-time слоя HTTP не подходит — нужен отдельный driving-адаптер поверх WebSocket/STOMP, вне текущей `webmvc`/`webflux` пары
- `data-*` — driven-адаптеры хранения; для Document/Permission/Comment годится обычный JPA/MongoDB, но поток Operation/Revision (append-only, высокая частота записи) скорее ложится на MongoDB/событийное хранилище, чем на реляционную БД
- `application-*` — composition root; здесь же должен подключаться WebSocket-слой, которого в текущей технологической матрице (5 composition root на сервис) нет ни в одном из трёх существующих сервисов

## Совместное редактирование в реальном времени — ядро сложности

Это единственная часть, для которой Spring-стек не даёт готового решения:

- **OT (Operational Transformation)** или **CRDT** — нужен один из двух алгоритмов трансформации конкурентных правок; готовых зрелых Java-реализаций CRDT для rich-text практически нет (в отличие от JS-экосистемы — Yjs, Automerge), реализация или порт — самостоятельная существенная работа
- **WebSocket/STOMP** — доставка правок в реальном времени; естественно ложится на Spring WebFlux (`webflux/`), а не на blocking `webmvc/`
- **Presence/курсоры других пользователей** — отдельный, более простой поток поверх того же WebSocket-канала

## Права доступа и аутентификация

- **Spring Security + OAuth2** — стартеры уже описаны в `docs/tech-glossary.md` → «OAuth2»; для Google Docs естественна интеграция с внешним IdP (Google) через `security-oauth2-client`
- Роли owner/editor/commenter/viewer — не просто Spring Security `@PreAuthorize`, а проверка на уровне конкретного документа (document-level ACL), которую типовой role-based security не покрывает — нужен отдельный permission-адаптер

## Spring Cloud

Пригождается, только если совместное редактирование выделяется в отдельный сервис от CRUD-части документа — тогда `gateway/`+`registry/`+`config/` маршрутизируют между ними (статус на момент написания раздела 2026-07-23 — см. `CLAUDE.md` → «Задачи» → статус по сервисам и модулям на дату чтения, актуальное состояние может отличаться). Для одного монолитного сервиса Spring Cloud не обязателен.

## Вне ядра, отложено

Версионирование/история изменений (естественно вытекает из модели Revision, если выбран event-sourcing подход), экспорт (PDF/DOCX), полнотекстовый поиск — не влияют на архитектурное решение по совместному редактированию, можно проектировать отдельно и позже.

## Рекомендация

Не проектировать всё сразу. Сначала — обычный CRUD-документ по существующему паттерну (`note/` → `Document`), с versioning и permissions как первым слоем. Real-time collaborative editing (OT/CRDT) — вынести в отдельную, отдельно оцениваемую задачу: это единственная часть с реальным техническим риском и без готового решения в экосистеме Spring.
