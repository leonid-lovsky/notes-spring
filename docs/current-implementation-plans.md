# Планы текущей реализации `UserNoteService` (sync) и `UserNoteServiceTests` (снимок 2026-10-08)

> **Назначение:** перечень дыр и ближайших шагов по текущей реализации sync-`UserNoteService` и его тестов; ниже дословно сообщение ассистента от 2026-10-08, записанное по просьбе пользователя
> **Когда читать:** перед продолжением TDD по `UserNoteService` (`replace`/`update`/`delete`) и при пересмотре тестов сервиса
> **Статус:** снимок 2026-10-08, не источник истины; решения — в `CLAUDE.md`

Если ограничиться sync-`UserNoteService` и `UserNoteServiceTests`, то дыры такие.

**В сервисе**
1. **Три метода не реализованы.** `replaceUserNoteById`, `updateUserNoteById`, `deleteUserNoteById` по-прежнему бросают `UnsupportedOperationException`, и тестов на них нет. Для них в порт надо добавить `deleteById`. `replace` и `update` обходятся имеющимися `findById` и `save`.
2. **Гонка в `create`.** Между `existsById` и `save` другой запрос может создать ту же запись. Сервисом это не исправить, нужна уникальность в БД и перевод ошибки адаптером.
3. **`new UserNoteMapper()` как инициализатор поля.** Это скрытая зависимость. Пока терпимо, поскольку маппер без состояния.
4. **Объявление класса** с пятью интерфейсами в одну длинную строку. Стилистика, не дефект.

**В тестах**
1. **Не покрыты ветки, которых ещё нет в коде**: `replace`, `update`, `delete`, то есть 404 для них.
2. **«Не найдено» проверяет только тип исключения.** Что в нём лежит нужный `id`, тест не фиксирует. Сейчас `id` виден лишь в тексте сообщения.
3. **Повтор подготовки данных.** В четырёх тестах одинаковые блоки с `UUID.randomUUID()`. Выносится в поля класса без приватных методов.
4. **Нет отдельного теста для `UserNoteMapper`.** Он тривиален и покрыт косвенно.

Серьёзных дыр в уже написанном коде я не вижу. Проверка `verify(…, never()).save(any())` защищает от перезаписи при конфликте. А то, что `save` получает сущность с правильными `userId` и `noteId`, фиксирует стаб `save(userNote)` по равенству записей.

Самое полезное сейчас — реализовать следующий метод через TDD. Предлагаю `replaceUserNoteById`: тест на 404, тест на успешную замену. Берём?

## Запуск приложения и минимальный CRUD (консультация 2026-10-10, решение не принято; сводка выше устарела: сервис уже переписан на единый `UserNoteService` с четырьмя методами, тесты есть для sync и reactive)

- **договорённость**: бизнес-правила (инвариант `OWNER`, правила ролей, границы списков) откладываются; цель — минимальный CRUD во всех сервисах и минимальный агрегирующий сервис (его действия и модели продумываются позже); слой `service-*` пока прослойка (вариант В откладывается до правил, но слой остаётся ради симметрии с агрегатором — `docs/microservices-reference.md` → «Агрегирующий сервис в той же структуре…»)
- **минимальный CRUD**: привести `note` и `user` к раскладке `user-note` (код пишет пользователь, ассистент сверяет копии `diff`); адаптер хранилища для каждой технологии; бин сервиса
- **почему приложение не запускается (проверено 2026-10-10, `:user-note:application:application-h2:test`)**: `contextLoads()` падает на `UserNoteController` — `NoSuchBeanDefinitionException: No qualifying bean of type 'com.example.usernote.UserNoteService'`; после регистрации сервиса следующей упадёт зависимость `UserNoteRepository` (реализации порта нет нигде); проверен один лист, остальные 23 падают по той же причине предположительно
- **минимум для запуска — два бина**: (1) `UserNoteService` — не автоконфигурация, а сканирование компонентов: все модули сервиса в одном пакете `com.example.usernote`, `@SpringBootApplication` листа найдёт класс с `@Service`; минимум — `spring-context` в `service-*` и аннотация на `UserNoteServiceImpl` (отступление от правила «без фреймворка» назвать при принятии); (2) бин порта `UserNoteRepository` — порт не расширяет интерфейсы Spring Data, поэтому Spring Data его не создаст, нужен класс-адаптер `@Component`/`@Repository`
- **что автоконфигурация даёт сама (по памяти о Spring Boot, сверить с docs.spring.io при реализации)**: стартер технологии на classpath листа создаёт инфраструктуру — JDBC: `DataSource` (для H2 встроенный), `JdbcClient`/`JdbcTemplate`, менеджер транзакций, репозитории Spring Data JDBC; R2DBC: `ConnectionFactory`/`DatabaseClient`; Mongo: `MongoClient`/`MongoTemplate`; стартеры и драйверы в листьях уже подключены
- **минимальный адаптер для JDBC без своей `@Configuration`**: (1) интерфейс Spring Data `Repository<сущность, UUID>` в пакете, который сканирует лист — реализацию создаёт автоконфигурация; (2) сущность хранения с аннотациями Spring Data; (3) класс-адаптер `@Component`, реализующий `UserNoteRepository`: вызывает интерфейс Spring Data и мапит сущность в `UserNoteResponseBody`. Эти три класса — содержимое варианта (а) «модуль адаптера на технологию» (JDBC, R2DBC, Mongo, Mongo reactive, общий для листьев технологии; возврат `data-*` с реальным содержимым); отвергнуты: (б) адаптер в каждом листе — 24 копии, (в) Spring Data как порт — порт назван по сценариям и возвращает готовые модели ответа
- **не нужно для запуска, нужно для первой записи**: схема — для встроенной H2 Boot выполняет `schema.sql` сам; для MySQL/PostgreSQL нужен `spring.sql.init.mode=always`; для Mongo схема не нужна; собственные `@Configuration` и свойства для H2 не нужны
- **рекомендация ассистента**: вариант (а) + `@Service` с `spring-context`; начать с JDBC на `application-h2` (без Docker); выбор варианта (а)/(б) пользователем не сделан
