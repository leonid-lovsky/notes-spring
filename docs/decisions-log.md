### Архитектура

- **Convention plugins в `build-logic/convention/`** (included build, не `buildSrc/`) — лучше инкрементальность (правка плагина не инвалидирует весь билд), `./gradlew clean build` из корня остаётся одной командой. Id namespaced (`com.example.{name}`) — снимает конфликт с внешними плагинами. Плагины лежат плоско в одном каталоге — id берётся только из имени файла, алфавит уже даёт естественную группировку (`spring-boot-*`, `spring-cloud-*`, ...; уточнения по словам-маркерам как префиксам, не суффиксам — см. «Именование convention-плагинов для sort-by-name-группировки» ниже)
- Вся Gradle-конфигурация — Kotlin DSL; рабочий код сервисов — Java. Precompiled script plugins не видят typed-аксессоры каталога — `libs.findVersion("key").get().requiredVersion` вместо `libs.versions.x.get()`
- Id не привязанных к папке плагинов — по смысловой роли, не только алфавиту. 7 плагинов 1:1 с папкой модуля/стартером (`webmvc`, `webflux`, `data-jpa`, `data-jdbc`, `data-r2dbc`, `data-mongodb`, `data-mongodb-reactive`) не переименовывать в отрыве от папки; `domain`/`contract*` — исключение (называются по зависимости, не по слою)
- **Пересмотрено 2026-07-23**: исходно `spring-boot-client-web`/`-client-rest` (не `webclient`/`restclient`, чтобы не путать с `webflux`) — пересмотрено в пользу полных литеральных имён технологии `spring-boot-client-webclient`/`-client-restclient`, см. «Именование convention-плагинов для sort-by-name-группировки» ниже; префикс `client-` сохранён и по-прежнему достаточен, чтобы не путать с `webflux` при сортировке (расхождение уже на символе после `spring-boot-`)
- `spring-boot-starter`/`-test` — в `com.example.spring-boot` (общий для любого Boot-модуля), не в `spring-boot-application`. Bootable-возможность (`org.springframework.boot`, ради `bootJar`) — вторая, ортогональная BOM-цепочке ось иерархии, см. диаграмму ниже
- Отступ 4 пробела, не табы — для Java жёсткая Checkstyle-проверка (`FileTabCharacterCheck`/`IndentationCheck`); для Kotlin build-скриптов — только соглашение
- Плагин `idea` — удалён (deprecated в Gradle, был только в domain/-модулях, несогласованно)

**Именование convention-плагинов для sort-by-name-группировки** (2026-07-23) — плоский каталог (48 файлов) полагается на алфавит для группировки (см. «Convention plugins в `build-logic/convention/`» выше), но два реальных дефекта в этом обнаружены и исправлены:
1. **Слово-маркер как суффикс, а не префикс, не группирует** — `{vendor}-database` (`h2-database`/`mysql-database`/`postgresql-database`/`r2dbc-{vendor}-database`) не давало группировки: слово `database` в конце строки не влияет на позицию при сортировке, реальную позицию задаёт имя вендора, и посторонние плагины (`oauth2-*`) физически врезались между `mysql-database` и `postgresql-database`. Переименовано в `spring-boot-database-{vendor}`/`spring-boot-database-r2dbc-{vendor}` — слово-маркер вынесено в префикс, вся вендорная ось (6 плагинов) теперь гарантированно смежна при любой сортировке, аналогично тому, как `data-*` (5 плагинов, префикс) уже работает корректно
2. **Приватные фрагменты одной композиции без общего маркера** — `checkstyle`/`jacoco`/`jacoco-report-aggregation`/`jspecify`/`nullaway` применяются исключительно изнутри `codequality` (проверено грепом — ни один из 39 листовых модулей их не применяет напрямую), но не имели с ним общего префикса. Переименовано в `codequality-{checkstyle,jacoco,jacoco-report-aggregation,jspecify,nullaway}` — сразу видно, что это дети `codequality`, не самостоятельные плагины
3. **Паттерн применён и к неточным именам технологий** — `spring-boot-oauth2-{authorization-server,client,resource-server}` не отражали реальное имя стартера Boot 4 (`spring-boot-starter-security-oauth2-*`, см. CLAUDE.md → «Стек» → «Spring Boot 4 — критичные отличия») — переименовано в `spring-boot-security-oauth2-*`, группировка тройки сохранена (общий префикс `security-oauth2-`, стал точнее). `spring-boot-client-web`/`-client-rest` — см. пересмотр выше в этом же разделе, `spring-boot-client-webclient`/`-client-restclient`
4. **Blast radius проверен по каждому переименованию отдельно** — 6 database-плагинов применяются 27 раз в 9 листовых build.gradle.kts (`application-jpa`/`-jdbc`/`-r2dbc` × 3 сервиса) — обновлено массовым `sed` по всем вхождениям; 5 codequality-плагинов и 5 client/oauth2-плагинов — 0 применений в листовых модулях (codequality-* — только внутри `codequality.gradle.kts`; client/oauth2 — отложенные технологии, ещё нигде не подключены, см. CLAUDE.md → «Задачи» → «ОТЛОЖЕНО»). `./gradlew projects` (конфигурация всего дерева) и точечный `clean check` по всем 9 задетым composition-root модулям — зелёные
5. **Не тронуто осознанно**: 7 плагинов 1:1 с папкой модуля (см. правило выше в этом разделе) — не переименовывались, даже если бы алфавит выиграл
6. **Отклонённый кандидат — `spring-boot-docker-compose`/`spring-boot-testcontainers*`**: изначально предложено сгруппировать (используются парой в одних и тех же 15 модулях), затем отклонено — технологически это разные, не связанные концерны (`docker-compose` — dev-time инфраструктура для `bootRun`, `developmentOnly`; `testcontainers` — тестовая инфраструктура для `test`, `testImplementation`). Совместное применение сегодня — следствие конкретной задачи (вендорная ось БД), не родство технологий; появись модуль с одним из них без другого — придуманное зонтичное слово осталось бы фикцией без основания. **Общий принцип**: группировка по имени — только для действительно родственных технологий (общий вендор, общий npm/maven-namespace, общий стартер), не для того, что просто применяется вместе в проекте на сегодняшний день — так же, как переименование `checkstyle`/`jacoco`/etc. в `codequality-*` обосновано структурно (они физически недостижимы иначе как через `codequality`), а не совпадением текущего использования
- Type-safe project accessors включены (`enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")`), требуют явного `rootProject.name` в обоих `settings.gradle.kts`
- `api` в `dependencies {}` — только когда тип в публичной сигнатуре модуля, иначе `implementation`, не полагаясь на транзитивный путь (проверено на `reactor-core`). `api project(...)` в `contract*/` — осознанное исключение (домен-типы больше неоткуда получить)
- Hexagonal: `domain/` не знает о JPA/MongoDB/Spring; адаптеры зависят от `contract*/` (порт) и явно `implementation(domain)`, не полагаясь на транзитивную `api(domain)`; `api(domain)` в самих `contract*/` остаётся — интерфейсы возвращают domain-типы
- **Один контроллер/контракт/адаптер на сущность, не на операцию** (пересмотрено 2026-07-08) — `NoteController` с 6 методами вместо по одному на HTTP-метод; применено по всем трём CRUD-сервисам, слои и hexagonal-изоляция не затронуты
- `service/` — только при координации нескольких портов; для простого CRUD не нужен
- `existsById` в контракте — валидный паттерн, не заменять на `findById`
- `add` ≠ `replace`: JPA — `save(null id)` vs `save(id)`; MongoDB — `insert()` vs `save()`
- `user-note/`: суррогатный `UUID id` (не составной `userId+noteId`) во всех технологиях; `userId+noteId` — unique constraint/index. Снимает ограничение Spring Data R2DBC (нет `@EmbeddedId`)
- Unique constraint `userId+noteId`: JPA — `@Table(uniqueConstraints=...)`; MongoDB — `@CompoundIndex(unique=true)`; R2DBC/JDBC (`spring-data-relational`) не имеют constraint-атрибутов вообще — только через схему
- **Управление схемой R2DBC/JDBC — `schema.sql`** (2026-07-14): `id UUID DEFAULT RANDOM_UUID() PRIMARY KEY`, `NOT NULL` на непустых колонках, `UNIQUE(...)` где нужно. Flyway/Liquibase не рассматривались (H2, схема простая). Исполняется при старте `application-r2dbc/` и `application-jdbc/` (последний подключён 2026-07-23, см. «Технологическая и вендорная ось адаптеров»)
- `user-note/role` — унифицирован до enum везде (2026-07-14) — Spring Data JDBC/R2DBC маппят enum в строку из коробки, ручная конвертация не нужна
- `data-jdbc/` — прежнее решение «сырой JDBC, без repository» отменено 2026-07-14 (признано ошибочным пользователем): теперь `model/`+`repository/`(`ListCrudRepository`)+`mapper/` по структуре `data-r2dbc/`, по всем трём сервисам
- **Трёхуровневая иерархия портов** вместо единого `{Entity}Contract`/`ContractReactive` (2026-07-13): `{Entity}Interface[Reactive]` (методы возвращают `Object`) → `{Entity}ServiceInterface[Reactive]` (конкретные типы, реализуют адаптеры `{Entity}Service`) → `{Entity}ControllerInterface[Reactive]` (`ResponseEntity`/`Mono<ResponseEntity>`). Приём — ковариантное переопределение `Object` (`Mono`/`Flux` — валидные подтипы, примитивный `void` — нет, поэтому sync `remove`/`deleteBy*` возвращают `Response`). `existsById`/`existsBy*` — реальные `GET`-эндпоинты. Разбивка методов по типу ключа — только в `user-note/`
- `user-note/`: операции разведены по типу ключа (суррогатный `userNoteId` и составной `userId+noteId` — отдельные методы, контракт из 15). `findByUserId`/`findByNoteId` сами бросают `UserNotFoundException`/`NoteNotFoundException` (собственные типы, не из `note/`/`user/` — сохраняет hexagonal-изоляцию между сервисами)
- **PUT (`replace*`) ≠ PATCH (`merge*`)**: `replace` — полная замена; `merge` — `null` в `request` значит «не менять». Оба бросают `NotFoundException` при отсутствии сущности
- **Диспетчеризация нескольких `@GetMapping` на одном пути** — `@RequestParam` не участвует в регистрации маппинга, нужен атрибут `params` (`@GetMapping(params = "userId")`), иначе `Ambiguous mapping` при старте контекста
- Reactive `findById`/`findBy*` бросают `{Entity}NotFoundException` вместо пустого `Mono` (пересмотрено 2026-07-13) — проверка перенесена из контроллера в сервис/адаптер, консистентно с sync
- `note/webflux`/`user/webflux`: `findAll()` оборачивает в `ResponseEntity<Flux<X>>` (было голый `Flux`)
- **Группировка модулей по слою в подпапку** (2026-08-01) — физический путь листового модуля для `note`/`user`/`user-note` сгруппирован по слою: `{service}/domain/{domain,contract,contract-reactive}/`, `{service}/persistence/data-*/`, `{service}/presentation/{webmvc,webflux}/`, `{service}/application/application-*/` (было плоско `{service}/{module}/`). Инициировано пользователем вручную в `user-note/` (`git mv`, с опечаткой `pestistence`), доведено агентом до всех трёх сервисов с исправленной опечаткой. Gradle project path и typesafe-accessor не меняются (`:{service}:{module}`, `projects.{service}.{module}`) — только `projectDir` каждого модуля переопределён в `settings.gradle.kts` на новый физический путь. Пересматривает более узкое отклонённое решение «каталог `data/` на уровне сервиса» (было: оставить плоско, см. CLAUDE.md → «Открытые решения») — на практике цена оказалась ниже ожидаемой именно благодаря `projectDir`-переопределению, не требующему менять форму accessor'ов

- **Трёхуровневая иерархия портов: `Object`-ковариантность → generic-параметризация** (2026-08-08, пересматривает предыдущий пункт «Трёхуровневая иерархия портов» выше) — та же 3-уровневая структура (`{Entity}Interface[Reactive]` → `{Entity}ServiceInterface[Reactive]` → `{Entity}ControllerInterface[Reactive]`) сохранена, но базовый интерфейс параметризован дженериком вместо возврата голого `Object`: `{Entity}Interface<B, S, L>` (sync `note`/`user` — B=exists-тип, S=единичный, L=список) / `{Entity}Interface<S, L>` (sync `user-note` — exists-методы не часть общего порта, только на `ServiceInterface`, как и было) / `{Entity}ReactiveInterface<B, S, L, V>` (reactive все три сервиса — V=delete/remove-тип, `Mono<Void>`). `ServiceInterface`/`ControllerInterface` — пустые тела, только `extends {Entity}Interface<конкретные типы>`. Причина пересмотра — см. CLAUDE.md → «Правила» → «Перед архитектурным ответом — контрольный список»: `Object`-ковариантность — вырожденный, не несущий типовой информации контракт (наследование ради синтаксического, не поведенческого сходства); честная дженерик-параметризация даёт то же самое (совпадение сигнатур между Controller/Service, гарантированное компилятором) без потери типобезопасности на уровне базового интерфейса. Реализовано по всем 6 порт-деревьям (sync+reactive × `note`/`user`/`user-note`) — 18 файлов интерфейсов переписаны, ни один класс-реализация (адаптер/контроллер) не изменён (конкретные сигнатуры после дженерик-подстановки идентичны прежним, только механизм получения другой). Попутно исправлены 7 pre-existing нарушений Checkstyle (`import com.example.*.domain.*`/`org.springframework.web.bind.annotation.*` — wildcard-импорты в `user-note/`, не связаны с этой правкой, но блокировали `clean check`). Верифицировано: `./gradlew clean check` — все задачи зелёные кроме уже известного блока Docker Hub CDN (`ContainerFetchException` на 24 Testcontainers-тестах, по 8 на сервис, см. CLAUDE.md → «Правила» → «Build»)

- **`L` признан неустранимым как свободный generic-параметр — дальнейший пересмотр в тот же день, 2026-08-08** (пересматривает пункт «Трёхуровневая иерархия портов: `Object`-ковариантность → generic-параметризация» выше; сама реализация в коде из предыдущего пункта на момент записи ещё не изменена) — пользователь указал, что `L` должен иметь bound (`List`/`Iterable`/`Collection` — «наиболее общий тип для перечисляемых типов»). Проверено и доказано физически, не рассуждением: (1) компилятором — `Box<List<X>>` не конвертируется в `Box<Iterable<X>>` (`incompatible types`, инвариантность generics в Java — тестовый `javac`-компайл), значит `L extends Iterable<S>` ломает 3 из 4 инстанциаций (`ResponseEntity<List<S>>`/`Flux<S>`/`ResponseEntity<Flux<S>>` — ни одна не `Iterable`); (2) исходниками `reactor-core` (`raw.githubusercontent.com/reactor/reactor-core`) — `Flux<T> implements CorePublisher<T>`, не `Iterable` — общего типа, который одновременно реализуют `List` и `Flux`, не существует в Java/Reactor в принципе. Рассмотрены и отклонены по ходу диалога: полная HKT-эмуляция (`Kind<F,T>`-witness, как в Vavr/Cyclops) — технически единственный полностью честный вариант, но тяжёлая, неидиоматичная для Spring/Java машинерия ради одного метода на 3 сущности; отказ от `ResponseEntity` в пользу `@ResponseStatus` + голых типов (устраняет проблему целиком, Controller/Service становятся идентичны по сигнатуре) — пользователь отверг явно, `ResponseEntity` — жёсткое, не подлежащее пересмотру требование; полное расщепление на 4 независимых интерфейса без общего предка, через рамку GoF Adapter (Controller — Object Adapter вокруг `NoteServiceInterface`-Adaptee, проверено на реальном коде `NoteController` — уже держит `NoteServiceInterface` через композицию, не наследование) — валидно, но теряет компилятором проверяемое совпадение сигнатур; annotation processor/кодогенерация (эталонный `@Port`-интерфейс → 4 генерируемых) — единственный вариант, одновременно дающий гарантию без дублирования и настоящую обобщаемость на будущие «вкусы» (GraphQL и т. п.), но пользователь явно исключил кодогенерацию из рассмотрения. Найден значимый прецедент уже в самой кодовой базе: `UserServiceInterface.findByEmail`/`findByUsername` уже сегодня объявлены вне общего generic-контракта, конкретными типами, без попытки унификации с `B`/`S`/`L` — `UserControllerInterface` их вообще не содержит. То есть «гарантия совпадения сигнатур через общий предок» и до этого пересмотра не была всеобъемлющей — она заведомо не покрывала entity-специфичные finder'ы, только буквальный CRUD-минимум. **Решение**: `{Entity}Interface<B, S>` (без `L`, `V` сохраняется у reactive для delete/remove) — общий предок только для однородных, линейно компонуемых по обёртке методов (`existsById`/`add`/`findById`/`replace`/`merge`/`remove`); `findAll()` и все entity-специфичные finder'ы (`findByUserId`/`findByNoteId` у `user-note`, `findByEmail`/`findByUsername` у `user`) — объявляются независимо, конкретным bounded-типом (`List<S>`/`ResponseEntity<List<S>>`/`Flux<S>`/`ResponseEntity<Flux<S>>`) в каждом из 4 интерфейсов на сущность — по прецеденту, который кодовая база уже сама для себя выбрала для custom-finder'ов. Статус на момент записи — решено, **реализация в коде не выполнена** (17 не-`user`-специфичных interface-файлов + `UserServiceInterface`/`UserControllerInterface` пересмотреть на предмет `findByEmail`/`findByUsername`, все три сервиса, sync+reactive) — следующий шаг сессии

- **`contextLoads()` на vendor-composition-root модулях — embedded H2 через testRuntimeOnly-fallback, не Testcontainers** (2026-08-18, `user-note`, 6 skeleton-модулей `JDBC`/`JPA`/`R2DBC` × `MySQL`/`PostgreSQL`, см. CLAUDE.md → «Задачи» → «Завершено 2026-08-18») — причинный разбор (начат 2026-08-16, см. запись «Апдейт 2026-08-16» в CLAUDE.md) искал источник для реального `DataSource` (Testcontainers/Docker Compose/embedded native binary), пока не был явно задан вопрос «а как решают уровень теста, где реальное окружение не тестируется» — переключивший ось с «каким реальным вендором поднять контекст» на «нужен ли контексту реальный вендор для этого конкретного теста вообще». `contextLoads()` — smoke-тест «контекст собирается», не «этот вендор ведёт себя как MySQL/PostgreSQL» — для первого достаточно любого рабочего `DataSource`. Решение: `testRuntimeOnly("com.h2database:h2")` в `com.example.spring-boot-database-mysql`/`-postgresql`, `testRuntimeOnly("io.r2dbc:r2dbc-h2")` в `-r2dbc-mysql`/`-r2dbc-postgresql` — 4 строки в 4 convention-плагинах, ни аннотаций (`@AutoConfigureTestDatabase`, рассмотрен и не понадобился), ни правки тестового класса. Механизм — тот же embedded-fallback, что уже делает `JDBC-H2`/`JPA-H2` зелёными без вендорного плагина вообще: `DataSourceProperties`/R2DBC-эквивалент при отсутствии заданного `url` в `application.properties` (skeleton-состояние этих модулей, см. «В процессе 2026-08-14» в CLAUDE.md) сами обращаются к `EmbeddedDatabaseConnection`-детекции classpath — раньше находили только вендорный MySQL/PostgreSQL-драйвер без встроенной БД и падали на bean creation, теперь дополнительно находят H2 и используют его. `runtimeOnly`-драйвер вендора не тронут (прод/`bootJar` не подхватывает H2, `testRuntimeOnly` не просачивается за пределы тестовой области). **Не решает и не притворяется, что решает**: реальное вендор-специфичное поведение (диалект/типы/констрейнты) этим тестом по-прежнему не проверяется — тот вопрос остаётся открытым отдельно (CLAUDE.md → «Открытые решения» → «Поведенческая аналогичность адаптеров/драйверов»), кандидаты на его решение (Testcontainers/embedded native binary/Docker Compose/CI-managed container) из разбора 2026-08-16 актуальны как справочник для этого будущего отдельного теста, не для `contextLoads()`. **Не путать с «MongoDB не имеет embedded-аналога H2»/«Testcontainers/Docker Compose возвращены симметрично» выше** (2026-07-23, зрелые модули `note`/`user`/старый `user-note`) — то решение про полноценную инфраструктуру реального вендора в зрелом сервисе, это — про WIP-skeleton, где `application.properties` ещё не содержит вендорных connection-свойств и полноценной инфраструктуры пока не строилось

**Тесты — на уровне application/bootable-модулей, не в модулях-реализациях** (2026-08-18, разговор в рамках TDD-переписывания проекта, начатого пользователем 2026-08-14 — см. CLAUDE.md → «Задачи» → «В процессе 2026-08-14»/«Завершено 2026-08-18, ещё позже в тот же день») — по итогам пошагового диалога выработан принцип размещения тестов для переписываемого проекта (сейчас применяется к `user-note/application/*`-composition-root модулям, распространяется на будущее переписывание `note/`/`user/`). Отправная точка — пользователь тестирует sociable/classicist-стилем: реальный Spring-контекст, реальные бины, без Mockito/`@MockitoBean`, без искусственно сконструированного поведения (`Mockito.when()`), с embedded H2/embedded Mongo вместо реального вендора, пока это возможно (эскалация на Testcontainers — только когда объективно нужно, см. запись выше «`contextLoads()` на vendor-composition-root...»). Из этого ограничения следует единственное место, где весь стек существует одновременно без единой подмены — bootable/application-модуль (composition-root): `presentation/webmvc`/`webflux` и `persistence/data-*` в изоляции протестировать без мока невозможно, там неоткуда взять недостающую половину стека.

Рассуждение углублено пользователем от операционного факта («негде поднять стек») до эпистемического: модуль-реализация владеет только сигнатурой контракта (`implements {Entity}ServiceInterface` и т. п.), но не знанием о том, зачем это поведение вообще нужно и как оно должно выглядеть с точки зрения системы в целом — у него нет цели, только механизм. Знание «зачем» существует только там, где кто-то собирает конкретную систему под конкретную цель (application-модуль, выбирающий конкретный вендор+технологию). Названная пользователем аналогия — работу человека должен принимать (тестировать) тот, кто дал ему задачу, не сам исполнитель — прямое соответствие стандартному термину acceptance testing (приёмочные критерии задаёт заказчик, знающий цель, не исполнитель, знающий только механизм). Это симметрично уже принятой в проекте архитектуре DI: порт (`contract`/`contract-reactive`) — чисто структурный контракт без поведенческой спецификации (см. CLAUDE.md → «Открытые решения» → «Поведенческая аналогичность адаптеров/драйверов», п. 1 — «порты вообще не специфицируют поведение», теперь помечено там же как осознанное разделение, не пробел), конкретное связывание реализаций происходит в application через Spring DI; тест распространяет ту же симметрию — верификация поведения происходит там же, где происходит конкретный выбор реализации, не раньше. Заодно закрывает пункт «unit-тесты бизнес-логики (не только `*ApplicationTests` на композицию)» из CLAUDE.md → «Задачи» → «Зрелость CRUD-модулей» — решено сознательным «не нужны отдельно», не забыто.

**Проблема дублирования и её решение** — прямое следствие переноса тестов на bootable-уровень: 11 application-модулей `user-note/` (в перспективе 33 по трём сервисам) при буквальном копировании HTTP-контрактного теста (вход/выход/ошибки) дублировали бы идентичный сценарий 7× (sync-семья: JDBC×3+JPA×3+MongoDB, общий `presentation/webmvc`) и 4× (reactive: R2DBC×3+MongoDB-reactive, общий `presentation/webflux`) — уже наблюдаемо на `contextLoads()`/`UserNoteApplication`. Разрешено разделением по типу дублирования, не единым правилом:
1. **Семантическое дублирование** (тестовый сценарий/assertions, растёт вместе с бизнес-логикой) — устраняется shared-модулем с абстрактным JUnit-классом (сценарий написан один раз), каждый application-модуль получает тонкий подкласс (2–3 строки), реально прогоняющий сценарий через свой настоящий стек. Рассмотрен и отклонён вариант «`java-test-fixtures` внутри самих `presentation/webmvc`/`webflux`» — противоречит прямому требованию пользователя «модули-реализации не содержат тестов вообще»; вместо этого — два отдельных shared-модуля (sync/reactive-семья), физически вне `presentation/*`, не нуждающиеся в compile-зависимости на `presentation/webmvc`/`webflux` как таковые (MockMvc/WebTestClient обращаются по HTTP/JSON, не к самому классу контроллера — тот package-private). Статус: решено на уровне принципа, имя/расположение модулей и конкретный convention-плагин (нужна `api`-транзитивная видимость JUnit/Spring-test-типов для подклассов, аналог `com.example.java-library`) не выбраны, реализация не начата
2. **Структурное дублирование** (`@SpringBootApplication`-класс, `build.gradle.kts`-boilerplate) — не устраняется: обязательно по одному bootable-классу на артефакт (требование самого Spring Boot, не случайное совпадение кода), устранение потребовало бы разделяемых Gradle source-каталогов между модулями — прямое нарушение уже принятого «явная композиция вместо неявного наследования» / «никаких shared-функций в build-logic». Цена дублирования принята по тому же прецеденту, что и диамант-правило («чистота/ясность/предсказуемость важнее объёма copy-paste», см. CLAUDE.md → «Правила» → «Кольцевые/ромбовидные зависимости»)

**Технологическая и вендорная ось адаптеров** (2026-07-23, закрывает «Стратегия активации адаптеров» и «Комбинации technology в `application/`», ранее в CLAUDE.md → «Открытые решения») — задача: скелет под полный выбор адаптера/драйвера БД пользователем, расширяемый под будущие неизвестные технологии без переписывания существующего кода. Решены две независимые оси:
- **Технология адаптера** (jpa/jdbc/r2dbc/mongodb/mongodb-reactive) — отдельный composition-root модуль на каждую (`application-jpa`/`application-jdbc`/`application-mongodb`/`application-r2dbc`/`application-mongodb-reactive`, было 2 — `application`/`application-reactive`, переименованы), а не `@Profile` внутри одного модуля. Причина — не только отсутствие диаманта: на classpath каждого модуля ровно одна repository-технология, поэтому `*RepositoriesAutoConfiguration`-классы Spring Boot (`@ConditionalOnClass`-гейтед) активируются автоматически; `@Profile`-вариант с двумя адаптерами сразу потребовал бы ручного `@EnableJpaRepositories`/`@EnableMongoRepositories(basePackages=...)`, что противоречит принципу «полагаться на autoconfiguration всегда, когда возможно» — вариант отдельных модулей аддитивен: новая технология в будущем — только новые файлы, ни один существующий модуль не редактируется. Это прямо отменяет прежнюю формулировку «MongoDB намеренно не подключена... не третья одновременная связка» — пересмотр, не продолжение (см. CLAUDE.md → «Правила» → «Пересмотр решений»)
- **Вендор БД** (H2/PostgreSQL/MySQL для jpa/jdbc/r2dbc — код `data-jpa`/`data-jdbc`/`data-r2dbc` идентичен для любого вендора) — НЕ отдельные модули: 4 новых convention-плагина (`spring-boot-postgresql-database`, `-mysql-database`, `-r2dbc-postgresql-database`, `-r2dbc-mysql-database`) кладут драйверы `runtimeOnly` (зеркалят `spring-boot-h2-database`/`-r2dbc-h2-database`, без версии — Spring Boot BOM), активный вендор — `spring.profiles.active=postgresql|mysql` + `application-{vendor}.properties` (`spring.datasource.url`/`spring.r2dbc.url`). Без активного профиля — H2 in-memory для JDBC (`DataSourceAutoConfiguration`, embeddable-enum H2/Derby/HSQLDB) **и для R2DBC** (embedded-detection есть и там — Spring Boot docs: «You need not provide any connection URLs... only include a build dependency to the embedded database»; проверено эмпирически 2026-07-23: `application-r2dbc` без `spring.r2dbc.url` и без активного профиля стартует на H2 даже с Postgres/MySQL-драйверами на classpath). Первая попытка (`spring.profiles.default=h2`+`application-h2.properties`) была лишним усложнением на основании ошибочного предположения «у R2DBC нет embedded-detection» — откачено, `application.properties` во всех `application-r2dbc/` не содержит вообще никакого упоминания БД, симметрично `application-jpa`/`application-jdbc`
- **MongoDB не имеет embedded-аналога H2** — построены и вживую верифицированы (не только `clean check`) `spring-boot-testcontainers` (нейтральная обвязка, годится для любого будущего Testcontainers-модуля) + `spring-boot-testcontainers-mongodb` (только `testcontainers-mongodb`-артефакт, композиция двух `id(...)` — исходно был один плагин, разделён в тот же день по замечанию о нарушении композиционного принципа; `MongoDBContainer` из пакета `org.testcontainers.mongodb`, сменился с `org.testcontainers.containers`; один контейнер/`MongoConnectionDetails` общий для sync и reactive клиента, Spring Boot сам выбирает тип по classpath — подтверждено docs.spring.io) и `spring-boot-docker-compose` (родитель `spring-boot` + прямой `id("org.springframework.boot")`, как у `spring-boot-application`, а не через него — тоже исправлено по замечанию о композиции; `bootRun` реально поднимал `mongo:8` без ручного `docker run`, `test` реально поднимал контейнер через Testcontainers). **Пересмотрено в тот же день** — оба плагина применялись в `application-mongodb*`, но пользователь указал на асимметрию: у `jpa`/`jdbc`/`r2dbc` H2 даёт бесплатный embedded zero-config путь, а PostgreSQL/MySQL там намеренно opt-in без какой-либо инфраструктурной обвязки (без Testcontainers/Compose для них); закрывать этот же пробел у MongoDB Testcontainers/Compose, пока проект на стадии подготовки скелета, а не реальной инфраструктуры — непоследовательно. **Итог**: оба convention-плагина (`spring-boot-testcontainers`/`-testcontainers-mongodb`/`spring-boot-docker-compose`) остаются в `build-logic/` про запас, но ни один `application-mongodb*`-модуль их больше не применяет — только `spring-boot-application`, без вендор/инфраструктурной обвязки, симметрично `jpa`/`jdbc`/`r2dbc`. `compose.yaml` и Testcontainers-based тесты удалены, `NoteMongoApplicationTests`-и-аналоги — обычный `contextLoads()` (проверено — проходит без запущенной Mongo, драйвер подключается лениво). Найден и исправлен реальный баг при верификации: `NoteMysqlR2dbcApplicationTests`/аналоги падали с `JdbcDatabaseContainer$NoDriverFoundException`, хотя `PostgreSQLContainer` в том же модуле проходил без проблем. ### Стиль кода

- Импорты: `java.*` → `javax.*` → `*` → `org.springframework.*`; пустая строка между группами
- `@NullMarked` на каждом `package-info.java`; `@Nullable` из `org.jspecify.annotations`
- **`@NullUnmarked` на классах Entity/Document** (пересмотрено 2026-07-14, было `@SuppressWarnings("NullAway.Init")` на конструкторе) — декомпиляция `spring-data-commons` показала, что framework всегда выбирает no-arg конструктор для чтения из БД через прямую рефлексию, минуя args-конструкторы; `@NullUnmarked` на классе — верный псевдоним «эта модель заполняется framework'ом вне null-checker'а», явные `@Nullable` внутри по-прежнему учитываются на границе. Применено ко всем 15 model-классам
- **Jakarta Bean Validation** — доступность подключена везде (`validation`-starter + `validation-api`), сами `@NotNull`/`@NotBlank` не расставлены ни на одном из 15 Entity/Document или domain-record'ов — не реализовывать до отдельного запроса
- **`@Service` на адаптерах, `@Repository` на Spring Data repository-интерфейсах** (2026-07-14, найдено и исправлено расхождение — все 15 `{Entity}Service` были на `@Repository`)
- Промежуточная переменная перед `return`, не inline в `.body()`
- **Длина строки не ограничена** (пересмотрено 2026-07-13) — переносы только вручную, авто-форматтер не используется
- **10 персональных правил форматирования** (реализовано 2026-07-13, п. 8 «порядок методов = порядок в интерфейсе» отложен — см. CLAUDE.md → «Открытые решения»): неограниченная длина строки; никогда пустая строка перед `}`, кроме пустого тела метода/класса (там она обязательна); всегда `\n` в конце файла; ровно одна пустая строка между методами, не более одной подряд; аннотации перед полями/классами/методами — каждая на своей строке, перед параметрами — никогда не переносятся; отступ 4 пробела без табов. Ловушка: Checkstyle-сообщения форматируются через `MessageFormat` — литеральные `{`/`}` в тексте `message` ломают парсинг
- **`checkstyle { configProperties = mapOf("projectRootPackage" to "com.example") }` удалён как мёртвый код** (2026-08-15, перепроверено декомпиляцией `SpringChecks.class` из реально установленного `spring-javaformat-checkstyle-0.0.48.jar`) — Gradle-уровневый `configProperties` подставляет `${...}`-плейсхолдеры только в файле, переданном как `configFile` (наш `gradle/checkstyle/checkstyle.xml`); там таких плейсхолдеров нет. `SpringChecks` — Java-класс, хранящий `projectRootPackage` собственным полем (дефолт `"org.springframework"`, зашит байткодом), и резолвящий `${projectRootPackage}` внутри своего `spring-checkstyle.xml` через СОБСТВЕННЫЙ `Properties`, никак не связанный с Gradle `checkstyle.configProperties`. Строка была чистым no-op с 2026-07-14, но выглядела как рабочая настройка — введена в заблуждение и убрана. Реальный порядок групп импортов (`java.*`→`javax.*`→`*`→`org.springframework.*`, `com.example.*` — внутри `*`) не изменился, т.к. и раньше определялся тем же дефолтом `"org.springframework"`, а не удалённой строкой — подтверждено полным зелёным `clean check` после удаления
- **`gradle/checkstyle/checkstyle.xml` — убран мёртвый `excludes`-элемент `JavadocStyleCheck`** (2026-08-15, по вопросу пользователя «checkstyle.xml требует изменений?» после апгрейда на стабильный `0.0.48`) — сверка модулей `spring-checkstyle.xml` между кэшированным `0.0.48-SNAPSHOT` и стабильным `0.0.48` (`diff` по списку `<module name=...>`) показала ровно одно изменение: `JavadocStyleCheck` удалён из `SpringChecks` (соответствует пункту «Checkstyle 13.9.0 cannot be used due to removal of JavadocStyleCheck» из release notes 0.0.48), на его месте — `SummaryJavadocCheck` (валидирует только structure существующего Javadoc-комментария, в проекте почти нет Javadoc — не должен сработать) и `MissingJavadocPackageCheck` (уже был исключён отдельно коммитом `8631318` до этой сессии, не задел). Исключать `JavadocStyleCheck` (которого больше нет в модуле) — не ошибка, а бессмысленный dead-код, убран. **Важно не путать**: `SpringMethodOrderCheck` (enforces строго `equals`→`hashCode`→`toString`, НЕ произвольный порядок методов интерфейса — проверено байткодом, `EXPECTED_ORDER = ["equals", "hashCode", "toString"]`) и `SpringNullabilityCheck` (банит non-JSpecify nullability-аннотации, требует JSpecify-аннотацию непосредственно перед типом — полностью совпадает с уже принятой в проекте конвенцией `org.jspecify.annotations`) — оба уже присутствовали в ранее использовавшемся `0.0.48-SNAPSHOT` и не являются новым поведением от сегодняшнего апгрейда на стабильный релиз; `SpringMethodOrderCheck` в частности НЕ закрывает открытый вопрос «порядок методов реализации = порядок объявления в интерфейсе» (см. CLAUDE.md → «Открытые решения») — решает совсем другую, более узкую задачу
- **`.editorconfig` добавлен в корень репозитория** (2026-08-15) — стандарт editorconfig.org, нативная поддержка IntelliJ IDEA/VS Code/Eclipse без плагинов (в отличие от `.idea/codeStyles/`, которая к тому же сейчас не закоммичена в git — см. CLAUDE.md → «Открытые решения» → «Качественная настройка Checkstyle/codequality»). Настроен под уже действующие 10 персональных правил и `IndentationCheck` (`gradle/checkstyle/checkstyle.xml`): `indent_style = space`, `indent_size = 4`, `end_of_line = lf`, `charset = utf-8`, `insert_final_newline = true`, `trim_trailing_whitespace = true`. Максимальная длина строки намеренно не задана — `SpringChecks` не содержит `LineLengthCheck` (подтверждено грепом по `spring-checkstyle.xml` из jar), задать её в `.editorconfig` значило бы придумать несуществующее в Checkstyle ограничение и создать ложные предупреждения в IDE
- **Spotless (`com.diffplug.spotless`) добавлен — автофикс порядка импортов, IDE-агностично** (2026-08-16, повод — реальное падение `checkstyleTest` на `import.separation [SpringImportOrder]` в новом файле `../user-note/application/webmvc/JDBC-H2/src/test/.../UserNoteApplicationTests.java`, добавленном пользователем вручную через IDE) — до этого момента `SpringImportOrderCheck` (через `SpringChecks`, см. запись выше) только диагностировал нарушение порядка импортов, чинить приходилось руками или переспрашивать агента; `io.spring.javaformat`'s `format`-таск импорты не переставляет (см. память `feedback_spring_javaformat`). Новый атомарный плагин `com.example.codequality-spotless` (версия `8.9.0`, сверена напрямую по `repo1.maven.org/maven2/com/diffplug/spotless/spotless-plugin-gradle/maven-metadata.xml`, GitHub-тег `gradle/8.9.0`) применяется через `com.example.java` (шестой `codequality-*`-фрагмент, тот же паттерн, что checkstyle/jacoco/jspecify/nullaway — без диаманта, каскадом, не отдельным `id(...)` на каждом листе). `importOrder("java", "javax", "", "org.springframework")` — та же группировка, что проверяет `SpringImportOrderCheck` (`""` — catch-all-группа для всего остального, включая `com.example.*`/`jakarta.*`/`reactor.*`); аргументы, разделённые запятой, дают пустую строку между группами (в отличие от `'java|javax'`, где `|` склеил бы группу без разделителя — не наш случай). `spotlessCheck` штатно подключился в `check` — падает так же, как раньше падал только `checkstyleTest`, но теперь есть `./gradlew spotlessApply`, реально переставляющий импорты. **Дополнено в тот же день, по прямому запросу пользователя «как сделать чтобы spotlessApply применялся автоматически»**: `tasks.named("compileJava") { dependsOn("spotlessApply") }` — любой `./gradlew compileJava`/`build`/`check` теперь сам чинит порядок импортов перед компиляцией, без ручного вызова `spotlessApply` и без обращения к агенту. Выбран путь «зависимость таска», а не git pre-commit хук — хук требует установки на каждой машине отдельно и обходится `--no-verify` (тот же минус, что уже названы для `.idea/codeStyles/`), а `./gradlew clean check`/`clean build` и так обязательны перед каждым коммитом по уже действующему правилу проекта — обвязка не добавляет разработчику ни одного нового шага. Компромисс осознан и явно проговорён с пользователем: build теперь молча мутирует файлы в `src/` как побочный эффект обычной компиляции (не только когда явно попросили формат) — принято ради того, что фикс происходит одинаково для любого разработчика независимо от IDE, без дополнительной установки чего-либо. Верифицировано вживую: сломан порядок импортов в `UserNoteApplicationTests.java` вручную, запущен ТОЛЬКО `:user-note:application:JDBC:JDBC-H2:compileJava` (без явного `spotlessApply`) — задача `spotlessApply` подтянулась в граф автоматически и починила файл, `./gradlew clean check` после — зелёный **Явно НЕ включена line-ending нормализация** — Spotless по умолчанию (`LineEnding.GIT_ATTRIBUTES_FAST_ALLSAME`) требует LF и падал на файлах с локальным CRLF (`core.autocrlf=true`, задокументированная отдельная тема — см. `.gitattributes`-правило в CLAUDE.md → «Правила», фикс которой — локальный git-конфиг разработчика, не общий файл репозитория); `lineEndings = LineEnding.PRESERVE` выставлен явно, чтобы Spotless не пересекался с этой темой без отдельного решения. Верифицировано вживую: `spotlessApply` сам поправил `UserNoteApplicationTests.java` (вставил пустую строку перед `org.springframework.boot.test.context.SpringBootTest`), `./gradlew clean check` — зелёный.
