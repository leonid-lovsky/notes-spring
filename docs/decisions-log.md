### Архитектура

- **Convention plugins в `build-logic/convention/`** (included build, не `buildSrc/`) — инкрементальность, `./gradlew clean build` одной командой; id namespaced `com.example.{name}`; каталог плоский, id — из имени файла, группировка — алфавитом (слово-маркер — префикс)
- Gradle — Kotlin DSL, код — Java; в precompiled script plugins — `libs.findVersion("key").get().requiredVersion`, не typed-аксессоры каталога
- `spring-boot-starter`/`-test` — в `com.example.spring-boot` (baseline любого Boot-модуля); bootable-ось (`org.springframework.boot`) ортогональна BOM-цепочке
- Плагин `idea` удалён (deprecated)
- **Именование convention-плагинов для sort-by-name-группировки** (2026-07-23) — слово-маркер как суффикс не группирует (`{vendor}-database` → `spring-boot-database-{vendor}`); приватные фрагменты одной композиции — общий префикс (`codequality-*`); неточные имена технологий — к имени стартера Boot 4 (`oauth2-*` → `security-oauth2-*`, `client-web`/`-rest` → `client-webclient`/`-restclient`). Отклонено: объединять имена `docker-compose`/`testcontainers` — разные концерны (dev-время против тестов); **группировка по имени — только для действительно родственных технологий, не для применяемого вместе сегодня**
- Type-safe project accessors (`TYPESAFE_PROJECT_ACCESSORS`) — были включены; с 2026-09-05 флаг убран по просьбе пользователя, зависимости — `project(":...")`
- `api` — только когда тип в публичной сигнатуре модуля, иначе `implementation`
- Hexagonal (эпоха `note/`): `domain/` без JPA/Mongo/Spring; адаптеры зависят от `contract*` и явно от `domain`
- **Один контроллер/контракт/адаптер на сущность, не на операцию** (2026-07-08)
- `service/` — только при координации нескольких портов; `existsById` в контракте — валидно; `add` ≠ `replace` (JPA `save(null id)`/`save(id)`, Mongo `insert()`/`save()`)
- Старый `user-note/`: суррогатный `UUID id` + unique (`userId`, `noteId`) во всех технологиях — снимает отсутствие `@EmbeddedId` в R2DBC; unique: JPA — `@Table(uniqueConstraints)`, Mongo — `@CompoundIndex(unique=true)`, JDBC/R2DBC — только схемой
- Схема JDBC/R2DBC — `schema.sql` (2026-07-14), Flyway/Liquibase не рассматривались; enum маппится в строку из коробки
- `data-jdbc` — Spring Data JDBC (`ListCrudRepository`), решение «сырой JDBC» отменено 2026-07-14
- **Трёхуровневая иерархия портов** (2026-07-13): `{Entity}Interface[Reactive]` → `{Entity}ServiceInterface[Reactive]` → `{Entity}ControllerInterface[Reactive]`; первоначально через ковариантный `Object`
- **Трёхуровневая иерархия портов: `Object`-ковариантность → generic-параметризация** (2026-08-08) — `Object` — вырожденный контракт (наследование ради синтаксиса); заменён на `{Entity}Interface<B, S, L>`/`<B, S, L, V>` (reactive, `V` — тип удаления); реализации не менялись. Тем же днём **`L` признан неустранимым свободным параметром** — инвариантность generics (`Box<List<X>>` ≠ `Box<Iterable<X>>`, проверено `javac`), `Flux` не `Iterable` (исходники reactor-core); решение — `<B, S>` для однородных методов, `findAll`/entity-finder'ы — конкретными типами в каждом интерфейсе (прецедент `findByEmail`). Отклонены: HKT-эмуляция (тяжело), отказ от `ResponseEntity` (жёсткое требование), GoF Adapter без общего предка (теряет проверку компилятором), кодогенерация (исключена пользователем). Урок — чек-лист «стандартный паттерн прежде локального рецепта» (CLAUDE.md → «Правила»)
- Старый `user-note/` — операции по суррогатному и составному ключу раздельно; `findByUserId`/`findByNoteId` бросают свои исключения (изоляция сервисов)
- **PUT (`replace`) ≠ PATCH (`merge`)** — `merge`: `null` = «не менять»; оба — `NotFoundException` при отсутствии
- Несколько `@GetMapping` на одном пути — атрибут `params`, иначе `Ambiguous mapping`
- Reactive `findBy*` бросают `NotFoundException`, не пустой `Mono` (2026-07-13); `findAll` — `ResponseEntity<Flux<X>>`
- **Группировка модулей по слою в подпапку** (2026-08-01) — `{service}/{layer}/{module}/`, project path плоский через `projectDir`; неактуально с 2026-08-29 (`user-note/` плоский)
- `contextLoads()` vendor-скелетов на embedded H2 через `testRuntimeOnly` (2026-08-18) — smoke-тесту не нужен реальный вендор; снято 2026-09-05 реальными Testcontainers
- **Тесты — на уровне application/bootable-модулей** (2026-08-18) — sociable/classicist (реальный контекст, без Mockito); модуль-реализация владеет механизмом, не целью — поведение принимает тот, кто собирает систему (аналогия acceptance testing, симметрично DI); семантическое дублирование сценария — shared-модуль с абстрактным тестом + тонкие подклассы; структурное (`@SpringBootApplication` на лист) — неустранимо, принято
- **Вехи переписывания 2026-08-14→2026-09-24**: 08-14 удалены `auth`/`config`/`gateway`/`registry`; 08-29 удалены гексагональный слой `user-note/` и `note/`/`user/`; 08-31 модули не сворачивать, абстракция — по ходу TDD; 09-05 application-driver → application-vendor; 09-06 `application-core` испробован (отменён 09-13), `spring-boot-bootable`, PMD/SpotBugs; 09-13 `libs.versions.toml` по алфавиту; 09-21 центральный вопрос, корневое дерево, `controller-*`/`data-*`, 4 пробела; 09-24 `contract`-плагины, `codequality` воссоздан, `java-library` удалён, `java` → `base`. Подробно — «Хронология переписывания `user-note/`» ниже

### Convention plugins — принцип именования и структура

- Id — по технологии, не по модулю/слою (исключения — CLAUDE.md → «Правила» → «Имя convention-плагина»); две оси — BOM-цепочка (один родитель) и bootable (`org.springframework.boot`); актуальный граф — `docs/convention-plugins-graph.md`
- `codequality-*` — фрагменты: checkstyle, jspecify (`id("java")` + `implementation`, не `java-library` — 2026-07-15), nullaway (+ `net.ltgt.errorprone`), jacoco, jacoco-report-aggregation; позже spotless, pmd, spotbugs
- **Диамант `spring-cloud-application`** — 2026-07-15 устранён копией BOM-импорта, тем же днём пользователь восстановил (два родителя), **2026-08-01 устранён окончательно** прямым `id("org.springframework.boot")` — стало возможно после выноса actuator (`spring-boot-application` стал чистым алиасом)
- **Технологическая и вендорная ось адаптеров** (2026-07-23) — технология адаптера (jpa/jdbc/r2dbc/mongodb/mongodb-reactive) — отдельный composition-root модуль, не `@Profile`: одна repository-технология на classpath → autoconfiguration работает сама, новая технология — только новые файлы. Вендор тогда был профилем (`runtimeOnly`-драйверы + `application-{vendor}.properties`); без профиля и JDBC, и R2DBC встают на embedded H2 (проверено; предположение «у R2DBC нет embedded» было ошибкой). Mongo без embedded-аналога — Testcontainers (`org.testcontainers.mongodb.MongoDBContainer`, один контейнер на sync и reactive) + `spring-boot-docker-compose`; тем же днём сняты ради симметрии и **возвращены симметрично** — PostgreSQL/MySQL доведены до того же покрытия
- **`MySQLContainer` требует JDBC-драйвер** (wait-strategy от `JdbcDatabaseContainer`), `PostgreSQLContainer` — нет (log-based) → `testRuntimeOnly(mysql-connector-j)` в `spring-boot-testcontainers-mysql`; `testcontainers-r2dbc` необходим (без него `ClassNotFoundException` при `@ServiceConnection` → `ConnectionFactory`)
- **Вендор БД — граница Gradle-модуля, не рантайм-профиль** (2026-07-24) — профиль выбирает бин, но не убирает драйверы из `bootJar` (driver bloat); один composition root на вендор; порядок имени пересмотрен тем же днём на `{vendor}-{tech}` (`application-h2-jpa`); `spring-boot-database-{vendor}-r2dbc`; проверено `dependencies --configuration runtimeClasspath` — в модуле только свой драйвер. 2026-08-19 для `user-note/` был возврат к объединённому модулю (driver bloat принят), отменён 2026-09-05 моделью application-vendor
- **Атомизация базовых плагинов** (2026-08-01) — `base` → `java`, `library` → `java-library` (id = имя ядрового плагина; голый `com.example` отклонён — сортируется не первым); агрегатор `codequality` убран (один потребитель); `spring-boot-validation` — атомарный, только где Bean Validation реально срабатывает; `reactor` → `project-reactor` (по императиву пользователя); `spring-boot-actuator` — атомарный, явный `id` на каждом bootable-листе (выбор пользователя: атомарность важнее числа правок). Позже: 2026-09-24 `java` → `base` обратно, `codequality` воссоздан (8 фрагментов), `java-library` удалён
- **Урок `developmentOnly`** (2026-08-01) — `id("org.springframework.boot")` в `spring-boot-docker-compose` не дубликат: typed-аксессор `developmentOnly` генерируется только от плагинов, применённых в этом же файле
- Gateway-плагины → `spring-cloud-gateway-server-webflux`/`-webmvc` (имя артефакта); `spring-cloud-*`-server-плагины — родитель `spring-cloud`, bootable — явной композицией на листе, без исключений
- **Правило «диаманты — всегда устранять»** (2026-08-01) — пользователь дважды принимал диамант ради экономии кода и оба раза откатывал; закреплены три постоянных правила: атомарные плагины, 0 диамантов даже ценой copy-paste, `.gitattributes` = шаблон Initializr. **Урок**: широкий `git checkout` отката стёр `spring-boot-actuator` с 37 листов при зелёном `clean check` (исправлено 2026-08-02) — отсюда правило сверки числа применений грепом
- **Spring Batch** (2026-08-15) — `spring-boot-batch`/`-batch-jdbc`/`-batch-data-mongodb`: три независимых id Initializr — три атомарных плагина, 0 применений

- `@Service` на адаптерах, `@Repository` на Spring Data-интерфейсах (2026-07-14)
- Промежуточная переменная перед `return`
- 2026-07-13…08-16 — стиль Spring (`SpringChecks`, 10 персональных правил, свои группы импортов, `.editorconfig`, Spotless с автофиксом на `compileJava`, `lineEndings=PRESERVE`); **с 2026-09-04 заменено Google Checks + `googleJavaFormat().aosp()`** (CLAUDE.md → «Правила» → «Отступы», «Ноль ошибок и предупреждений»). - **Имя convention-плагина — по подключаемой технологии, а не по архитектурной роли, за 5 исключениями** (наблюдение 2026-09-24, зафиксировано по прямому запросу пользователя; классификация `spring-boot-bootable` дважды пересмотрена в той же сессии — сначала «исключение» без проверки, затем «не исключение» по непроверенному утверждению «bootable — официальный термин Spring Boot», в итоге проверено через `docs.spring.io` и возвращено к «исключение», см. ниже) — общее правило: имя плагина = официальное имя технологии/стартера/инструмента, который он добавляет (`spring-boot-webmvc`→`spring-boot-starter-webmvc`, `project-reactor`→`reactor-core`, `codequality-checkstyle`→Checkstyle); работает и для голых Gradle/внешних плагинов без `dependencies{}`, пока имя совпадает с официальным термином (`spring-cloud`→BOM `spring-cloud-dependencies`, `codequality-jacoco`→JaCoCo). Исключения — плагины, названные придуманным проектом словом для архитектурной роли/фазы сборки, не заимствованным у самой технологии: `com.example.base` (фундамент языка, а не одна технология; переименован из `com.example.java` 2026-09-24 по прямому запросу пользователя — обратный откат решения 2026-08-01 «`base`→`java`, id = имя обёрнутого ядрового Gradle-плагина», принятый сознательно, несмотря на то что `java` был не ролью, а точным именем технологии), `com.example.contract`/`com.example.contract-reactive` (слой порта — чистые алиасы `id("com.example.base")`/`id("com.example.project-reactor")` без единой своей зависимости, введены 2026-09-24 при разборе, почему `contract` не собирался), `com.example.codequality` (агрегатор 8 `codequality-*`, категория самого проекта, не название технологии, введён 2026-09-24 при выносе общего гейта качества из `com.example.base`; тот же плагин уже существовал и был явно удалён 2026-08-01 как «обёртка без переиспользования, один потребитель» — воссоздан заново 2026-09-24 по прямому запросу, тот же прежний повод («один потребитель») сегодня уже не единственный — 8 фрагментов вместо 5), `com.example.spring-boot-bootable` (`id("org.springframework.boot")` — официальная терминология Spring Boot для того, что этот плагин включает, — «executable jar»/«executable archive»/«fat jar» (`docs.spring.io/spring-boot/gradle-plugin/packaging.html`, проверено 2026-09-24), слова «bootable» там нет — имя придумано проектом, не заимствовано). ### Правило «.gitattributes» (полный текст)

- **`.gitattributes` — всегда точная копия шаблона Spring Initializr, ничего сверх неё** (закреплено 2026-08-01): `/gradlew text eol=lf`, `*.bat text eol=crlf`, `*.jar binary` — три строки, без `* text=auto` и любых других добавлений, даже если локальный `core.autocrlf=true` из-за этого выдаёт предупреждения `LF will be replaced by CRLF` при `git add` (сами предупреждения игнорировать — не повод отступать от стандартного шаблона; правильное место фикса — локальный `git config` конкретного контрибьютора, не общий для репозитория файл) 2026-09-21: файл был удалён коммитом `358ffb3` (2026-09-04, в составе перехода на Google Checks; намерение не выяснено) — из-за этого при `core.autocrlf=true` свежий checkout давал `gradlew` с CRLF (`/bin/sh^M: bad interpreter`, воспроизведено в `git worktree`); восстановлен пользователем 2026-09-21 (три строки шаблона; в конце файла добавлен перевод строки, у шаблона его нет), эффект проверен: `git check-attr` — `gradlew` text/eol=lf, `*.jar` binary

### Правило «Конвенции — везде» (полный текст)

- **Конвенции — везде, где применимо, и без расхождений внутри самих себя** (2026-09-13, повод — расхождение суффикса `-plugin` в `gradle/libs.versions.toml`, найдено пользователем; разбор по `git log -p` — несогласованность зародилась ещё в дорефакторинговых Groovy-переменных `buildSrc` (`errorpronePluginVersion` vs `springBootVersion`/`dependencyManagementVersion`, ни один суффикс не был решением, просто разные локальные имена), механически перенесена в каталог версий при миграции 2026-07-01, дальше закреплена по аналогии в одних местах (`spotbugs-plugin`, 2026-09-06) и проигнорирована в других (`spotless`, 2026-08-16) — ни разу никто не сверился с уже существующим прецедентом при добавлении новой записи, потому что сверяться было не с чем: правило нигде не было записано явно) — практически всё в проекте должно следовать той или иной явной конвенции (naming/порядок/структура), не оставаться на усмотрение последней добавленной по соседству строки. Два разных механизма для двух разных классов конвенций: (1) **механически проверяемые** (Java-стиль/форматирование/порядок импортов) — уже закрыты Checkstyle/Spotless/PMD/SpotBugs, `check` красный при нарушении, расхождение невозможно по конструкции, дополнительно ничего не требуется; (2) **существующие только прозой** (naming в `libs.versions.toml`, паттерны раздела «Именование», атомарность convention-плагинов, leaf-purity) — расхождение здесь неизбежно без парной проверки: формулировать правило явным проверяемым критерием (не «как принято», а конкретное условие) **и** рядом класть воспроизводимую команду проверки (grep/список) — уже действующий в этом файле паттерн (пример — leaf-purity-grep у правила «Только convention-плагины…» ниже, сверка числа применений у правила «После широкого `git checkout`…» ниже), применять его и к новым такого рода правилам, не изобретать заново. Полная механическая проверка сборкой (кастомный Gradle-таск/тест) — эскалация на будущее, не default: нестандартный код в `build-logic/` по-прежнему требует отдельного «делай», см. «Без самоуправства в build-логике» — правило не переопределяется, только применяется к новому классу случаев

### Правило «Плагины-расширители» (полный текст)

- **Плагины-расширители (`java-library` и подобные) — только там, где реально нужна расширенная конфигурация, не каскадом «на всякий случай»** (введено 2026-07-15): прецедент — `com.example.jspecify` подключал `id("java-library")` только ради `api("org.jspecify")`, и через каскад `base → codequality → jspecify` эта конфигурация просачивалась во все 39 модулей, хотя видимость зависимости на потребителях от `api`/`implementation` не зависела (jspecify достаётся каждому модулю напрямую через собственный каскад `id(...)`, а не через project-to-project зависимость, где `api` реально что-то протаскивает дальше). Исправлено на `id("java")` + `implementation(...)`; `java-library` тогда остался только в `com.example.java-library` (переименован из `com.example.library` 2026-08-01 — id совпадает с именем обёрнутого ядрового Gradle-плагина, см. `docs/decisions-log.md`), применяемом `contract`/`contract-reactive`, где `api(projects.*.domain)` был настоящей публичной сигнатурой — **сам плагин удалён 2026-09-24**, `domain`-слой, ради которого он существовал, удалён ещё 2026-08-29, `contract`/`contract-reactive` сегодня не используют `api(...)` вообще (см. `com.example.contract`/`com.example.contract-reactive`, «Правила» → исключения из правила именования плагинов); в проекте сейчас нет ни одного плагина-расширителя — правило актуально на случай, если он понадобится снова. При добавлении/правке convention-плагина, если он подключает id, расширяющий базовый (`java-library` поверх `java` и аналоги) — проверять: (1) нужна ли расширенная конфигурация именно этому плагину для собственной декларации зависимостей, или сводится к базовой; (2) не полагаться на то, что зависимость «протекает» api-путём к потребителям, если фактическая топология — каскадное применение `id(...)` внутри одного проекта, а не project-to-project. Проверка: `grep -rln 'id("java-library")'` по `build-logic/convention/` — список плагинов должен совпадать со списком, где реально объявлен `api(...)`

### Правило «Sandboxed/remote-окружение» (полный текст с апдейтом)

- **⚠️ Sandboxed/remote-агент окружение может не уметь запустить сборку вообще** (2026-07-24, обнаружено при работе через Claude Code on the web; **частично решено** в тот же день, см. апдейт ниже): проект требует Java 25 (`.java-version`), но в некоторых remote execution environment физически установлена только JDK 21, а автозагрузка нужного тулчейна через Gradle toolchain resolver `foojay` (`api.foojay.io`) заблокирована сетевой политикой окружения (`CONNECT tunnel failed, 403` — так же падает и прямой `curl` на `api.foojay.io`/`start.spring.io`, не только Gradle). ### Открытое решение «Дублирование application.properties» (полный текст)

  - **Дублирование `application.properties` в 8 листьях — реализовано 2026-09-21** (пока что то, что можно существующими модулями): технологические строки (`logging.level.org.springframework.data=DEBUG` + `...data.<jdbc|r2dbc|mongodb>=DEBUG`) вынесены в `user-note/data-<tech>/src/main/resources/application-data-<tech>.properties`, лист подключает их строкой `spring.profiles.include=data-<tech>` (профильный файл из зависимого модуля Boot находит по имени); в листе оставались `problemdetails`, `logging.level.org.springframework.web=DEBUG` и строка `include` (вечером — в `controller-*`, см. ниже). Проверено (Boot 4.1.0, опыты в отдельном `git worktree` и на месте): набор DEBUG-логгеров в отчётах тестов всех 8 листьев до и после идентичен (в нём есть `o.s.d.*`), `clean check` зелёный, IntelliJ IDEA не показывает ошибок ни в листьях, ни в файлах модулей (`get_file_problems`). Путь к решению (опыты): `application.properties` в модуле-зависимости НЕ работает — его перекрывает одноимённый файл листа; `spring.config.import=classpath:…` работает в Boot, но IDEA разрешает `classpath:` только среди собственных ресурсов модуля (`Cannot resolve file` для файлов зависимых модулей и jar); файл с произвольным именем IDEA не признаёт конфигурацией Spring Boot (`Unused property`), профильное `application-<x>.properties` признаёт автоматически (документация JetBrains; остальные — вручную в Project Structure, то есть настройкой IDE, не репозитория); `spring.profiles.include` (документация Boot: только в непрофильных документах) снимает обе проблемы; `@PropertySource` не подходит (документация: слишком поздно для `logging.*`); `EnvironmentPostProcessor` не проверялся. Цена: Boot пишет `The following 1 profile is active: "data-<tech>"`, профиль виден в `Environment` (фрагмент конфигурации, не выбор вендора); что профильные файлы грузятся из зависимых jar, документация не говорит — подтверждено только опытом. Остаточное дублирование: только строка `include` (структурно неизбежна) — `web`/`problemdetails` вынесены вечером тем же механизмом в `controller-webmvc`/`controller-webflux`. Общий принцип: общее живёт на том уровне дерева, где оно общее, механизм — по виду артефакта (код — shared-модуль/`testFixtures`, сборка — convention-плагин, конфигурация — профильные файлы модулей + `spring.profiles.include`)

  3. ### Открытое решение «Чистая архитектура» (полный текст с разбором вариантов)

- **Чистая архитектура — решено 2026-09-29 (пользователь): сценарии реализуются в `data-*` (вариант (В), толстый порт) — прагматично сейчас, рефакторинг к выделенному слою сценариев — позже, это тот же сквозной вопрос устранения дублирования (правила копируются в 4 `data-*`)**; порты — в `contract-synchronous`/`contract-reactive` без фреймворка, модели запроса/ответа — в `contract-common` (общий для обоих; `contract-reactive` не зависит от синхронного контракта — указание пользователя 2026-09-29), реализации — `{Port}Service` (`FindNoteByIdSynchronousService`/`FindNoteByIdReactiveService`) в `data-*` (тела пока `UnsupportedOperationException`), порты — с суффиксом стека: `Synchronous` (`FindNoteByIdSynchronous`, решение пользователя 2026-09-29) и `Reactive` (`FindNoteByIdReactive`), **один интерфейс на сценарий** (`FindNoteByIdSynchronous`, `CreateNote`, `ReplaceNoteByIdSynchronous`, `UpdateNoteByIdSynchronous`, `DeleteNoteByIdSynchronous`, у `User` так же; пара в `contract-reactive`), **семантика HTTP — «максимально простой вариант» (решение пользователя 2026-09-29, отменяет upsert того же дня)**: `id` задаёт клиент, без автогенерации; `GET /{id}` — нет → 404; `POST /{id}` `create{E}ById(id, request)` — есть → 409 Conflict (RFC 9110 §15.5.10), создал → 201; `PUT /{id}` — только полная замена, нет → 404 (RFC допускает `PUT` без создания); `PATCH /{id}` — меняются только переданные поля, нет → 404; `DELETE /{id}` — возвращает удалённую сущность (200), нет → 404; названные отступления от стандартов — `PATCH` с `{E}Request` в `application/json`, не RFC 7396; нет ETag/условных запросов (SHOULD RFC 9110 §8.8.3); `POST` на адрес ещё не существующего ресурса вместо канонического для клиентского `id` `PUT`; единственный метод порта — `execute` (решение пользователя 2026-09-29: `findNoteById.execute(id)`), `DeleteNoteByIdSynchronous` возвращает `NoteResponse` удалённой заметки (200 с представлением, RFC 9110 §9.3.5), `CreateNote` → `CreateNoteByIdSynchronous`, **одна реализация на сценарий** в каждом `data-*` (решение пользователя 2026-09-29, ISP; бины — стереотипы Spring в `data-*`, не в контрактах); контроллер — тонкий адаптер: одна строка на метод, вызов порта, без `if` и приватных методов. Прежний разбор вариантов: (2026-09-29, консультация) — круги Мартина на модулях: сущности `Note`/`User`/`UserNote` на чистой Java (новый модуль, прежний `domain` удалён 2026-08-29) → сценарии (входные порты «один сценарий — один интерфейс», interactor, модели запроса/ответа, выходной порт хранилища; правило «не найдено», генерация `id`, `replace`/`merge`) в двух копиях sync/reactive (Reactor во внутреннем круге reactive — названное отступление) → адаптеры `controller-*`/`data-*` (своя модель хранения + маппинг) → листья `application-*` как Main. Правило зависимостей обеспечивают модули Gradle при компиляции. По дереву: сущности — первое содержимое узла «общее»; тест на порт хранилища — `testFixtures` модуля сценариев; риск — маппинг ×4 в `data-*`; бины interactor-ов — по одной `@Configuration` на стек в `controller-*` или `@Service` на interactor (проще и ближе к AutoConfiguration по правилу «Принципы — прагматично», но Spring во внутреннем круге). Варианты: (А) строгая (presenter, модели на каждой границе) — буквально по книге, много моделей/маппинга, presenter плохо сочетается с `ResponseEntity`/`Mono`; (Б) прагматичная — interactor возвращает модель ответа, `{Entity}Request`/`{Entity}Response` одновременно модели сценария и JSON, Reactor в reactive-сценариях — рекомендация ассистента, закрывает пп.1–3 «Решений, которые нужно принять»; (В) толстый порт без слоя сценариев (прежний `note/`) — не Clean, правила копируются по адаптерам.
