## Правила

- **Голый API-стартер не подключается, если есть обёртка (Spring Data и т. п.) для той же технологии — даже если технически обёртка не несёт 100% функционала голого стартера** (2026-08-15, явное решение пользователя, отменяет собственную рекомендацию агента по итогам факт-проверки) — прецедент: `spring-boot-starter-elasticsearch` подключён рядом с `spring-boot-starter-data-elasticsearch` (несёт реальный `elasticsearch-java`-драйвер, которого `data-elasticsearch` транзитивно не тянет, проверено и POM, и Gradle Module Metadata) — пользователь всё равно убрал голый стартер вручную и явно сформулировал общее правило: «не используем голый API при наличии обёртки». Риск (Spring Data Elasticsearch без реального клиента может не заработать в рантайме) осознан пользователем — «проверить при реальном обращении», не превентивным подключением про запас. Это отменяет более узкое обоснование из записи 2026-08-15 «пересматривает правило... но избыточность, доказанную фактами, применять не мешает» — теперь правило шире факта транзитивности: голый API не нужен как класс решений, независимо от того, доказана ли конкретная избыточность фактами по каждой технологии отдельно
- **⚠️ ИСТОЧНИК ИСТИНЫ ДЛЯ SPRING-ФАКТОВ — НЕ MAVEN CENTRAL ПОИСК** [НЕ СОКРАЩАТЬ/НЕ УДАЛЯТЬ — исключение из правила «убирать избыточность», даже при явной задаче уменьшить объём CLAUDE.md] (2026-07-14, резкая реакция пользователя на ошибку): вопрос «существует ли артефакт X» **никогда** не проверять через `search.maven.org` (Solr-индекс отстаёт от реального репозитория, `0 numFound` НЕ значит «не существует» — конкретная ошибка: заявил, что `spring-boot-starter-r2dbc` не существует по 0 результатам поиска, хотя это реальный отдельный от `data-r2dbc` стартер). Источник истины — **Spring Initializr** (`start.spring.io/metadata/client` — реальный список id/name/description), **GitHub spring-projects**, **официальная документация docs.spring.io**. Maven Central годится только для номера версии уже известного, существующего артефакта — не для вопроса о самом его существовании. **`docs/spring-boot-starters-reference.md`** (2026-07-14) — дословная копия со Spring Initializr, лежит в репозитории локально: для вопроса «существует ли стартер X» и «как называется» обращаться сначала туда, не в web-поиск. При выборе/добавлении стартера под конкретную технологию — сверяться по этому файлу, есть ли для неё отдельный `-test`-компаньон (`spring-boot-starter-{tech}-test`), и подключать его вместе с основным, если существует — не пропускать по своему усмотрению (см. прецедент с `spring-boot-starter-r2dbc`/`-jdbc`/`-elasticsearch`, где `-test`-версия изначально была упущена). Также перед добавлением зависимости в Spring Boot модуль — сверяться, нет ли для этой технологии уже готового `spring-boot-starter-*`: если есть, подключать именно его, а не «сырую» внешнюю зависимость напрямую (starter уже несёт нужный BOM-managed набор транзитивных зависимостей и autoconfiguration — обходить его напрямую значит терять то и другое). **Принадлежность к Initializr — определять только буквальным поиском строки артефакта в `docs/spring-boot-starters-reference.md`, никогда рассуждением по форме имени артефакта** (2026-08-02, резкая реакция пользователя на ошибку): конкретная ошибка — заявил, что `org.springframework.boot:spring-boot-docker-compose` «не Initializr-стартер», по неверной логике «раз в имени артефакта нет `-starter-`, значит это core-модуль Boot, а не выбираемая в Initializr зависимость» — вывод по паттерну имени, без единой проверки. У Spring Initializr многие зависимости (Docker Compose Support, Lombok, Actuator и др.) не содержат `-starter-` в имени артефакта, наличие/отсутствие этого подслова в имени не говорит ничего о членстве в Initializr. Строка `developmentOnly 'org.springframework.boot:spring-boot-docker-compose'` при этом дословно уже присутствовала в `docs/spring-boot-starters-reference.md:178` — файл был не прочитан перед утверждением. Правило: любое утверждение вида «X не относится к Initializr»/«X не существует как стартер» — сначала grep по точной строке артефакта в `docs/spring-boot-starters-reference.md`, и только отсутствие там даёт право на такое утверждение (с оговоркой, что файл не абсолютно полон — см. соответствующий пункт правила выше)

- **Перед архитектурным ответом — контрольный список: стандартный паттерн / переформулировка / другой угол / альтернативы** (2026-08-08, из диалога про единый контракт Controller/Service — см. «Задачи» → «Завершено» и `docs/decisions-log.md` → «Архитектура», где ассистент трижды прошёлся по локальным вариациям, прежде чем распознать типовой случай): перед предложением решения явно проверять четыре вопроса, не хвататься за первый локальный рецепт — (1) не частный ли это случай известного стандартного паттерна (пример — «N классов с одной сигнатурой, разным типом возврата» → параметрический полиморфизм, как `Optional<T>`/`Comparator<T>`/`CrudRepository<T, ID>`); (2) можно ли переформулировать саму постановку задачи, не размывая заданных ограничений; (3) можно ли посмотреть с другого угла — от абстрактной формы задачи, а не от уже реализованного в репозитории локального прецедента; (4) есть ли альтернативы помимо первой идеи. Решения, снимающие заданное ограничение ради тривиальности (пример — убрать `ResponseEntity` из Controller), предлагать можно, но явно помечая «меняет постановку задачи», не как рекомендованный ответ. **Чек-лист проходить явно и видимо в самом ответе** (уточнено 2026-08-08 и 2026-08-21 — резкая реакция на буквальные ярлыки-вопросы вида «Стандартный паттерн? Да —») — не молчаливая внутренняя проверка, а показанные шаги рассуждения обычной связной прозой, без ярлыков/риторических заголовков на каждый пункт — чек-лист держится в голове, в тексте виден только результат естественным языком; при повторном применении к уже решённому вопросу — переискать заново, не просто повторить вывод (пример — контракт Controller/Service передуман через рамку Adapter/GoF и driving/driven-симметрию портов, не просто снова назван «параметрический полиморфизм»). **Свежий взгляд, не фиксация на уже предложенных вариантах** — набор вариантов, уже прозвучавших в диалоге, не исчерпывающий по умолчанию, не потолок для дальнейшего поиска

Отменяет более раннюю формулировку «решение за пользователем»: пользователь дважды осознанно принимал диамант ради устранения дублирования (`spring-cloud-application`, 2026-07-15 и 2026-08-01) и оба раза откатывал обратно к нулю диамантов — правило зафиксировано по этому повторяющемуся исходу. Находку по-прежнему сообщать всегда, действие по умолчанию — «устранить», не «спросить». Прецедент устранения без дублирования: `spring-cloud-application` (диамант `spring-cloud`+`spring-boot-application`) устранён прямым `id("org.springframework.boot")`, т. к. `spring-boot-application` стал чистым alias — 0 диамант, 0 дублирования. Прецедент устранения ценой дублирования: `spring-boot-actuator` — атомарный плагин, явный `id(...)` на каждом из 37 bootable-листьев (не встроен вторым родителем в `spring-boot-application`/`spring-cloud-application`, хотя это устранило бы 37 явных `id(...)` ценой диаманта — отклонено). Никаких shared-функций в `build-logic/` для устранения схождений — только композиция через `id(...)`. **Два вида схождения**: вид 1 — диамант внутри самого convention-плагина (файл в `build-logic/` в своём `plugins{}` вызывает 2+ `id("com.example.*")`, сходящихся в общем предке) — устранять всегда. Вид 2 — лист (`build.gradle.kts` сервиса) применяет 2+ плагина, сходящихся в общем предке (`note/application-h2-jpa` — `spring-boot-application`+`spring-boot-database-h2`; `gateway/application` — `spring-cloud-application`+3 `spring-cloud-*`) — не диамант для устранения, осознанная композиция независимых плагинов в точке использования, ради которой вся система построена (решено 2026-07-15, не поднимать заново без нового повода)
- **Дублирование в коде — стремится к абсолютному нулю, в существующем и будущем коде** (2026-09-06) — не буквальный ноль (часть повторов навязана фреймворком/архитектурой — прецеденты `UserNoteTestApplication.java`/`build.gradle.kts`, см. «Активная нить» → «2026-09-06»), а ноль необъяснённого дублирования. Механизм — структурный, не аудит/тул (PMD CPD отклонён как избыточный): реально общий код выносится в отдельный модуль, для мест, которые ДОЛЖНЫ быть чистой композицией — физическое обнуление `sourceSets`, а не полагание на дисциплину. **Не любой ценой** — вынос через не-bootable модуль-зависимость (`application-core`, введён 2026-09-06, отменён 2026-09-13) не годится, если он жертвует другим инвариантом (bootable-природой листового модуля) — см. «Открытые решения» → «Как выделить общее из `application-vendor`…»
- **Convention-плагины — всегда атомарны, один плагин = один концерн/технология** (закреплено как постоянное правило 2026-08-01, до этого — серия точечных решений, см. `docs/decisions-log.md` → «Атомизация базовых плагинов»): не объединять в одном плагине несколько независимых зависимостей/стартеров ради удобства, даже если они сегодня всегда применяются вместе (прецедент — вынос `spring-boot-starter-validation` из `spring-boot` в отдельный `spring-boot-validation`; воссоздание `spring-boot-actuator` из `spring-boot-application`). Если возможность применяется не везде одинаково или концептуально независима — отдельный плагин, композиция через явный `id(...)` в точке использования, не через объединение содержимого
- **Предпочитаем явную композицию неявному наследованию — во всём проекте, не только в convention-плагинах** (закреплено 2026-08-01, обобщает предыдущий пункт и правило про диаманты — все три работают вместе на один результат; область действия расширена пользователем в тот же день с Gradle-плагинов на весь проект целиком): когда модулю/классу/конфигурации нужны 2+ независимые возможности — явное объявление каждой рядом, в точке использования, а не одна возможность, встроенная родителем/зависимостью другой ради экономии строк. Действует одинаково в трёх плоскостях:
  - **Convention-плагины** (где правило впервые сформулировано) — явный `id(...)` для каждой возможности на листе, не встраивание через родителя. Даже если возможность нужна на 100% модулей, где применяется родитель, без единого исключения (как у `spring-boot-actuator`) — это не повод встраивать её через наследование. Отход от композиции — не ради компактности кода, а только когда явной альтернативы физически не существует (прецедент: `spring-boot-docker-compose` — `id("org.springframework.boot")` там не встраивание ради экономии, а техническая необходимость для typed-аксессора `developmentOnly`)
  - **Java-код** — предпочитать композицию наследованию классов везде, где выбор есть (внедрение зависимости/делегирование вместо `extends` ради переиспользования кода); интерфейсная иерархия портов (`{Entity}Interface`→`{Entity}ServiceInterface`/`{Entity}ControllerInterface`, см. «Именование») — контракт, не реализация, этого правила не касается
  - **Настройки/конфигурация** (Spring `application.properties`, профили и т. п.) — явные, отдельные свойства/файлы на концерн, не неявное наследование конфигурации через профили-предки или глубоко вложенные default-механизмы

  Естественное следствие для всех трёх — диамантов/скрытых схождений не возникает вообще, потому что диамант — всегда результат наследования от 2+ путей, а не композиции
- **`.gitattributes` — всегда точная копия шаблона Spring Initializr, ничего сверх неё** (закреплено 2026-08-01): `/gradlew text eol=lf`, `*.bat text eol=crlf`, `*.jar binary` — три строки, без `* text=auto` и любых других добавлений, даже если локальный `core.autocrlf=true` из-за этого выдаёт предупреждения `LF will be replaced by CRLF` при `git add` (сами предупреждения игнорировать — не повод отступать от стандартного шаблона; правильное место фикса — локальный `git config` конкретного контрибьютора, не общий для репозитория файл)
- **Только convention-плагины — листовые модули не применяют ничего напрямую** (проверено и закреплено 2026-07-15; project-to-project форма пересмотрена 2026-09-05): ни один листовой `build.gradle.kts` не должен применять plugin id, не начинающийся с `com.example.*`, и не должен объявлять зависимость иначе как `implementation(project(":..."))`/`api(project(":..."))` (project-to-project, строковый path). **Не** typesafe `projects.*`-accessor — при подключении `user-note/data-*` к `application-*` 2026-09-05 пробовали `projects.userNote.dataJdbc` (требует `enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")` в `settings.gradle.kts`, без него `projects` резолвится в булт-ин `TaskContainer.projects`/`ProjectReportTask`, ошибка компиляции), пользователь явно попросил убрать флаг — текущая форма зависимости `project(":...")`. Все внешние зависимости, плагины, версии и настройка сборки — только через `build-logic/convention/`. Проверка (список сервисов сузился до `user-note` — `note`/`user`/`auth`/`registry`/`config`/`gateway` удалены из репозитория, см. «Задачи» → «Статус по сервисам»; вернуть остальные в список, если сервисы вернутся): `grep -rn 'id("' --include="build.gradle.kts" user-note | grep -v 'id("com\.example\.'` и аналогично по `dependencies{}`-блокам — оба должны быть пустыми. Прогонять эту проверку при добавлении новой зависимости/плагина в любой листовой модуль
- **Конвенции — везде, где применимо, и без расхождений внутри самих себя** (2026-09-13, повод — расхождение суффикса `-plugin` в `gradle/libs.versions.toml`, найдено пользователем; разбор по `git log -p` — несогласованность зародилась ещё в дорефакторинговых Groovy-переменных `buildSrc` (`errorpronePluginVersion` vs `springBootVersion`/`dependencyManagementVersion`, ни один суффикс не был решением, просто разные локальные имена), механически перенесена в каталог версий при миграции 2026-07-01, дальше закреплена по аналогии в одних местах (`spotbugs-plugin`, 2026-09-06) и проигнорирована в других (`spotless`, 2026-08-16) — ни разу никто не сверился с уже существующим прецедентом при добавлении новой записи, потому что сверяться было не с чем: правило нигде не было записано явно) — практически всё в проекте должно следовать той или иной явной конвенции (naming/порядок/структура), не оставаться на усмотрение последней добавленной по соседству строки. Два разных механизма для двух разных классов конвенций: (1) **механически проверяемые** (Java-стиль/форматирование/порядок импортов) — уже закрыты Checkstyle/Spotless/PMD/SpotBugs, `check` красный при нарушении, расхождение невозможно по конструкции, дополнительно ничего не требуется; (2) **существующие только прозой** (naming в `libs.versions.toml`, паттерны раздела «Именование», атомарность convention-плагинов, leaf-purity) — расхождение здесь неизбежно без парной проверки: формулировать правило явным проверяемым критерием (не «как принято», а конкретное условие) **и** рядом класть воспроизводимую команду проверки (grep/список) — уже действующий в этом файле паттерн (пример — leaf-purity-grep у правила «Только convention-плагины…» ниже, сверка числа применений у правила «После широкого `git checkout`…» ниже), применять его и к новым такого рода правилам, не изобретать заново. Полная механическая проверка сборкой (кастомный Gradle-таск/тест) — эскалация на будущее, не default: нестандартный код в `build-logic/` по-прежнему требует отдельного «делай», см. «Без самоуправства в build-логике» — правило не переопределяется, только применяется к новому классу случаев

- **Плагины-расширители (`java-library` и подобные) — только там, где реально нужна расширенная конфигурация, не каскадом «на всякий случай»** (введено 2026-07-15): прецедент — `com.example.jspecify` подключал `id("java-library")` только ради `api("org.jspecify")`, и через каскад `base → codequality → jspecify` эта конфигурация просачивалась во все 39 модулей, хотя видимость зависимости на потребителях от `api`/`implementation` не зависела (jspecify достаётся каждому модулю напрямую через собственный каскад `id(...)`, а не через project-to-project зависимость, где `api` реально что-то протаскивает дальше). Проверка: `grep -rln 'id("java-library")'` по `build-logic/convention/` — список плагинов должен совпадать со списком, где реально объявлен `api(...)`

**Целевая картина (согласована 2026-08-31, вечер; порядок работы уточнён 2026-09-04) — сверху вниз:**
1. `user-note` — одно приложение с одним поведением. Описывается один раз (максимум два: sync/reactive — и только из-за конфликта webmvc/webflux на classpath). Всё остальное — сменная реализация. **Уточнение 2026-09-04**: граница sync/reactive (как и вендорная граница) — чисто техническая, вынужденная сборкой (`WebApplicationType.deduceFromClasspath()`, driver bloat), не поведенческая — для потребителя API (и для порт-теста через `WebTestClient`/`TestRestTemplate` на реальном порту, см. п.1 ниже) разницы нет вообще, контракт один. Та же логика, что уже привела к «HTTP-контракт один на все 5 модулей» — распространяется и на смысл самого разделения sync/reactive: оно существует ради компилятора/classpath, не ради разного поведения.
2. Абстракция = порт (`UserNoteInterface`/`…Reactive`) + `application-core`(`-reactive`) (общий `@SpringBootApplication` + тест поведения на порт в `testFixtures`) + convention-плагин `com.example.user-note-application`(`-reactive`) — **возникает по ходу TDD, не выносится заранее** (пересмотрено 2026-09-04, см. выше).
3. Конкретные composition-root различаются **ТОЛЬКО составом classpath**. Каждый `application-X` = «плагин абстракции + плагин адаптера», ни своей Java, ни своего теста — это целевое состояние ПОСЛЕ TDD, не стартовая точка.
4. Ось адаптеров = SQL vs non-SQL. SQL: один адаптер на модель доступа (`jdbc`/`jpa`/`r2dbc`) покрывает все SQL-вендоры, вендор = профиль. Non-SQL (Cassandra/Couchbase/Neo4j/Elasticsearch/DynamoDB/Redis/Mongo/in-memory): каждый вендор — свой адаптер и свой модуль. sync/reactive удваивает каждый, где драйвер позволяет.
5. Тесты — та же архитектура, что код: один тест на порт, параметризован, гоняется против каждой реализации. **Два уровня, не один** (уточнено 2026-09-04): тест на порт (service+persistence, без HTTP) и E2E-тест через HTTP (кандидат на shared testFixtures — контракт не зависит от технологии персистенции). **Почему один и тот же тест на N реализаций доказывает «разницы нет», не просто совпадение** — рассмотрена и отклонена альтернатива differential testing (сверка вывода байт-в-байт без явных assert-ов, как тестируют компиляторы): (1) CRUD-сущность — оракул пишется легко, не тот случай; (2) differential ловит только расхождение МЕЖДУ реализациями, общий баг во всех пяти (например в самом контракте порта) не найдёт, explicit-assert найдёт; (3) N-парных сравнений растёт комбинаторно, один прогон общего теста — линейно. Дыра conformance-подхода — ловит только то, что явно assert-ит автор теста; принята как цена, оправданная простотой домена.
6. Это корневая идея проекта, рекурсивно: hexagonal в коде + convention-плагины на уровне системы — и та же связка абстракция/реализация/DIP на слое composition-root.
7. Порядок работы (пересмотрено 2026-09-04): (1) TDD против порта, код по слоям вниз, абстракция появляется по ходу → (2) compose для dev runtime.

1. **Полный TDD против порта — тест написан НА АБСТРАКЦИИ, не на реализации, порт и абстракция выводятся ПО ХОДУ, не заранее** (объединяет прежние п.0+п.1, пересмотрено 2026-09-04) — тест поведения **один**, зависит **только от `UserNoteInterface` / `UserNoteReactiveInterface`** (не от `DataSource`/`MongoTemplate`), параметризован технологией и вендором (`@ParameterizedTest`/`@ActiveProfiles` по профилям), гоняется против каждого из 5 модулей. Конкретный адаптер модуля удовлетворяет контракт абстракции — реализация подставляется под тест, не наоборот. `getDatabaseProductName()`/`buildInfo`-ассерты и любые `abstract`-пробы удаляются — это связанность абстракции с реализацией. **К тестам — те же паттерны проектирования и та же архитектура, что к коду приложения** (принципиальное требование пользователя, не деталь оформления). sociable/classicist-стиль, реальный Spring-контекст, Testcontainers (принцип — «Завершено» → «2026-08-18, архитектура тестирования»). От тестов — реальный доменный/persistence/presentation код (нижние слои, идём вниз).
   - **Два уровня теста, оба на composition-root, оба — кандидаты на shared testFixtures** (обсуждено 2026-09-04): (а) **тест на порт** — `@Autowired UserNoteInterface`, проверяет service+persistence, минуя контроллер; (б) **E2E-тест через HTTP** — отдельный, не то же самое, ловит то, что порт-тест не видит (маппинг JSON, `@Valid`, `NoteExceptionHandler`→`ProblemDetail`, HTTP-статусы). Рекомендация по механике E2E: `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate` (webmvc) / `WebTestClient` (webflux) на реальном порту — **не** `@AutoConfigureMockMvc`/`@AutoConfigureWebTestClient`-in-container (тот не гоняет через реальный сокет, тот же компромисс, что и мок, только тоньше — противоречит уже принятому sociable/classicist-принципу). Оба уровня — максимум 2 варианта каждый (sync/reactive), как и порт-тест — не отдельная новая абстракционная задача, тот же `application-core`.
   - **Уточнение того же вечера — E2E не удваивается на sync/reactive, порт-тест удваивается** (пользователь поймал ошибку в исходной рекомендации). Порт-тест — максимум 2 варианта, механически неустранимо: `UserNoteInterface.add(...)` возвращает `UserNote`, `UserNoteReactiveInterface.add(...)` — `Mono<UserNote>`, разные Java-типы, один тестовый метод не годится для обоих без блокирующего/реактивного моста (убивает смысл теста реактивного пути). E2E/HTTP-тест — **один**, не два: при `@SpringBootTest(webEnvironment = RANDOM_PORT)` и `WebTestClient.bindToServer().baseUrl("http://localhost:"+port)` (или `TestRestTemplate`) клиент работает поверх реального сокета через HTTP — ему не важно, blocking или reactive сервер на другом конце, это чистый протокол. Различие sync/reactive у тест-клиента существует только в in-container-режиме (`@AutoConfigureMockMvc`↔`DispatcherServlet`, `@AutoConfigureWebTestClient`↔`WebHandler` напрямую, без сокета) — который уже отвергнут выше в пользу настоящего HTTP. Итог: HTTP-контракт (JSON/статусы) один на все 5 модулей, один E2E-тест-класс их все покрывает.
   - **Форма самого теста — один сценарный метод («flow»), не россыпь независимых assert-ов** (обсуждено 2026-09-04, вопрос пользователя «как протестировать, что у пользователя один user flow вне зависимости от технологии» — про форму теста, не про механику расшаривания, изначально понято неверно). «Один user flow» доказывается не тем, что пять реализаций проходят похожие, но раздельные `@Test`-методы (`addThenFindByIdReturnsSameUserNote()`, `removeThenExistsByIdReturnsFalse()` и т. п. по отдельности) — а тем, что это буквально **один сценарный метод** (условно `userManagesTheirNoteEndToEnd()`), описывающий реальную последовательность действий пользователя (создал → прочитал → изменил → удалил → убедился, что удалено) целиком в одном потоке, лежащий в `testFixtures`, прогоняемый целиком против каждого из 5 модулей. Сам факт «это один метод, не пять» и делает идею «один flow» видимой в коде теста, а не только в механизме его расшаривания (testFixtures byte-identical class — гарантия, что тест не разъедется, но не про форму самого сценария).
   - **Организация проверки API при нескольких composition root** (обсуждено 2026-09-04, вопрос пользователя «как организовать проверку API при наличии нескольких composition root» — финальная точка длинного разбора, начатого с «один API, одни результаты», прошедшего через мехнику testFixtures/форму теста/black-box). У проекта нет одного работающего приложения с переключаемой начинкой — 5 отдельных composition root, 5 отдельных `main()`, 5 независимо собранных графов объектов. «Один API» — не факт про единый процесс, а контракт, который каждый composition root обязан реализовать по отдельности; доказывается не одним прогоном, а N прогонами одного и того же теста без изменений. Конкретная организация:
     - Тест физически лежит в `application-core`/`testFixtures` (порт-тест на `UserNoteInterface`) и `application-core-reactive`/`testFixtures` (на `UserNoteReactiveInterface`) — **2 копии, не 5**, по числу типов порта, не по числу composition root
     - Каждый из 5 `application-X/build.gradle.kts` подхватывает нужный набор не копированием, а зависимостью — convention-плагин `com.example.user-note-application`(`-reactive`) сам тянет `testImplementation(testFixtures(project(":user-note:application-core"[-reactive])))`; лист выбирает только, какой convention-плагин применить (sync/reactive), тест наследуется автоматически
     - Прогон по всем N сразу — уже существующий `./gradlew clean check --continue` из корня: Gradle сам находит все `include(...)`-модули `settings.gradle.kts` и гоняет их `test`-таски независимо; ничего специального «раннера по composition root» писать не нужно, это прямое следствие уже выбранной multi-module-структуры. `--continue` обязателен именно здесь — без него сборка остановится на первом расхождении, не покажет, разошёлся один composition root или несколько
     - E2E-тест (технологически-агностичен, см. `WebTestClient`/`RANDOM_PORT` выше) не обязан жить в 2 местах как порт-тест — либо маленькая общая fixtures-зависимость на оба `-core`, либо 2 копии одного маленького сценарного класса (цена дублирования мала, отдельный третий shared-модуль ради одного класса не оправдан)
   - Механику расшаривания тестов (testFixtures + convention-плагин / test-jar) выбрать по ходу, когда появится реальный контент для расшаривания — не заранее.
2. **Docker Compose** — `compose.yaml`, делается **после** TDD, при заходе на dev runtime (`bootRun`). Механика профиль↔compose (`spring.docker.compose.profiles.active` в `application-<vendor>.properties`, `profiles: [<vendor>]` на сервисах, `spring.docker.compose.enabled=false` в `application-h2.properties`) — «Активная нить» → «2026-08-31, properties и профили ↔ compose/Testcontainers». Тогда же вернутся вендорные `application-<vendor>.properties` — уже с мост-строкой. Пересекается с открытым вопросом «Единый источник истины для версий»

## Архитектура и структура проекта

**Корневое дерево вариантов — корень архитектуры приложения** (2026-09-21, прямое указание пользователя; форма дерева подтверждена вторым сообщением с явной вложенностью). Это не описание текущей раскладки модулей, а рабочий инструмент: на нём проверяется любое архитектурное решение, оно выявляет архитектурные проблемы и подталкивает к верным решениям, а не к копированию туториалов, рассчитанных на одну ветку (одна БД, один API):

- общее — порты, прикладное поведение, тесты на порт: всё, что обязано быть одним для всех веток
  - синхронное (webmvc)
    - JDBC (`data-jdbc`)
      - H2 — `application-h2`
      - MySQL — `application-mysql`
      - PostgreSQL — `application-postgresql`
    - Mongo (`data-mongodb`) — `application-mongodb`
  - реактивное (webflux)
    - R2DBC (`data-r2dbc`)
      - H2 — `application-h2-reactive`
      - MySQL — `application-mysql-reactive`
      - PostgreSQL — `application-postgresql-reactive`
    - Mongo (`data-mongodb-reactive`) — `application-mongodb-reactive`

- **Как пользоваться деревом** — любое архитектурное решение прогоняется по всем 8 листьям: работает ли на каждой ветке, остаётся ли различие только там, где ветки объективно различаются (драйвер, диалект, вендор, classpath sync/reactive, Mongo без SQL), не копируется ли код по веткам. Решение, которое сходится на одной ветке, а на другой ломается или требует копирования, — признак архитектурной проблемы, а не повод дублировать. Верное решение — то, где для «общего» есть одно место
- **Уровни отражают природу различия** — sync/reactive вынужденно classpath (`WebApplicationType.deduceFromClasspath()`, разные типы порта); технология доступа (JDBC/R2DBC/Mongo) — разные драйверы и модельные классы; вендор — драйвер, диалект, семантика. Чем выше уровень, на котором различие проявляется, тем дороже оно (модули, дублирование) — критерий, куда его загнать. 8 листьев = 8 `application-*` (сегодняшняя раскладка совпадает с деревом)
- **Дерево открыто для роста** — JPA (`data-jpa` удалён 2026-09-13), другие драйверы и вендоры — возможные будущие ветки (2026-09-21, уточнение пользователя); цена добавления ветки — прямая метрика архитектуры (см. «Открытые решения» → «Как выделить общее из `application-vendor`…» и «Стоимость масштабирования composition-root матрицы»). Позиция ассистента по JPA (проверено по jar 4.1.0): пока JPA не нужен, парой к R2DBC служит JDBC — оба лежат на `spring-data-relational`, `JdbcDialect` и `R2dbcDialect` расширяют один `Dialect`, оба без генерации DDL (схема явная, `schema-<vendor>.sql`), id генерирует БД; у Hibernate свой `Dialect` и `@GeneratedValue`, а реактивной пары в Spring Data у JPA нет (Hibernate Reactive — отдельный проект, не R2DBC; не проверялось). При добавлении JPA лист получит несимметричную пару — принять сознательно
- **Ограничения дерева (обсуждение 2026-09-21)** — (1) необходимо, но недостаточно: сила детектора пропорциональна нагрузке, на пустом `UserNote` все 8 листьев зелёные без смысла, нужны враждебные данные; (2) «одинаково» — видимые результаты порта/HTTP на ожидаемых путях, не динамика (границы транзакций reactive, отмена подписки, транзакции Mongo между документами); (3) цена общего знаменателя — приложение не использует сильные стороны вендоров (`jsonb`, массивы PostgreSQL), осознанная цена исследовательского проекта, смягчена отсутствием связей между сущностями; (4) корень «общее» на уровне типов раздвоен (`S` против `Mono<S>`, в Java нет HKT) — единой может быть спецификация, не код; идея на проверку: сценарий как данные (шаги+ожидаемые исходы) и два тонких исполнителя, sync и reactive; (5) H2 — эмулятор и самый шумный лист, статус решить до первого прогона; (6) дерево покрывает только хранилище и парадигму — нет версии вендора (PostgreSQL 16/18), диалект не ветка, а следствие вендора и фреймворка, нет входной стороны (gRPC/GraphQL умножили бы листья)
- **Состояние дерева на 2026-09-21** — «общее» пусто (порта, прикладного сервиса, общего теста нет); каждый лист = `spring-boot`+`bootable`+`actuator`+веб-стартер+`spring-boot-data-*`+драйвер+`implementation(project(":user-note:data-*"))`, тесты везде `contextLoads()`; Testcontainers у mysql/postgresql/mongodb-листьев, у H2 нет; `data-*` — пустой `UserNote` + `UserNoteRepository` (`ListCrudRepository` у sync, `ReactiveCrudRepository` у reactive); JDBC-листья делят `data-jdbc`, R2DBC-листья — `data-r2dbc`
- **Зеркальность на 2026-09-21 (проверено по md5, содержимому, документации и байткоду)** — побайтово одинаковы во всех 8: `UserNoteApplication`, `package-info`, `UserNoteApplicationTests`; `UserNoteTestApplication` — в 6 (в двух H2 нет, законно: контейнера нет); `UserNoteTestConfiguration` — в паре sync/reactive одного вендора. Логи выровнены 2026-09-21 по указанию пользователя: во всех 8 `logging.level.org.springframework.web=DEBUG` (строка со страницы Boot logging) и `logging.level.org.springframework.data=DEBUG` + дочерний `...data.jdbc`/`data.r2dbc`/`data.mongodb` в своей ветке (`data.mongodb` дословно на странице MongoDB Java driver «spring-queries»; `data`/`data.jdbc`/`data.r2dbc` дословно не найдены, укладываются в форму `logging.level.<logger-name>=<level>`; дочерние при родителе на DEBUG функционально избыточны); SQL-логи `org.springframework.jdbc`/`org.springframework.r2dbc` (дословно в документации Spring Data) не включены — вне `org.springframework.data`; `log-request-details` и `debug=true` не включены. Реальное расхождение поведения: sync-SQL при старте подключается к БД (Hikari `Added connection`), reactive SQL по логам с DEBUG `io.r2dbc`/`io.asyncer`/`org.springframework.r2dbc` — нет, то есть `contextLoads()` reactive SQL-листьев не доказывает доступность вендора. `testcontainers-r2dbc` только у reactive MySQL/PostgreSQL — **законная асимметрия, не дефект**: `testcontainers-mysql`/`-postgresql` тянут транзитивно `testcontainers-jdbc` (POM: compile), но не `testcontainers-r2dbc`; `MySQLR2DBCDatabaseContainer`/`PostgreSQLR2DBCDatabaseContainer` (в модулях вендоров) реализуют `org.testcontainers.r2dbc.R2DBCDatabaseContainer`, а фабрики Boot 4.1.0 вызывают `XR2DBCDatabaseContainer.getOptions(container)` — без модуля ожидается `NoClassDefFoundError` (статически подтверждено, запуском без модуля не проверялось). Документация Testcontainers (r2dbc) говорит явно: «Both the database module (e.g. `org.testcontainers:testcontainers-mysql`) and `org.testcontainers:testcontainers-r2dbc` need to be on your application's classpath at runtime», без оговорки про URL-схему; документация Spring Boot об этом молчит. Причина — в самом Testcontainers (JDBC-поддержка входит в вендорный модуль, R2DBC требует явного дополнительного), не в листьях. Mongo: sync и reactive используют один `testcontainers-mongodb` и `MongoDBContainer` без `.withReplicaSet()`; по документации Testcontainers multi-document транзакции MongoDB 4+ работают только на replica set — между собой зеркально, но при появлении `@Transactional` разойдутся с SQL-листьями. Итоговые runtime/test classpath 8 листьев сравнены (`dependencies --configuration runtimeClasspath`/`testRuntimeClasspath`, по одному листу на вызов — параллельный вывод Gradle перемешивается): изоляция подтверждена (в каждом листе ровно свой драйвер, вендоры не протекают в чужие листья; sync без R2DBC, reactive без Tomcat/Hikari/JDBC-драйвера); внутри ветки различаются только драйвер и вендорный модуль Testcontainers; sync-H2 несёт `spring-boot-h2console`+`jakarta.servlet-api` (reactive-H2 нет — Servlet-UI), reactive SQL несёт `spring-jdbc` без драйвера и пула (транзитивно, безвредно)
- **Уже выявлено деревом (не туториалом)** — `remove` разной формы у sync и reactive порта («Активная нить» → «2026-09-21, консультация»); `NoUniqueBeanDefinitionException` и `SERVLET`-выбор при слиянии веток в один модуль («Активная нить» → «2026-08-19…21, сводка»); `MySQLContainer` требует JDBC-драйвер, `PostgreSQLContainer` нет, из-за чего дедупликация зависимостей сломала r2dbc-ветку («Завершено» → «2026-09-04, регрессия и фикс»); `application-core` отвергнут из-за bootable-природы листа («Активная нить» → «2026-09-13»); H2 — эмулятор, а не вендор («Открытые решения» → центральный вопрос)

## Именование

Формат каждой строки: **элемент** — паттерн — пример.

- **Adapter impl (sync и reactive)** — голый `{Entity}Service` в пакете своей технологии, без суффикса технологии в имени класса — `com.example.note.data.jpa.adapter.NoteService`, `com.example.note.data.r2dbc.adapter.NoteService` и т. д.

- **JPA model class** — `{Entity}Entity` — `NoteEntity`
- **R2DBC model class** — `{Entity}{Tech}Entity` — `NoteR2dbcEntity`
- **MongoDB model class** — `{Entity}Document` — `NoteDocument`

## Открытые решения

- **⚠️ ЦЕНТРАЛЬНЫЙ ВОПРОС АРХИТЕКТУРЫ И ПРИЛОЖЕНИЯ — как доказать, что приложение ведёт себя одинаково на разных вендорах, драйверах и диалектах** (2026-09-21, определён пользователем как центральный; текущая работа идёт над ним, остальные пункты ниже производные; **решение не принято** — здесь постановка, состояние и рекомендация ассистента, не решение):
  - **Терминология** — цепочка запроса: репозиторий Spring Data → диалект → драйвер → вендор. Вендор — сама СУБД со своим поведением (PostgreSQL/MySQL/H2/MongoDB): типы, регистр и collation при сравнении, ограничения, транзакции, порядок NULL. Драйвер — клиентская библиотека протокола вендора под конкретный API (JDBC — `mysql-connector-j`, R2DBC — `r2dbc-mysql`, Mongo driver); привязан к паре «вендор × API», у одного вендора минимум два драйвера — это и есть граница sync/reactive; отвечает за транспорт и маппинг типов, не за текст SQL. Диалект — знание слоя над драйвером (Hibernate `Dialect`, Spring Data JDBC/R2DBC `Dialect`), как писать SQL под вендора: кавычки, `LIMIT`/`FETCH`, плейсхолдеры, получение сгенерированного id, типы; зависит от версии сервера, обычно определяется автоматически по соединению (для Boot 4.1 механизм по байткоду не проверялся — сверить при реализации); у Mongo диалекта нет (нет SQL). Ошибка диалекта — синтаксическая ошибка SQL, ошибка драйвера — расхождение типов/протокола, ошибка вендора — расхождение семантики
  - **Что значит «одинаково» — не определено**, без этого тест не знает, что считать ошибкой. Кандидаты на расхождение: схема/DDL (`UUID()`/`gen_random_uuid()`/`RANDOM_UUID()`); генерация id; типы (UUID, точность `Instant` — Mongo мс, boolean); регистр и collation (MySQL по умолчанию сравнивает без учёта регистра); duplicate-key и трансляция ошибок; транзакции и optimistic lock; порядок и позиция NULL без `ORDER BY`; путь sync против reactive; для Mongo — представление UUID в драйвере (не проверено). H2 — эмулятор, не вендор: зелёный тест на H2 говорит о совместимости с H2, не с PostgreSQL
  - **Состояние на 2026-09-21** — доказывать нечем: `UserNote` и репозитории `data-*` — пустые заглушки, порта и схем нет, тесты — голый `contextLoads()`; образы `mysql:latest`/`postgres:latest` без пина, хотя версия сервера — часть оси диалекта. Из истории `note/` (см. «Активная нить» → «2026-09-21, консультация»): расхождение sync/reactive заложено в самом порте (`remove` — `S` против `Mono<Void>`), правило «не найдено» жило не в `domain`, а в каждом адаптере, бизнес-слоя не было — то же придётся решить для `user-note` заранее
  - **Следующий шаг — варианты, не выбрано.** (А) спецификация вперёд: заранее составить список поведений и по каждому решить «обязано совпасть / нормализуется в адаптере или схеме / допустимое отличие», потом писать тест — плюс ясность, минус список составляется гаданием и пропустит неочевидное. (Б) характеризационный прогон — суть в том, что спецификация берётся из прогона, а не из головы; для него нужен минимум (sync): сущность с провоцирующими полями (UUID-id, ищущая строка, `Instant`, unique-поле), порт, вендорные схемы в `application-<vendor>`, один сценарий на враждебных данных против H2+MySQL+PostgreSQL — порядок построения этого минимума (срезом или слоями) не предписан, см. «Правила» → «Порядок работы — по удобству»; каждая красная разница — вопрос «нормализуем или признаём отличием», ответы и есть спецификация — плюс расхождения находит реальность, а не воображение, минус срез и схемы нужны до первого ответа. **Рекомендация ассистента — Б**, с двумя решениями до старта: форма `remove` в порте (sync `S` против reactive `Mono<Void>`) и где живёт правило «не найдено» (порт/домен/адаптер). Дальше: пин версий образов (см. «Единый источник истины для версий»), статус H2 (реальный вендор или dev-эмулятор), затем общий сценарный тест в `testFixtures` («Задачи» → п.1)
  - **Граница порта — варианты, не выбрано (2026-09-21, обсуждение)** — (а) толстый порт, как в `note/`: поведение (правило «не найдено», семантика `replace`/`merge`) в каждом адаптере, TCK на весь порт против всех листьев; минус — правила копируются по веткам; (б) тонкий порт хранилища (сохранить/найти/удалить/проверить) + один прикладной сервис в двух копиях (sync/reactive): TCK переезжает на порт хранилища в `testFixtures` и гоняется в каждом `application-vendor`, поведение задано один раз, вендорные различия сосредоточены в контракте хранилища; минус — лишний слой и маппинг, каждый finder (`findByUsername`) расширяет контракт и вендорную поверхность; (в) сервис прямо на Spring Data `CrudRepository` без своего порта — отклонён: модельные классы разные по технологиям, общий класс с аннотациями всех технологий загрязнил бы домен. **Рекомендация ассистента — (б)** (событийные подходы ES/CQRS сузили бы контракт сильнее, но меняют постановку и для CRUD не нужны)
  - **Связано** — «Поведенческая аналогичность адаптеров/драйверов», «Симметрия ArchUnit» п.3, «Единый источник истины для версий», «Как выделить общее из `application-vendor`…», «Активная нить» → «2026-09-05, консультация — стандартная практика conformance-тестирования (Testcase Superclass/TCK)»

  2. Матрица тестового покрытия — вариант (A) «отдельный класс/модуль на комбинацию» реализован для `note`/`user` (33 composition-root модуля, один `*ApplicationTests` на модуль); **для `user-note` этот инвариант больше не действует с 2026-08-19** (5 объединённых модулей, вендор внутри — см. «Задачи» → «Активная нить»). Вариант (B) `@ParameterizedTest` снят как противоречащий тогдашнему «вендор — граница модуля»; вариант (C) — мета-тест по типу ArchUnit («на каждый вендорный плагин должен существовать application-модуль») — зависит от решения по пункту 1, актуальность для `user-note` пересмотреть заново после изменения 2026-08-19
  3. **Дополнено 2026-09-05** (консультация, «Активная нить» → «2026-09-05») — вариант (C) выше сформулирован конкретнее как один из 4 слоёв гарантии «реализация реально протестирована»: мета-тест графа сборки закрывает только «тест вообще не заведён для нового модуля»; отдельно нужен JaCoCo `jacocoTestCoverageVerification` (byte-code-доказательство, что код реализации реально исполнился, не просто что тест существует) — оба дополняют, не заменяют друг друга
- **Поведенческая аналогичность адаптеров/драйверов** (названо пользователем главной проблемой на пути к зрелости CRUD-модулей, 2026-07-24; **не реализовывать до отдельного запроса**) — реализации порта по матрице технология×вендор должны вести себя одинаково при одинаковом сценарии; находки по факту чтения кода `note/` (не перепроверялись отдельно для `user/`/`user-note/`, предполагается та же структура):
  1. Порты не специфицируют поведение (голый `Object`, без `throws`/`Optional`/`@Nullable`/Javadoc) — **2026-08-18 переосмыслено как осознанное разделение**: спецификация поведения сознательно живёт в тестах application-уровня, порт остаётся чисто структурным контрактом
  2. Обработка «не найдено» сегодня случайно одинакова во всех 5 адаптерах (`orElseThrow(NoteNotFoundException)`/`switchIfEmpty(Mono.error(...))`) — не гарантирована ни портом, ни тестом
  3. Реальные расхождения: генерация ID тремя механизмами (JPA — `@GeneratedValue` через Hibernate; JDBC/R2DBC — `DEFAULT RANDOM_UUID()` в `schema.sql`; MongoDB — `UUID.randomUUID()` в мапере); duplicate-key нигде не транслируется ни в одном из 5 адаптеров (сценарий сегодня недостижим — нет unique-constraint кроме PK — но латентный риск, `NoteExceptionHandler` обработает только `NoteNotFoundException`); MongoDB (blocking) `add()` использует `mongoTemplate.insert()` напрямую, минуя repository, в отличие от остальных операций/адаптеров
  4. Одинаковые (не расходящиеся) пробелы во всех 5: `@Transactional` отсутствует везде (`merge()`/`replace()` — read-then-write без атомарности); Bean Validation отсутствует везде (аннотации `@NotNull`/`@NotBlank` на model-классах не расставлены, хотя `spring-boot-starter-validation` подключён точечно)
  5. **Referential integrity между `user-note/` и `user/`·`note/` не проверяется вообще** (найдено 2026-07-24) — `create()` в `UserNoteService` (`data-jpa`) сохраняет `UserNoteEntity` без проверки, что `userId`/`noteId` реально существуют в `user/`/`note/`: ни синхронного вызова порта, ни события, ни constraint (сервисы физически разделены). Там, где проверка вроде есть (`existsByUserId` — проверяет «есть ли уже связка в `user_note`», не «существует ли пользователь»), она обманчива — `UserNotFoundException` там означает «у userId нет заметок», не «пользователя нет». Не перепроверено для jdbc/r2dbc/mongodb/mongodb-reactive `user-note/`. Тот же класс проблемы («нет referential integrity через границу сервиса») встанет и в «Регистрация auth/ ↔ user/» ниже

  Кандидат-решение, не проработан: общий conformance test suite через `java-test-fixtures` — абстрактный JUnit-класс против интерфейса порта, параметризуемый в каждом `data-*`/composition-root модуле своим адаптером; требует заранее провести границу «что обязано совпадать» vs «что законно различается» (пример законного различия — bean-validation автотриггер: Hibernate триггерит, MongoDB/R2DBC/JDBC — нет)
- **Стоимость масштабирования composition-root матрицы** (2026-07-24) — рост числа модулей мультипликативен (сервисы × технологии × вендоры). Два разных вопроса: (1) рост числа модулей — цена уже принятого решения «вендор — граница модуля» (для `note`/`user`; `user-note` отступил от этого с 2026-08-19, см. «Задачи»), откат вернул бы driver bloat; (2) рост стоимости добавления модуля (дублирующийся boilerplate) — можно снижать без изменения топологии, варианты не проработаны (пересмотреть обязательность полной 3×3-симметрии; оценить реальный объём дублирования перед решением, что менять). Эмпирика по времени сборки — см. «Правила» → «Build» → «`clean check` с реальным Docker» (MySQL ~2× медленнее PostgreSQL/MongoDB, H2 без контейнера 9–14с). Не реализовывать до отдельного запроса
- **Область подключения `spring-boot-starter-validation`** — решено 2026-08-01 (атомарный `spring-boot-validation`, только `webmvc`/`webflux`/`data-jpa` × 3 сервиса). Остаточный пункт, **не поднимать и не напоминать до отдельного запроса**: `data-mongodb`/`data-mongodb-reactive` требуют написать и зарегистрировать `ValidatingMongoEventListener`+`LocalValidatorFactoryBean` (Spring Boot не автоконфигурирует), без этого голый стартер там ничего не даёт. R2DBC/JDBC (Spring Data Relational) — ни автотриггера, ни listener-механизма нет вообще, подключать нечего
- **Регистрация `auth/` ↔ `user/`** — Lazy / Sync / Events (Kafka); та же проблема класса «нет referential integrity через границу сервиса», уже реально найденная между `user-note/` и `user/`·`note/` — см. «Поведенческая аналогичность» → п. 5 выше
- **Межсервисная консистентность `user-note` ↔ `user`/`note` (и другие сервисы) — цель переформулирована шире (2026-09-13, консультация, ничего не реализовано)**: цель — тренировка архитектурно правильного микросервисного приложения, где каждый сервис независимо выбирает БД (уже реализовано как ось `application-vendor` для `user-note`), расширенная на реальную многосервисную систему. Ключевое ограничение: database-per-service исключает FK/JOIN между сервисами — «связь» только на уровне приложения/сети; общая БД/прямой доступ к чужой БД — анти-паттерн, исключён сразу. Стандартные паттерны (перечислены, не выбраны): (1) синхронный вызов при записи (REST/gRPC на `user`/`note`) — просто, но runtime-связанность и растущая задержка; (2) асинхронная событийная связь (`UserCreated`/`NoteDeleted`, локальная эвентуально-консистентная проекция в `user-note`) — без runtime-связанности, ценой брокера/идемпотентности/окна рассинхронизации; (3) API composition/CQRS для чтения — отдельная задача, если цель «связи» — обогащение данных, не проверка существования; (4) Saga — для компенсирующих действий между сервисами. Расширяет, не отменяет «Регистрацию `auth/`↔`user/`» и «Поведенческую аналогичность» → п. 5 — тот же класс «нет referential integrity через границу сервиса», теперь на уровне общего принципа. Выбор брокера — отдельное решение, см. `docs/tech-glossary.md`. Два открытых вопроса: (а) целостность при записи vs обогащение при чтении — разные задачи; (б) `user`/`note` (удалены 2026-08-29) возвращаются сейчас или протокол проектируется без второго реального сервиса. **Не реализовывать до отдельного запроса и до ответа на оба вопроса** — текущая нить (TDD против порта `user-note`) не отменяется
