## Правила

- **Голый API-стартер не подключается, если есть обёртка (Spring Data и т. п.) для той же технологии — даже если технически обёртка не несёт 100% функционала голого стартера** (2026-08-15, явное решение пользователя, отменяет собственную рекомендацию агента по итогам факт-проверки) — прецедент: `spring-boot-starter-elasticsearch` подключён рядом с `spring-boot-starter-data-elasticsearch` (несёт реальный `elasticsearch-java`-драйвер, которого `data-elasticsearch` транзитивно не тянет, проверено и POM, и Gradle Module Metadata) — пользователь всё равно убрал голый стартер вручную и явно сформулировал общее правило: «не используем голый API при наличии обёртки». Риск (Spring Data Elasticsearch без реального клиента может не заработать в рантайме) осознан пользователем — «проверить при реальном обращении», не превентивным подключением про запас. Это отменяет более узкое обоснование из записи 2026-08-15 «пересматривает правило... но избыточность, доказанную фактами, применять не мешает» — теперь правило шире факта транзитивности: голый API не нужен как класс решений, независимо от того, доказана ли конкретная избыточность фактами по каждой технологии отдельно
- **⚠️ ИСТОЧНИК ИСТИНЫ ДЛЯ SPRING-ФАКТОВ — НЕ MAVEN CENTRAL ПОИСК** [НЕ СОКРАЩАТЬ/НЕ УДАЛЯТЬ — исключение из правила «убирать избыточность», даже при явной задаче уменьшить объём CLAUDE.md] (2026-07-14, резкая реакция пользователя на ошибку): вопрос «существует ли артефакт X» **никогда** не проверять через `search.maven.org` (Solr-индекс отстаёт от реального репозитория, `0 numFound` НЕ значит «не существует» — конкретная ошибка: заявил, что `spring-boot-starter-r2dbc` не существует по 0 результатам поиска, хотя это реальный отдельный от `data-r2dbc` стартер). Источник истины — **Spring Initializr** (`start.spring.io/metadata/client` — реальный список id/name/description), **GitHub spring-projects**, **официальная документация docs.spring.io**. Maven Central годится только для номера версии уже известного, существующего артефакта — не для вопроса о самом его существовании. **`docs/spring-boot-starters-reference.md`** (2026-07-14) — дословная копия со Spring Initializr, лежит в репозитории локально: для вопроса «существует ли стартер X» и «как называется» обращаться сначала туда, не в web-поиск. При выборе/добавлении стартера под конкретную технологию — сверяться по этому файлу, есть ли для неё отдельный `-test`-компаньон (`spring-boot-starter-{tech}-test`), и подключать его вместе с основным, если существует — не пропускать по своему усмотрению (см. прецедент с `spring-boot-starter-r2dbc`/`-jdbc`/`-elasticsearch`, где `-test`-версия изначально была упущена). Также перед добавлением зависимости в Spring Boot модуль — сверяться, нет ли для этой технологии уже готового `spring-boot-starter-*`: если есть, подключать именно его, а не «сырую» внешнюю зависимость напрямую (starter уже несёт нужный BOM-managed набор транзитивных зависимостей и autoconfiguration — обходить его напрямую значит терять то и другое). **Принадлежность к Initializr — определять только буквальным поиском строки артефакта в `docs/spring-boot-starters-reference.md`, никогда рассуждением по форме имени артефакта** (2026-08-02, резкая реакция пользователя на ошибку): конкретная ошибка — заявил, что `org.springframework.boot:spring-boot-docker-compose` «не Initializr-стартер», по неверной логике «раз в имени артефакта нет `-starter-`, значит это core-модуль Boot, а не выбираемая в Initializr зависимость» — вывод по паттерну имени, без единой проверки. У Spring Initializr многие зависимости (Docker Compose Support, Lombok, Actuator и др.) не содержат `-starter-` в имени артефакта, наличие/отсутствие этого подслова в имени не говорит ничего о членстве в Initializr. Строка `developmentOnly 'org.springframework.boot:spring-boot-docker-compose'` при этом дословно уже присутствовала в `docs/spring-boot-starters-reference.md:178` — файл был не прочитан перед утверждением. Правило: любое утверждение вида «X не относится к Initializr»/«X не существует как стартер» — сначала grep по точной строке артефакта в `docs/spring-boot-starters-reference.md`, и только отсутствие там даёт право на такое утверждение (с оговоркой, что файл не абсолютно полон — см. соответствующий пункт правила выше)

- **Перед архитектурным ответом — контрольный список: стандартный паттерн / переформулировка / другой угол / альтернативы** (2026-08-08, из диалога про единый контракт Controller/Service — см. «Задачи» → «Завершено» и `docs/decisions-log.md` → «Архитектура», где ассистент трижды прошёлся по локальным вариациям, прежде чем распознать типовой случай): перед предложением решения явно проверять четыре вопроса, не хвататься за первый локальный рецепт — (1) не частный ли это случай известного стандартного паттерна (пример — «N классов с одной сигнатурой, разным типом возврата» → параметрический полиморфизм, как `Optional<T>`/`Comparator<T>`/`CrudRepository<T, ID>`); (2) можно ли переформулировать саму постановку задачи, не размывая заданных ограничений; (3) можно ли посмотреть с другого угла — от абстрактной формы задачи, а не от уже реализованного в репозитории локального прецедента; (4) есть ли альтернативы помимо первой идеи. Решения, снимающие заданное ограничение ради тривиальности (пример — убрать `ResponseEntity` из Controller), предлагать можно, но явно помечая «меняет постановку задачи», не как рекомендованный ответ. **Чек-лист проходить явно и видимо в самом ответе** (уточнено 2026-08-08 и 2026-08-21 — резкая реакция на буквальные ярлыки-вопросы вида «Стандартный паттерн? Да —») — не молчаливая внутренняя проверка, а показанные шаги рассуждения обычной связной прозой, без ярлыков/риторических заголовков на каждый пункт — чек-лист держится в голове, в тексте виден только результат естественным языком; при повторном применении к уже решённому вопросу — переискать заново, не просто повторить вывод (пример — контракт Controller/Service передуман через рамку Adapter/GoF и driving/driven-симметрию портов, не просто снова назван «параметрический полиморфизм»). **Свежий взгляд, не фиксация на уже предложенных вариантах** — набор вариантов, уже прозвучавших в диалоге, не исчерпывающий по умолчанию, не потолок для дальнейшего поиска
- **Любое архитектурное решение проверять на корневом дереве вариантов** (2026-09-21, прямое указание пользователя) — перед предложением или принятием решения прогнать его по всем 8 листьям дерева из «Архитектура и структура проекта» → «Корневое дерево вариантов»: работает ли на каждой ветке, где остаётся различие, не копируется ли код по веткам. **Целевая картина (согласована 2026-08-31, вечер; порядок работы уточнён 2026-09-04) — сверху вниз:**
1. `user-note` — одно приложение с одним поведением. Описывается один раз (максимум два: sync/reactive — и только из-за конфликта webmvc/webflux на classpath). Всё остальное — сменная реализация. **Уточнение 2026-09-04**: граница sync/reactive (как и вендорная граница) — чисто техническая, вынужденная сборкой (`WebApplicationType.deduceFromClasspath()`, driver bloat), не поведенческая — для потребителя API (и для порт-теста через `WebTestClient`/`TestRestTemplate` на реальном порту, см. п.1 ниже) разницы нет вообще, контракт один. Та же логика, что уже привела к «HTTP-контракт один на все 5 модулей» — распространяется и на смысл самого разделения sync/reactive: оно существует ради компилятора/classpath, не ради разного поведения.
2. Абстракция = порт (`UserNoteInterface`/`…Reactive`) + `application-core`(`-reactive`) (общий `@SpringBootApplication` + тест поведения на порт в `testFixtures`) + convention-плагин `com.example.user-note-application`(`-reactive`) — **возникает по ходу TDD, не выносится заранее** (пересмотрено 2026-09-04, см. выше).
3. Конкретные composition-root различаются **ТОЛЬКО составом classpath**. Каждый `application-X` = «плагин абстракции + плагин адаптера», ни своей Java, ни своего теста — это целевое состояние ПОСЛЕ TDD, не стартовая точка.
4. Ось адаптеров = SQL vs non-SQL. SQL: один адаптер на модель доступа (`jdbc`/`jpa`/`r2dbc`) покрывает все SQL-вендоры, вендор = профиль. Non-SQL (Cassandra/Couchbase/Neo4j/Elasticsearch/DynamoDB/Redis/Mongo/in-memory): каждый вендор — свой адаптер и свой модуль. sync/reactive удваивает каждый, где драйвер позволяет.
5. Тесты — та же архитектура, что код: один тест на порт, параметризован, гоняется против каждой реализации. **Два уровня, не один** (уточнено 2026-09-04): тест на порт (service+persistence, без HTTP) и E2E-тест через HTTP (кандидат на shared testFixtures — контракт не зависит от технологии персистенции). **Почему один и тот же тест на N реализаций доказывает «разницы нет», не просто совпадение** — рассмотрена и отклонена альтернатива differential testing (сверка вывода байт-в-байт без явных assert-ов, как тестируют компиляторы): (1) CRUD-сущность — оракул пишется легко, не тот случай; (2) differential ловит только расхождение МЕЖДУ реализациями, общий баг во всех пяти (например в самом контракте порта) не найдёт, explicit-assert найдёт; (3) N-парных сравнений растёт комбинаторно, один прогон общего теста — линейно. Дыра conformance-подхода — ловит только то, что явно assert-ит автор теста; принята как цена, оправданная простотой домена.
6. Это корневая идея проекта, рекурсивно: hexagonal в коде + convention-плагины на уровне системы — и та же связка абстракция/реализация/DIP на слое composition-root.
7. Порядок работы (пересмотрено 2026-09-04): (1) TDD против порта, код по слоям вниз, абстракция появляется по ходу → (2) compose для dev runtime.

1. **Полный TDD против порта — тест написан НА АБСТРАКЦИИ, не на реализации, порт и абстракция выводятся ПО ХОДУ, не заранее** (объединяет прежние п.0+п.1, пересмотрено 2026-09-04) — тест поведения **один**, зависит **только от `UserNoteInterface` / `UserNoteReactiveInterface`** (не от `DataSource`/`MongoTemplate`), параметризован технологией и вендором (`@ParameterizedTest`/`@ActiveProfiles` по профилям), гоняется против каждого из 5 модулей. Конкретный адаптер модуля удовлетворяет контракт абстракции — реализация подставляется под тест, не наоборот. `getDatabaseProductName()`/`buildInfo`-ассерты и любые `abstract`-пробы удаляются — это связанность абстракции с реализацией. **К тестам — те же паттерны проектирования и та же архитектура, что к коду приложения** (принципиальное требование пользователя, не деталь оформления). sociable/classicist-стиль, реальный Spring-контекст, Testcontainers (принцип — «Завершено» → «2026-08-18, архитектура тестирования»). От тестов — реальный доменный/persistence/presentation код (нижние слои, идём вниз).
   - **Два уровня теста, оба на composition-root, оба — кандидаты на shared testFixtures** (обсуждено 2026-09-04): (а) **тест на порт** — `@Autowired UserNoteInterface`, проверяет service+persistence, минуя контроллер; (б) **E2E-тест через HTTP** — отдельный, не то же самое, ловит то, что порт-тест не видит (маппинг JSON, `@Valid`, `NoteExceptionHandler`→`ProblemDetail`, HTTP-статусы). Рекомендация по механике E2E: `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate` (webmvc) / `WebTestClient` (webflux) на реальном порту — **не** `@AutoConfigureMockMvc`/`@AutoConfigureWebTestClient`-in-container (тот не гоняет через реальный сокет, тот же компромисс, что и мок, только тоньше — противоречит уже принятому sociable/classicist-принципу). Оба уровня — максимум 2 варианта каждый (sync/reactive), как и порт-тест — не отдельная новая абстракционная задача, тот же `application-core`.
   - **Уточнение того же вечера — E2E не удваивается на sync/reactive, порт-тест удваивается** (пользователь поймал ошибку в исходной рекомендации). Порт-тест — максимум 2 варианта, механически неустранимо: `UserNoteInterface.add(...)` возвращает `UserNote`, `UserNoteReactiveInterface.add(...)` — `Mono<UserNote>`, разные Java-типы, один тестовый метод не годится для обоих без блокирующего/реактивного моста (убивает смысл теста реактивного пути). E2E/HTTP-тест — **один**, не два: при `@SpringBootTest(webEnvironment = RANDOM_PORT)` и `WebTestClient.bindToServer().baseUrl("http://localhost:"+port)` (или `TestRestTemplate`) клиент работает поверх реального сокета через HTTP — ему не важно, blocking или reactive сервер на другом конце, это чистый протокол. Различие sync/reactive у тест-клиента существует только в in-container-режиме (`@AutoConfigureMockMvc`↔`DispatcherServlet`, `@AutoConfigureWebTestClient`↔`WebHandler` напрямую, без сокета) — который уже отвергнут выше в пользу настоящего HTTP. Итог: HTTP-контракт (JSON/статусы) один на все 5 модулей, один E2E-тест-класс их все покрывает.
   - **Форма самого теста — один сценарный метод («flow»), не россыпь независимых assert-ов** (обсуждено 2026-09-04, вопрос пользователя «как протестировать, что у пользователя один user flow вне зависимости от технологии» — про форму теста, не про механику расшаривания, изначально понято неверно). «Один user flow» доказывается не тем, что пять реализаций проходят похожие, но раздельные `@Test`-методы (`addThenFindByIdReturnsSameUserNote()`, `removeThenExistsByIdReturnsFalse()` и т. п. по отдельности) — а тем, что это буквально **один сценарный метод** (условно `userManagesTheirNoteEndToEnd()`), описывающий реальную последовательность действий пользователя (создал → прочитал → изменил → удалил → убедился, что удалено) целиком в одном потоке, лежащий в `testFixtures`, прогоняемый целиком против каждого из 5 модулей. Сам факт «это один метод, не пять» и делает идею «один flow» видимой в коде теста, а не только в механизме его расшаривания (testFixtures byte-identical class — гарантия, что тест не разъедется, но не про форму самого сценария).
   - **Организация проверки API при нескольких composition root** (обсуждено 2026-09-04, вопрос пользователя «как организовать проверку API при наличии нескольких composition root» — финальная точка длинного разбора, начатого с «один API, одни результаты», прошедшего через мехнику testFixtures/форму теста/black-box). У проекта нет одного работающего приложения с переключаемой начинкой — 5 отдельных composition root, 5 отдельных `main()`, 5 независимо собранных графов объектов. «Один API» — не факт про единый процесс, а контракт, который каждый composition root обязан реализовать по отдельности; доказывается не одним прогоном, а N прогонами одного и того же теста без изменений. Конкретная организация:
     - Тест физически лежит в `application-core`/`testFixtures` (порт-тест на `UserNoteInterface`) и `application-core-reactive`/`testFixtures` (на `UserNoteReactiveInterface`) — **2 копии, не 5**, по числу типов порта, не по числу composition root
     - Каждый из 5 `application-X/build.gradle.kts` подхватывает нужный набор не копированием, а зависимостью — convention-плагин `com.example.user-note-application`(`-reactive`) сам тянет `testImplementation(testFixtures(project(":user-note:application-core"[-reactive])))`; лист выбирает только, какой convention-плагин применить (sync/reactive), тест наследуется автоматически
     - Прогон по всем N сразу — уже существующий `./gradlew clean check --continue` из корня: Gradle сам находит все `include(...)`-модули `settings.gradle.kts` и гоняет их `test`-таски независимо; ничего специального «раннера по composition root» писать не нужно, это прямое следствие уже выбранной multi-module-структуры. `--continue` обязателен именно здесь — без него сборка остановится на первом расхождении, не покажет, разошёлся один composition root или несколько
     - E2E-тест (технологически-агностичен, см. `WebTestClient`/`RANDOM_PORT` выше) не обязан жить в 2 местах как порт-тест — либо маленькая общая fixtures-зависимость на оба `-core`, либо 2 копии одного маленького сценарного класса (цена дублирования мала, отдельный третий shared-модуль ради одного класса не оправдан)
   - Механику расшаривания тестов (testFixtures + convention-плагин / test-jar) выбрать по ходу, когда появится реальный контент для расшаривания — не заранее.

## Архитектура и структура проекта

**Корневое дерево вариантов — корень архитектуры приложения** (2026-09-21, прямое указание пользователя; форма дерева подтверждена вторым сообщением с явной вложенностью). Это не описание текущей раскладки модулей, а рабочий инструмент: на нём проверяется любое архитектурное решение, оно выявляет архитектурные проблемы и подталкивает к верным решениям, а не к копированию туториалов, рассчитанных на одну ветку (одна БД, один API):

- общее — порты, прикладное поведение, тесты на порт: всё, что обязано быть одним для всех веток (сегодня пусто)
  - синхронное (webmvc) — driving-модуль `controller-webmvc`
    - JDBC — `data-jdbc`
      - H2 — `application-h2`
      - MySQL — `application-mysql`
      - PostgreSQL — `application-postgresql`
    - Mongo — `data-mongodb` — `application-mongodb`
  - реактивное (webflux) — driving-модуль `controller-webflux`
    - R2DBC — `data-r2dbc`
      - H2 — `application-h2-reactive`
      - MySQL — `application-mysql-reactive`
      - PostgreSQL — `application-postgresql-reactive`
    - Mongo — `data-mongodb-reactive` — `application-mongodb-reactive`

- **Модули по уровням и контексты тестов** (2026-09-21): `controller-*` и `data-*` — слайс-тесты (`@WebMvcTest`/`@WebFluxTest`/`@DataJdbcTest`/`@DataR2dbcTest`/`@DataMongoTest`) с побайтово одинаковым test-scope `UserNoteApplication` (точка входа слайса: в основном коде такой класс нельзя — другое имя ломает листья `Found multiple @SpringBootConfiguration`, то же имя даёт хрупкий дубль); `data-jdbc`/`data-r2dbc` на встроенной H2 в test-scope (`spring-boot-test-h2`/`-r2dbc-h2`, `testRuntimeOnly`, не утекает; сами `data-*` не знают ни вендора, ни драйвера); `application-*` — полный контекст и реальный вендор. Те же data-тесты в будущем должны запускаться и против реальных вендоров (Testcontainers) — «Открытые решения» → вопрос про тесты
- **Как пользоваться деревом** — любое архитектурное решение прогоняется по всем 8 листьям: работает ли на каждой ветке, остаётся ли различие только там, где ветки объективно различаются (драйвер, диалект, вендор, classpath sync/reactive, Mongo без SQL), не копируется ли код по веткам. Решение, которое сходится на одной ветке, а на другой ломается или требует копирования, — признак архитектурной проблемы, а не повод дублировать. Верное решение — то, где для «общего» есть одно место
- **Уровни отражают природу различия** — sync/reactive вынужденно classpath (`WebApplicationType.deduceFromClasspath()`, разные типы порта); технология доступа (JDBC/R2DBC/Mongo) — разные драйверы и модельные классы; вендор — драйвер, диалект, семантика. Чем выше уровень, на котором различие проявляется, тем дороже оно (модули, дублирование) — критерий, куда его загнать. 8 листьев = 8 `application-*` (сегодняшняя раскладка совпадает с деревом)
- **Дерево открыто для роста** — JPA (`data-jpa` удалён 2026-09-13), другие драйверы и вендоры — возможные будущие ветки (2026-09-21, уточнение пользователя); цена добавления ветки — прямая метрика архитектуры (см. «Открытые решения» → «Как выделить общее из `application-vendor`…» и «Стоимость масштабирования composition-root матрицы»). Позиция ассистента по JPA (проверено по jar 4.1.0): пока JPA не нужен, парой к R2DBC служит JDBC — оба лежат на `spring-data-relational`, `JdbcDialect` и `R2dbcDialect` расширяют один `Dialect`, оба без генерации DDL (схема явная, `schema-<vendor>.sql`), id генерирует БД; у Hibernate свой `Dialect` и `@GeneratedValue`, а реактивной пары в Spring Data у JPA нет (Hibernate Reactive — отдельный проект, не R2DBC; не проверялось). При добавлении JPA лист получит несимметричную пару — принять сознательно
- **Ограничения дерева (обсуждение 2026-09-21)** — (1) необходимо, но недостаточно: сила детектора пропорциональна нагрузке, на пустом `UserNote` все 8 листьев зелёные без смысла, нужны враждебные данные; (2) «одинаково» — видимые результаты порта/HTTP на ожидаемых путях, не динамика (границы транзакций reactive, отмена подписки, транзакции Mongo между документами); (3) цена общего знаменателя — приложение не использует сильные стороны вендоров (`jsonb`, массивы PostgreSQL), осознанная цена исследовательского проекта, смягчена отсутствием связей между сущностями; (4) корень «общее» на уровне типов раздвоен (`S` против `Mono<S>`, в Java нет HKT) — единой может быть спецификация, не код; идея на проверку: сценарий как данные (шаги+ожидаемые исходы) и два тонких исполнителя, sync и reactive; (5) H2 — вендор наравне с MySQL и PostgreSQL (решение пользователя 2026-09-21, без двусмысленности): его отличия — то, что дерево должно выявлять, и обрабатываются как отличия любого вендора; (6) дерево покрывает только хранилище и парадигму — нет версии вендора (PostgreSQL 16/18), диалект не ветка, а следствие вендора и фреймворка, нет входной стороны (gRPC/GraphQL умножили бы листья)
- **Состояние дерева на 2026-09-21** — «общее» пусто (порта, прикладного сервиса, общего теста нет); лист = `spring-boot`+`bootable`+`actuator`+веб-стартер+`spring-boot-data-*`+драйвер+`implementation(project(":user-note:data-*"))`+`implementation(project(":user-note:controller-*"))`; `controller-*` — пустой `@RestController` (зеркально), `data-*` — пустой `UserNote` (побайтово одинаков во всех 4) + `UserNoteRepository` (`ListCrudRepository` у sync, `ReactiveCrudRepository` у reactive); тесты — `contextLoads()` (листья — `@SpringBootTest`, `controller-*`/`data-*` — слайс-аннотации); Testcontainers у mysql/postgresql/mongodb-листьев, у H2 нет; JDBC-листья делят `data-jdbc`, R2DBC-листья — `data-r2dbc`
- **Зеркальность на 2026-09-21 (по md5, содержимому, документации, байткоду, classpath)** — побайтово одинаковы во всех 8 листьях: `UserNoteApplication`, `package-info`, `UserNoteApplicationTests`; `UserNoteTestApplication` удалены 2026-09-21; `UserNoteTestConfiguration` — в паре sync/reactive одного вендора. Логи (по указанию пользователя): `logging.level.org.springframework.web=DEBUG` — в `application-controller-<stack>.properties`; `logging.level.org.springframework.data=DEBUG`+дочерний `data.<jdbc|r2dbc|mongodb>` — в `application-data-<tech>.properties`; SQL-логи `org.springframework.jdbc`/`.r2dbc`, `log-request-details` и `debug=true` не включены. Реальное расхождение поведения: sync-SQL при старте подключается к БД (Hikari), reactive SQL — нет, `contextLoads()` reactive SQL-листьев не доказывает доступность вендора (исчезнет с первым реальным запросом, вариант Б). `testcontainers-r2dbc` только у reactive MySQL/PostgreSQL — **законная асимметрия**: вендорные модули тянут транзитивно `testcontainers-jdbc`, но не `-r2dbc`; фабрики Boot 4.1.0 вызывают `XR2DBCDatabaseContainer.getOptions(container)` (без модуля ожидается `NoClassDefFoundError`, запуском не проверялось); документация Testcontainers: «Both the database module … and `org.testcontainers:testcontainers-r2dbc` need to be on your application's classpath at runtime». Mongo sync/reactive — один `testcontainers-mongodb`, `MongoDBContainer` без `.withReplicaSet()` (multi-document транзакции только на replica set — с `@Transactional` разойдётся с SQL). Classpath 8 листьев: изоляция подтверждена (в листе ровно свой драйвер; sync без R2DBC, reactive без Tomcat/Hikari/JDBC-драйвера); `spring-boot-h2console` из `spring-boot-database-h2` убран пользователем 2026-09-21 (раньше sync-H2 нёс его вместе с `jakarta.servlet-api`); reactive SQL несёт `spring-jdbc` без драйвера и пула (транзитивно, безвредно)
- **Уже выявлено деревом (не туториалом)** — `remove` разной формы у sync и reactive порта («Активная нить» → «2026-09-21, консультация»); `NoUniqueBeanDefinitionException` и `SERVLET`-выбор при слиянии веток в один модуль («Активная нить» → «2026-08-19…21, сводка»); `MySQLContainer` требует JDBC-драйвер, `PostgreSQLContainer` нет, из-за чего дедупликация зависимостей сломала r2dbc-ветку («Завершено» → «2026-09-04, регрессия и фикс»); `application-core` отвергнут из-за bootable-природы листа («Активная нить» → «2026-09-13»); H2 ведёт себя иначе, чем MySQL/PostgreSQL, — ожидаемая вендорная разница («Открытые решения» → центральный вопрос)

## Открытые решения

- **⚠️ ЦЕНТРАЛЬНЫЙ ВОПРОС АРХИТЕКТУРЫ И ПРИЛОЖЕНИЯ — как доказать, что приложение ведёт себя одинаково на разных вендорах, драйверах и диалектах** (2026-09-21, определён пользователем как центральный; текущая работа идёт над ним, остальные пункты ниже производные; **решение не принято** — здесь постановка, состояние и рекомендация ассистента, не решение):
  - **Терминология** — цепочка запроса: репозиторий Spring Data → диалект → драйвер → вендор. Вендор — сама СУБД со своим поведением (PostgreSQL/MySQL/H2/MongoDB): типы, регистр и collation при сравнении, ограничения, транзакции, порядок NULL. Драйвер — клиентская библиотека протокола вендора под конкретный API (JDBC — `mysql-connector-j`, R2DBC — `r2dbc-mysql`, Mongo driver); привязан к паре «вендор × API», у одного вендора минимум два драйвера — это и есть граница sync/reactive; отвечает за транспорт и маппинг типов, не за текст SQL. Диалект — знание слоя над драйвером (Hibernate `Dialect`, Spring Data JDBC/R2DBC `Dialect`), как писать SQL под вендора: кавычки, `LIMIT`/`FETCH`, плейсхолдеры, получение сгенерированного id, типы; зависит от версии сервера, обычно определяется автоматически по соединению (для Boot 4.1 механизм по байткоду не проверялся — сверить при реализации); у Mongo диалекта нет (нет SQL). Ошибка диалекта — синтаксическая ошибка SQL, ошибка драйвера — расхождение типов/протокола, ошибка вендора — расхождение семантики
  - **Что значит «одинаково» — не определено**, без этого тест не знает, что считать ошибкой. Кандидаты на расхождение: схема/DDL (`UUID()`/`gen_random_uuid()`/`RANDOM_UUID()`); генерация id; типы (UUID, точность `Instant` — Mongo мс, boolean); регистр и collation (MySQL по умолчанию сравнивает без учёта регистра); duplicate-key и трансляция ошибок; транзакции и optimistic lock; порядок и позиция NULL без `ORDER BY`; путь sync против reactive; для Mongo — представление UUID в драйвере (не проверено). H2 — вендор наравне с MySQL и PostgreSQL (решение пользователя 2026-09-21): зелёный тест на H2 говорит о поведении на H2, а расхождение с другими вендорами и есть предмет сравнения
  - **Состояние на 2026-09-21** — доказывать нечем: `UserNote` и репозитории `data-*` — пустые заглушки, порта и схем нет, тесты — голый `contextLoads()`; образы `mysql:latest`/`postgres:latest` без пина, хотя версия сервера — часть оси диалекта. Из истории `note/` (см. «Активная нить» → «2026-09-21, консультация»): расхождение sync/reactive заложено в самом порте (`remove` — `S` против `Mono<Void>`), правило «не найдено» жило не в `domain`, а в каждом адаптере, бизнес-слоя не было — то же придётся решить для `user-note` заранее
  - **Следующий шаг — варианты, не выбрано.** (А) спецификация вперёд: заранее составить список поведений и по каждому решить «обязано совпасть / нормализуется в адаптере или схеме / допустимое отличие», потом писать тест — плюс ясность, минус список составляется гаданием и пропустит неочевидное. (Б) характеризационный прогон — суть в том, что спецификация берётся из прогона, а не из головы; для него нужен минимум (sync): сущность с провоцирующими полями (UUID-id, ищущая строка, `Instant`, unique-поле), порт, вендорные схемы в `application-<vendor>`, один сценарий на враждебных данных против H2+MySQL+PostgreSQL — порядок построения этого минимума (срезом или слоями) не предписан, см. «Правила» → «Порядок работы — по удобству»; каждая красная разница — вопрос «нормализуем или признаём отличием», ответы и есть спецификация — плюс расхождения находит реальность, а не воображение, минус срез и схемы нужны до первого ответа. **Рекомендация ассистента — Б**, с двумя решениями до старта: форма `remove` в порте (sync `S` против reactive `Mono<Void>`) и где живёт правило «не найдено» (порт/домен/адаптер). Дальше: пин версий образов (см. «Единый источник истины для версий»), затем общий сценарный тест в `testFixtures` («Задачи» → п.1)
  - **Граница порта — варианты, не выбрано (2026-09-21, обсуждение)** — (а) толстый порт, как в `note/`: поведение (правило «не найдено», семантика `replace`/`merge`) в каждом адаптере, TCK на весь порт против всех листьев; минус — правила копируются по веткам; (б) тонкий порт хранилища (сохранить/найти/удалить/проверить) + один прикладной сервис в двух копиях (sync/reactive): TCK переезжает на порт хранилища в `testFixtures` и гоняется в каждом `application-vendor`, поведение задано один раз, вендорные различия сосредоточены в контракте хранилища; минус — лишний слой и маппинг, каждый finder (`findByUsername`) расширяет контракт и вендорную поверхность; (в) сервис прямо на Spring Data `CrudRepository` без своего порта — отклонён: модельные классы разные по технологиям, общий класс с аннотациями всех технологий загрязнил бы домен. **Рекомендация ассистента — (б)** (событийные подходы ES/CQRS сузили бы контракт сильнее, но меняют постановку и для CRUD не нужны)
  - **Связано** — «Поведенческая аналогичность адаптеров/драйверов», «Симметрия ArchUnit» п.3, «Единый источник истины для версий», «Как выделить общее из `application-vendor`…», «Активная нить» → «2026-09-05, консультация — стандартная практика conformance-тестирования (Testcase Superclass/TCK)»
- **⚠️ ОТКРЫТЫЙ ВОПРОС ВСЕЙ АРХИТЕКТУРЫ — как писать тесты и избегать дублирования в мульти-вендорном приложении** (2026-09-21, зафиксировано по указанию пользователя; парный к центральному вопросу: тот спрашивает, ЧТО доказываем — одинаковое поведение на всех ветках дерева, этот — КАК устроить тесты и общий код, чтобы доказательство не стоило 8 копий; **решений нет**):
  - **Принято ранее**: тест один и написан на порте, не на реализации; гоняется против каждого листа (`clean check --continue`); sociable/classicist, реальный Spring-контекст, Testcontainers; тесты строятся по той же архитектуре и паттернам, что код; дублирование стремится к нулю, реально общее выносится в модуль; явная композиция через `id(...)`, без диамантов («Правила», «Задачи»)
  - **Неустранимо по природе** (не тратить силы): sync и reactive не делят код (`S` против `Mono<S>`, `WebApplicationType.deduceFromClasspath()`) — единой может быть спецификация, не код; `@SpringBootApplication` на лист (требование Spring Boot); вендорный `UserNoteTestConfiguration` (контейнер, драйвер); строка `include` в листе
  - **Требование пользователя 2026-09-21 к тестам `data-*`**: `data-*` тестируются без реального контейнера (встроенная БД только в test-scope — плагины `spring-boot-test-h2`/`spring-boot-test-r2dbc-h2`; сами `data-*` не знают ни вендора, ни драйвера), но те же тесты в будущем должны запускаться против реальных вендоров и драйверов (Testcontainers) — двойной контекст исполнения одних и тех же тестов, снова упирающийся в дублирование. Проверено 2026-09-21: в Boot 4.1.1 есть свойство `spring.test.database.replace` (по умолчанию `any`, `spring-boot-jdbc-test`) — подмену `DataSource` в `@DataJdbcTest` можно выключить свойством без смены аннотации; у `spring-boot-data-r2dbc-test` такого свойства нет (документация: встроенная БД по умолчанию; подменяет ли `@DataR2dbcTest` уже заданную `ConnectionFactory` — не проверено); Gradle-задача `test` ищет тестовые классы только в `testClassesDirs` — тесты из `testFixtures` другого модуля в листе сами не находятся. Варианты, не выбраны: (а) контрактный абстрактный тест в `testFixtures` `data-*` + тонкий подкласс в `data-*` (слайс, встроенная БД) и в каждом листе (полный контекст, контейнер) — рекомендация ассистента; (б) добавлять классы фикстур в `testClassesDirs` листа через convention-плагин — нестандартный код `build-logic`; (в) общий `srcDir` тестов — связывает сборку листа с раскладкой файлов `data-*`; (г) Testcontainers прямо в `data-*` — отклонено: `data-*` не знают вендора
  - **Уже снимается**: конфигурация — профильные файлы модулей + `spring.profiles.include`; сборка — convention-плагины; тест на порт — `testFixtures` (форма не выбрана)
  - **Не решено**: (1) где живёт общий тест и как попадает в лист (`testFixtures` + convention-плагин; `application-core` отменён, лист обязан оставаться самостоятельно bootable); (2) две семьи тестов sync/reactive — спецификация как данные (шаги и ожидаемые исходы) + два тонких исполнителя или две копии; (3) второй уровень — E2E через HTTP, один на все листья (реальный порт, `RANDOM_PORT`) — где живёт; (4) что сравнивается: видимые результаты порта/HTTP на ожидаемых путях, не динамика; реестр законных расхождений (H2 — вендор наравне с MySQL и PostgreSQL, решение пользователя 2026-09-21; его отличия обрабатываются как отличия любого вендора); (5) как принуждать, чтобы реализация не была тихо пропущена (4 слоя-кандидата, «Активная нить» → «2026-09-05, консультация»); (6) вендорные схемы и данные тестов — в `application-<vendor>` или общий механизм; (7) цена: 24 контейнерных теста, MySQL ~2× медленнее
  - **Порядок не предписан** («Правила» → «Порядок работы — по удобству»); практический шаг — вариант Б центрального вопроса и модули `webmvc`/`webflux` («Точка возврата»). **Связано**: центральный вопрос; «Устранение дублирования кода»; «Как выделить общее из `application-vendor`…»; «Симметрия ArchUnit»; «Задачи» → п.1 «Полный TDD против порта»
- **Модель доступа `UserNote` — права на заметку и роли** (2026-09-25, консультация, **решение не принято, в коде ничего нет**) — точка остановки: плоские enum `Permission`/`Role`, таблицы `Map` «право → что требует» и «роль → права», объект-значение `Permissions` с проверкой инварианта (READ обязателен, зависимости выполнены), роль — только шаблон для UI-таблицы флажков, не хранится; права строкой во всех 4 `data-*`; в JWT только userId.   - **Дублирование `application.properties` в 8 листьях — реализовано 2026-09-21** (пока что то, что можно существующими модулями): технологические строки (`logging.level.org.springframework.data=DEBUG` + `...data.<jdbc|r2dbc|mongodb>=DEBUG`) вынесены в `user-note/data-<tech>/src/main/resources/application-data-<tech>.properties`, лист подключает их строкой `spring.profiles.include=data-<tech>` (профильный файл из зависимого модуля Boot находит по имени); в листе оставались `problemdetails`, `logging.level.org.springframework.web=DEBUG` и строка `include` (вечером — в `controller-*`, см. ниже). Проверено (Boot 4.1.0, опыты в отдельном `git worktree` и на месте): набор DEBUG-логгеров в отчётах тестов всех 8 листьев до и после идентичен (в нём есть `o.s.d.*`), `clean check` зелёный, IntelliJ IDEA не показывает ошибок ни в листьях, ни в файлах модулей (`get_file_problems`). Путь к решению (опыты): `application.properties` в модуле-зависимости НЕ работает — его перекрывает одноимённый файл листа; `spring.config.import=classpath:…` работает в Boot, но IDEA разрешает `classpath:` только среди собственных ресурсов модуля (`Cannot resolve file` для файлов зависимых модулей и jar); файл с произвольным именем IDEA не признаёт конфигурацией Spring Boot (`Unused property`), профильное `application-<x>.properties` признаёт автоматически (документация JetBrains; остальные — вручную в Project Structure, то есть настройкой IDE, не репозитория); `spring.profiles.include` (документация Boot: только в непрофильных документах) снимает обе проблемы; `@PropertySource` не подходит (документация: слишком поздно для `logging.*`); `EnvironmentPostProcessor` не проверялся. Цена: Boot пишет `The following 1 profile is active: "data-<tech>"`, профиль виден в `Environment` (фрагмент конфигурации, не выбор вендора); что профильные файлы грузятся из зависимых jar, документация не говорит — подтверждено только опытом. Остаточное дублирование: только строка `include` (структурно неизбежна) — `web`/`problemdetails` вынесены вечером тем же механизмом в `controller-webmvc`/`controller-webflux`. Общий принцип: общее живёт на том уровне дерева, где оно общее, механизм — по виду артефакта (код — shared-модуль/`testFixtures`, сборка — convention-плагин, конфигурация — профильные файлы модулей + `spring.profiles.include`)
- **Как выделить общее из `application-vendor` без потери bootable-природы и уже существующих тестов на модуль** (2026-09-13, открыто после отмены `application-core`, см. «Активная нить») — цель, сформулированная пользователем: добавление нового вендора должно быть максимально дешёвым, сразу самостоятельно bootable, сразу учитывать уже существующие тесты. `application-core` (main-класс в не-bootable модуле-зависимости) — испробованный и отклонённый вариант, конкретная причина отказа — каждый `application-*` перестаёт быть самодостаточным. **Не форсировать поспешным решением** — пользователь допишет проект сам, разбор нового варианта — по отдельному запросу
