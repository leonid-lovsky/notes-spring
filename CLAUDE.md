## Правила

- **Голый API-стартер не подключается, если есть обёртка (Spring Data и т. п.) для той же технологии — даже если технически обёртка не несёт 100% функционала голого стартера** (2026-08-15, явное решение пользователя, отменяет собственную рекомендацию агента по итогам факт-проверки) — прецедент: `spring-boot-starter-elasticsearch` подключён рядом с `spring-boot-starter-data-elasticsearch` (несёт реальный `elasticsearch-java`-драйвер, которого `data-elasticsearch` транзитивно не тянет, проверено и POM, и Gradle Module Metadata) — пользователь всё равно убрал голый стартер вручную и явно сформулировал общее правило: «не используем голый API при наличии обёртки». Риск (Spring Data Elasticsearch без реального клиента может не заработать в рантайме) осознан пользователем — «проверить при реальном обращении», не превентивным подключением про запас. Это отменяет более узкое обоснование из записи 2026-08-15 «пересматривает правило... но избыточность, доказанную фактами, применять не мешает» — теперь правило шире факта транзитивности: голый API не нужен как класс решений, независимо от того, доказана ли конкретная избыточность фактами по каждой технологии отдельно
- **⚠️ ИСТОЧНИК ИСТИНЫ ДЛЯ SPRING-ФАКТОВ — НЕ MAVEN CENTRAL ПОИСК** [НЕ СОКРАЩАТЬ/НЕ УДАЛЯТЬ — исключение из правила «убирать избыточность», даже при явной задаче уменьшить объём CLAUDE.md] (2026-07-14, резкая реакция пользователя на ошибку): вопрос «существует ли артефакт X» **никогда** не проверять через `search.maven.org` (Solr-индекс отстаёт от реального репозитория, `0 numFound` НЕ значит «не существует» — конкретная ошибка: заявил, что `spring-boot-starter-r2dbc` не существует по 0 результатам поиска, хотя это реальный отдельный от `data-r2dbc` стартер). Источник истины — **Spring Initializr** (`start.spring.io/metadata/client` — реальный список id/name/description), **GitHub spring-projects**, **официальная документация docs.spring.io**. Maven Central годится только для номера версии уже известного, существующего артефакта — не для вопроса о самом его существовании. **`docs/spring-boot-starters-reference.md`** (2026-07-14) — дословная копия со Spring Initializr, лежит в репозитории локально: для вопроса «существует ли стартер X» и «как называется» обращаться сначала туда, не в web-поиск. При выборе/добавлении стартера под конкретную технологию — сверяться по этому файлу, есть ли для неё отдельный `-test`-компаньон (`spring-boot-starter-{tech}-test`), и подключать его вместе с основным, если существует — не пропускать по своему усмотрению (см. прецедент с `spring-boot-starter-r2dbc`/`-jdbc`/`-elasticsearch`, где `-test`-версия изначально была упущена). Также перед добавлением зависимости в Spring Boot модуль — сверяться, нет ли для этой технологии уже готового `spring-boot-starter-*`: если есть, подключать именно его, а не «сырую» внешнюю зависимость напрямую (starter уже несёт нужный BOM-managed набор транзитивных зависимостей и autoconfiguration — обходить его напрямую значит терять то и другое). **Принадлежность к Initializr — определять только буквальным поиском строки артефакта в `docs/spring-boot-starters-reference.md`, никогда рассуждением по форме имени артефакта** (2026-08-02, резкая реакция пользователя на ошибку): конкретная ошибка — заявил, что `org.springframework.boot:spring-boot-docker-compose` «не Initializr-стартер», по неверной логике «раз в имени артефакта нет `-starter-`, значит это core-модуль Boot, а не выбираемая в Initializr зависимость» — вывод по паттерну имени, без единой проверки. У Spring Initializr многие зависимости (Docker Compose Support, Lombok, Actuator и др.) не содержат `-starter-` в имени артефакта, наличие/отсутствие этого подслова в имени не говорит ничего о членстве в Initializr. Строка `developmentOnly 'org.springframework.boot:spring-boot-docker-compose'` при этом дословно уже присутствовала в `docs/spring-boot-starters-reference.md:178` — файл был не прочитан перед утверждением. Правило: любое утверждение вида «X не относится к Initializr»/«X не существует как стартер» — сначала grep по точной строке артефакта в `docs/spring-boot-starters-reference.md`, и только отсутствие там даёт право на такое утверждение (с оговоркой, что файл не абсолютно полон — см. соответствующий пункт правила выше)

- **Перед архитектурным ответом — контрольный список: стандартный паттерн / переформулировка / другой угол / альтернативы** (2026-08-08, обобщено по итогам диалога про единый контракт Controller/Service — см. «Задачи» → «Завершено» → «2026-08-08, единый generic-контракт Controller/Service/Repository» и `docs/decisions-log.md` → «Архитектура», где ассистент сначала трижды прошёлся по локальным вариациям (Object-хак / отказ от интерфейса / снятие ограничения), прежде чем распознать типовой случай): прежде чем предлагать вариант решения, явно проверять четыре вопроса, не бросаться к первому найденному через локальный код рецепту — (1) не является ли задача частным случаем известного стандартного паттерна (пример прецедента — «N классов с совпадающими по сигнатуре, имя+параметры, JLS, методами, различающихся типом возврата» → параметрический полиморфизм, как `Optional<T>`/`Comparator<T>`/`CrudRepository<T, ID>`); (2) можно ли переформулировать саму постановку задачи, не размывая заданных пользователем ограничений; (3) можно ли посмотреть на неё с другого угла — начинать рассуждение с абстрактной формы задачи, а не с того, что уже реализовано в репозитории как локальный прецедент; (4) есть ли альтернативные способы решения помимо первого пришедшего в голову. Решения, которые снимают заданное пользователем ограничение ради тривиальности (прецедент — предложение убрать `ResponseEntity` из Controller), предлагать можно, но явно помечая как «меняет постановку задачи», не выдавая за рекомендованный ответ на исходный вопрос. **Чек-лист проходить явно и видимо в самом ответе** (уточнено 2026-08-08, повторный запрос пользователя зафиксировать «способ размышления»; форма уточнена 2026-08-21 — резкая реакция на буквальные ярлыки-вопросы вида «Стандартный паттерн? Да —») — не как молчаливая внутренняя проверка перед выводом готового решения, а как показанные шаги рассуждения, поданные обычной связной прозой, без ярлыков/риторических вопросов-заголовков на каждый пункт чек-листа — форма чек-листа (четыре вопроса) держится в голове при рассуждении, в тексте виден только его результат, естественным языком; при повторном применении к уже решённому вопросу — не просто повторять прежний вывод, а переискать его заново (пример — единый контракт Controller/Service передуман через рамку Adapter/GoF и уже принятую в проекте driving/driven-симметрию портов, а не просто повторно назван «параметрический полиморфизм»). **Свежий взгляд, не фиксация на уже предложенных вариантах** (уточнено 2026-08-08, третий подряд запрос пользователя зафиксировать способ размышления) — при создании решения смотреть на проблему заново, не ограничиваясь набором вариантов, уже прозвучавших в диалоге (A/B/C/D/F и т. п.) — этот набор не исчерпывающий по умолчанию, промежуточный список — не потолок для дальнейшего поиска
- **Запрещены заглушки как решение задачи** (2026-08-08) — заглушка (placeholder, TODO-затычка, урезанная версия «пока сойдёт») не решает проблему, а избегает её; решение всегда рабочее
- **Запрещён откат к более примитивному варианту ради простоты реализации** (2026-08-08) — если выбранное решение оказывается сложным в реализации, разбираться со сложностью, не понижать задним числом планку уже выбранного варианта — это тоже избегание проблемы, не решение

- **Кольцевые/ромбовидные зависимости — ВСЕГДА избегать, без исключений, в любом месте проекта** (введено 2026-07-14, ужесточено 2026-07-15, **сделано абсолютным 2026-08-01**): при любой правке convention-плагинов, Gradle project-зависимостей (`projects.*`) или Java-иерархий портов/адаптеров — проверять граф на циклы и на схождение путей (диамант «вида 1» — определение см. в этом же пункте, «Два разных вида схождения — не путать») и устранять его, даже ценой дублирования кода — чистота/ясность/предсказуемость графа важнее объёма copy-paste. Это отменяет более раннюю формулировку «решение оставить/устранить — за пользователем»: пользователь дважды экспериментировал с осознанным принятием диаманта ради устранения дублирования (`spring-cloud-application` дважды — 2026-07-15 и 2026-08-01) и оба раза в итоге откатывал это решение обратно к нулю диамантов — правило зафиксировано на основе этого повторяющегося исхода, не отдельного случая. Сообщать о находке по-прежнему обязательно (что найдено, где), но действие по умолчанию теперь «устранить», а не «спросить». Прецедент устранения без дублирования, когда возможно: `spring-cloud-application` (диамант `spring-cloud`+`spring-boot-application`) устранён заменой на прямой `id("org.springframework.boot")`, так как `spring-boot-application` к тому моменту стал чистым alias без собственной нагрузки — 0 диамант, 0 дублирования. Прецедент устранения ценой дублирования: `spring-boot-actuator` — отдельный атомарный плагин, применяется явно `id(...)` на каждом из 37 bootable-листовых модулей (не встроен вторым родителем ни в `spring-boot-application`, ни в `spring-cloud-application`, хотя это устранило бы необходимость 37 явных `id(...)` ценой диаманта — отклонено). Никаких shared-функций/helper-кода в `build-logic/` для устранения подобных схождений — только композиция через `id(...)`. **Два разных вида схождения — не путать**: вид 1 — диамант внутри самого convention-плагина (файл в `build-logic/` сам в своём `plugins{}` вызывает 2+ `id("com.example.*")`, сходящихся в общем предке) — устранять всегда, без исключений. Вид 2 — листовой модуль (`build.gradle.kts` сервиса) напрямую применяет 2+ convention-плагина, сходящихся в общем предке (например `note/application-h2-jpa` — `spring-boot-application`+`spring-boot-database-h2`; `gateway/application` — `spring-cloud-application`+3 `spring-cloud-*`) — **не диамант для устранения**, а осознанная композиция независимых convention-плагинов в точке использования, ради которой вся система convention-плагинов и построена (решено пользователем 2026-07-15, не поднимать заново без нового явного повода)
- **Convention-плагины — всегда атомарны, один плагин = один концерн/технология** (закреплено как постоянное правило 2026-08-01, до этого — серия точечных решений, см. `docs/decisions-log.md` → «Атомизация базовых плагинов»): не объединять в одном плагине несколько независимых зависимостей/стартеров ради удобства, даже если они сегодня всегда применяются вместе (прецедент — вынос `spring-boot-starter-validation` из `spring-boot` в отдельный `spring-boot-validation`; воссоздание `spring-boot-actuator` из `spring-boot-application`). Если возможность применяется не везде одинаково или концептуально независима — отдельный плагин, композиция через явный `id(...)` в точке использования, не через объединение содержимого
- **Предпочитаем явную композицию неявному наследованию — во всём проекте, не только в convention-плагинах** (закреплено 2026-08-01, обобщает предыдущий пункт и правило про диаманты — все три работают вместе на один результат; область действия расширена пользователем в тот же день с Gradle-плагинов на весь проект целиком): когда модулю/классу/конфигурации нужны 2+ независимые возможности — явное объявление каждой рядом, в точке использования, а не одна возможность, встроенная родителем/зависимостью другой ради экономии строк. Действует одинаково в трёх плоскостях:
  - **Convention-плагины** (где правило впервые сформулировано) — явный `id(...)` для каждой возможности на листе, не встраивание через родителя. Даже если возможность нужна на 100% модулей, где применяется родитель, без единого исключения (как у `spring-boot-actuator`) — это не повод встраивать её через наследование. Отход от композиции — не ради компактности кода, а только когда явной альтернативы физически не существует (прецедент: `spring-boot-docker-compose` — `id("org.springframework.boot")` там не встраивание ради экономии, а техническая необходимость для typed-аксессора `developmentOnly`)
  - **Java-код** — предпочитать композицию наследованию классов везде, где выбор есть (внедрение зависимости/делегирование вместо `extends` ради переиспользования кода); интерфейсная иерархия портов (`{Entity}Interface`→`{Entity}ServiceInterface`/`{Entity}ControllerInterface`, см. «Именование») — контракт, не реализация, этого правила не касается
  - **Настройки/конфигурация** (Spring `application.properties`, профили и т. п.) — явные, отдельные свойства/файлы на концерн, не неявное наследование конфигурации через профили-предки или глубоко вложенные default-механизмы

  1. **Порядок старта контейнерного `@Bean`** — `docs.spring.io` → «Lifecycle of Managed Containers» документирует гарантию «container beans are created and started before all other beans» дословно, но не называет механизм.   2. **`JdbcConnectionDetails` — обязательная прослойка в Boot 4.1, не опция `@ServiceConnection`** — байткод `DataSourceConfiguration$Hikari.dataSource(DataSourceProperties, JdbcConnectionDetails, Environment)` показывает, что метод создания `HikariDataSource`-бина принимает `JdbcConnectionDetails` как обязательный параметр всегда, вне зависимости от наличия `@ServiceConnection`. Значит `DataSource`-бин **создаётся в обоих случаях**; `@ServiceConnection` не включает/выключает его создание, а лишь подменяет, какой именно `JdbcConnectionDetails`-бин победит (`@ConditionalOnMissingBean`-подобный приоритет: bean от `@ServiceConnection` — с реальным портом контейнера, иначе — `PropertiesJdbcConnectionDetails` со статичным портом из properties)
  3. **Практическое следствие, если убрать `@ServiceConnection`** — Testcontainers всегда мапит порт контейнера на случайный свободный порт хоста (не совпадает с портом в properties, например `3306`/`5432`). Без `@ServiceConnection`/`@DynamicPropertySource` контекст всё равно поднимается (создание `HikariDataSource`-объекта не требует соединения), но `contextLoads()` падает именно на `dataSource.getConnection()` — на выписанном в properties порту никто не слушает. Худший случай — на этом порту случайно слушает настоящий сервер (например, локальный dev-инстанс MySQL у разработчика) — тест тогда молча подключается не к тому, что нужно, теряя изоляцию. Это общая проблема любого сочетания Testcontainers+Spring Boot, не специфика этого проекта — `@DynamicPropertySource` (более старый способ, предшествующий `@ServiceConnection`) решает её вручную тем же путём

## Архитектура и структура проекта

**Многомодульная сборка (Gradle)** — схема: путь — назначение:
- `build-logic/settings.gradle.kts` — `include(":convention")`; included build, подключён через `pluginManagement { includeBuild(...) }` в корневом `settings.gradle.kts`
- `build-logic/convention/.../com.example.{name}.gradle.kts` — convention plugins (Kotlin DSL), namespaced id без суффикса `-conventions` (`com.example.spring-boot`, не `-conventions`); полный граф родитель→потомок всех 49 — см. `docs/convention-plugins-graph.md`
- `settings.gradle.kts` — единственный, в корне; `include(":...")` на все subprojects
- `{service}/{module}/build.gradle.kts` — применяет plugin через `id("com.example.{name}")`
- `{service}/{application,domain,persistence,presentation}/{module}/build.gradle.kts` — для `note`/`user`/`user-note` физическое расположение модуля вложено в подпапку по слою (2026-08-01, было плоско `{service}/{module}/`; см. «Именование» → «Группировка модулей по слою в подпапку» и «Открытые решения»/decisions-log за 2026-08-01). Gradle project path остаётся плоским (`:{service}:{module}`, без вложенности) — `settings.gradle.kts` переопределяет `project(":{service}:{module}").projectDir` на новый физический путь; typesafe accessors (`projects.note.domain`, `projects.userNote.dataJpa` и т. п.) не меняются

**Пакеты по сервисам** — путь — package:
- `note/` → `com.example.note`
- `user/` → `com.example.user`
- `user-note/` → `com.example.usernote` (не `user.note`!)

**Слои внутри сервиса** (зависимость → куда смотрит; физические пути — для `note`/`user`/`user-note`, сгруппированы по подпапке слоя с 2026-08-01) — схема: путь — роль — зависимость:
- `domain/domain/` — records·enums·exceptions — чистая Java, без зависимостей на инфраструктуру
- `domain/contract/` — sync port interfaces → `domain/domain/` (api)

- `presentation/webmvc/` — driving adapter sync → `domain/contract/`
- `presentation/webflux/` — driving adapter reactive → `domain/contract-reactive/`
- `persistence/data-jpa/` — driven adapter JPA → `domain/contract/`
- `persistence/data-jdbc/` — driven adapter JDBC → `domain/contract/`
- `persistence/data-r2dbc/` — driven adapter R2DBC → `domain/contract-reactive/`
- `persistence/data-mongodb/` — driven adapter MongoDB → `domain/contract/`
- `persistence/data-mongodb-reactive/` — driven adapter Mongo reactive → `domain/contract-reactive/`
- `application/application-{h2,mysql,postgresql}-jpa/` — composition root (sync) → presentation/webmvc + persistence/data-jpa
- `application/application-{h2,mysql,postgresql}-jdbc/` — composition root (sync) → presentation/webmvc + persistence/data-jdbc
- `application/application-{h2,mysql,postgresql}-r2dbc/` — composition root (reactive) → presentation/webflux + persistence/data-r2dbc

Ровно один driven-адаптер и ровно один вендорный БД-драйвер на classpath каждого composition root — обе оси (технология адаптера, вендор БД для jpa/jdbc/r2dbc) выражены границей Gradle-модуля, не рантайм-профилем (пересмотр 2026-07-24 — было `spring.profiles.active`, см. `docs/decisions-log.md` → «Архитектура»: профиль выбирает bean в рантайме, но не убирает лишние драйверы из паковки). 11 composition-root модулей на сервис (9 реляционных + 2 Mongo, у Mongo вендорной оси нет) × 3 сервиса = 33. **⚠️ `user-note/` сознательно отступает от этого абзаца с 2026-08-19** (не WIP — см. «Задачи» → «Продолжение 2026-08-19», «Апдейт 2026-08-19, ещё позже») — вендорная ось для JDBC/JPA/R2DBC снова совмещена в одном модуле на технологию (3 драйвера на classpath, driver bloat принят сознательно как меньшее зло по сравнению со сложностью shared test-fixtures); не постоянное решение — пользователь допускает возврат к разделению по вендору специально ради driver bloat в будущем. `note`/`user` физически не тронуты (33-модульная структура сохраняется) — перенос этого выбора на них не вопрос для обсуждения, станет виден по факту правки пользователем.

**Tech**: `Jpa` · `Mongo` · `Jdbc` · `R2dbc` · `MongoReactive` (в имени класса — только для `{Tech}MapperContract`/`{Tech}Mapper`/`{Tech}Repository`/`{Tech}Entity`; адаптеры и порт-интерфейсы суффикс технологии в имени не несут — технология различается пакетом/модулем)

**Vendor** (2026-07-24, только для composition-root класса/модуля jpa/jdbc/r2dbc, см. «Composition-root главный класс» выше): `H2` · `MySQL` · `PostgreSQL` — всегда префикс перед `{Tech}`, порядок `{Vendor}{Tech}` (`H2Jpa`, не `JpaH2`) — пересмотрено в тот же день: изначально был выбран порядок `{Tech}{Vendor}` («технология доступа архитектурно более фундаментальна»), затем перевёрнут по решению пользователя без изменения обоснования самой оси (вендор/технология остаются раздельными осями именования, поменялся только порядок отображения). **Вопрос снят как неактуальный 2026-08-19** — модуль `{Tech}-{Vendor}` физически перестал существовать (5 плоских модулей вместо 11 вложенных вендорных, см. «Задачи» → «Продолжение 2026-08-19» п. 2), сравнивать порядок `{Vendor}{Tech}` vs `{Tech}{Vendor}` больше не с чем; если вендорная ось модуля когда-нибудь вернётся — вопрос открыть заново, не считать прежнее наблюдение решением

**Группировка модулей по слою в подпапку** (2026-08-01, начато пользователем вручную в `user-note/` — `git mv` в новую вложенность, опечатка `pestistence` вместо `persistence`; агент исправил опечатку и применил ту же структуру симметрично к `note/`·`user/`): для всех трёх зрелых сервисов физический путь листового модуля — `{service}/{layer}/{module}/`, где `{layer}` ∈ `application`·`domain`·`persistence`·`presentation` (`domain/domain`, `domain/contract`, `domain/contract-reactive` — все три под `domain/`; `data-*` → `persistence/data-*`; `webmvc`/`webflux` → `presentation/{module}`; все `application-*` → `application/application-*`). Сам Gradle project path (и, следовательно, имя typesafe-accessor) не меняется — остаётся плоским `:{service}:{module}` — только физическая директория переопределена через `project(":{service}:{module}").projectDir` в `settings.gradle.kts` (см. «Архитектура и структура проекта» → «Многомодульная сборка»). Ранее аналогичный, но более узкий вопрос («каталог `data/` на уровне сервиса» — только для `data-*`) обсуждался и было решено оставить плоско (цена реорганизации выше пользы) — это решение пересмотрено данным изменением, которое к тому же шире исходного вопроса (охватывает все 4 слоя, не только `data-*`)

## Открытые решения

- **Единый источник истины для версий (Docker-образы, Java) во всех окружениях — dev/test/prod/GitHub Actions/Kubernetes** (2026-08-21, вырос из узкого вопроса «версия Docker-образа для Testcontainers vs реальный запуск», см. «Задачи» → «Активная нить» → «2026-08-20»/«2026-08-21» — там же техническое решение конкретно для `JDBC`-модуля; здесь — вопрос шире, по всему проекту и всем окружениям; **решение — в следующей сессии, здесь только исследование**) — главная находка: **для Java эта проблема уже решена в репозитории**, и решение — рабочий образец для Docker. Корневой `.java-version` (значение `21`) читают одновременно (1) Gradle — `build-logic/convention/.../com.example.java.gradle.kts:20`, `providers.fileContents(rootProject.layout.projectDirectory.file(".java-version")).asText.get().trim().toInt()` → `JavaLanguageVersion.of(...)`; (2) `.github/workflows/gradle.yml` — `actions/setup-java@v4` c `java-version-file: '.java-version'` (подтверждено официальной документацией `actions/setup-java` — параметр поддерживает файлы `.java-version`/`.tool-versions`/`.sdkmanrc`). Один файл, два независимых читателя, ни одной второй копии числа `21` в репозитории — то есть по оси «Java» единый источник истины уже есть и не требует решения.
  По оси **Docker-образов** (`mysql:9`/`postgres:18`/…) готового моста между инструментами нет, и это факт устройства экосистемы, не недосмотр: Docker Compose умеет **нативно** интерполировать `${VAR}` в `image:` из project-level `.env`-файла (официальная документация Docker Compose — `.env` подставляется до парсинга самого compose-файла); Testcontainers-Java — нет, `MySQLContainer`/`PostgreSQLContainer` принимают тег только явным Java-аргументом конструктора, единственный официальный конфигурационный крюк — `testcontainers.properties`+`ImageNameSubstitutor` (полная подмена образа, не выбор версии) — точечное переопределение тега через конфиг **официально не рекомендовано и deprecated** (`java.testcontainers.org/features/configuration`); GitHub Actions читает версию сама только если использует `services:`-контейнеры — в этом проекте Testcontainers всегда стартует изнутри Gradle `test`-таска на раннере, отдельного `services:`-блока нет, значит ось GitHub Actions для Docker-образов сегодня не требует отдельного моста вообще, она уже наследует то, что получит Gradle; Kubernetes в проекте не используется совсем (см. «Технологии» → `docs/tech-glossary.md`) — для него нет ни одного файла, с которым сверяться, вопрос сегодня чисто гипотетический, готовый паттерн на будущее — Kustomize `images:`-трансформер или Helm `values.yaml` (централизация тега на уровне манифеста, независимая проверка через `kubernetes-sigs/kustomize` доку).
  Рассмотренные варианты для Docker-оси: (а) **зеркалировать `.java-version`-паттерн** — общий текстовый файл (например корневой `.env` или `docker-versions.properties`) с одной строкой на вендор, Gradle читает его тем же `providers.fileContents(...)`, что уже используется для Java, и прокидывает как `systemProperty`/`environment` в `test`-таск, Testcontainers-код читает `System.getProperty(...)` вместо литерала; `compose.yaml` (если появится) читает тот же `.env` нативной интерполяцией Compose — совпадает по механике с уже проверенным Java-решением, не изобретает новый инструмент. (б) **Gradle version catalog (`libs.versions.toml`)** — рассмотрен и отклонён для этой конкретной оси: официальная позиция Gradle («Best Practices for Dependencies») — catalog предназначен для версий зависимостей/плагинов, использование `[versions]` как общего хранилища произвольных строк (образ БД — не Gradle-зависимость) прямо не рекомендовано самим Gradle; остаётся легитимным для смежного, но другого вопроса — версий Java-библиотек (`mysql-connector-j`, testcontainers-модули и т. п.), не тегов образов. (в) **Renovate `customManagers`/`regexManagers` с группировкой PR** — не устраняет дублирование строк, а автоматически держит все совпадения (в т. ч. Java-литерал и `compose.yaml`) синхронно забамленными через один PR по регулярке — дополняет (а), не заменяет: (а) устраняет саму необходимость двух копий, Renovate нужен, только если копии всё равно остаются (например тег в `compose.yaml` и версия `mysql-connector-j` — два разных, но связанных числа, которые физически нельзя слить в одну строку). (г) **mise/asdf `.tool-versions`** — рассмотрен и отклонён как нерелевантный для Docker-оси: управляет версиями устанавливаемых локально CLI-инструментов (Java, Node и т. п. — тем же, что уже решает `.java-version`+`setup-java`), не версиями тегов образов внешних сервисов, которые не устанавливаются, а пуллятся.
  **Рекомендация для следующей сессии**: вариант (а), как прямое расширение уже проверенного и работающего в этом репозитории паттерна — не нового изобретения; (в) держать в уме как дополнение, когда/если появится второй легитимно-раздельный источник той же версии (например Java-драйвер БД). Ничего не реализовано — только сбор фактов, ждёт решения пользователя

  2. Матрица тестового покрытия — вариант (A) «отдельный класс/модуль на комбинацию» реализован для `note`/`user` (33 composition-root модуля, один `*ApplicationTests` на модуль); **для `user-note` этот инвариант больше не действует с 2026-08-19** (5 объединённых модулей, вендор внутри — см. «Задачи» → «Активная нить»). Вариант (B) `@ParameterizedTest` снят как противоречащий тогдашнему «вендор — граница модуля»; вариант (C) — мета-тест по типу ArchUnit («на каждый вендорный плагин должен существовать application-модуль») — зависит от решения по пункту 1, актуальность для `user-note` пересмотреть заново после изменения 2026-08-19
- **Поведенческая аналогичность адаптеров/драйверов** (названо пользователем главной проблемой на пути к зрелости CRUD-модулей, 2026-07-24; **не реализовывать до отдельного запроса**) — реализации порта по матрице технология×вендор должны вести себя одинаково при одинаковом сценарии; находки по факту чтения кода `note/` (не перепроверялись отдельно для `user/`/`user-note/`, предполагается та же структура):
  1. Порты не специфицируют поведение (голый `Object`, без `throws`/`Optional`/`@Nullable`/Javadoc) — **2026-08-18 переосмыслено как осознанное разделение**: спецификация поведения сознательно живёт в тестах application-уровня, порт остаётся чисто структурным контрактом
  2. Обработка «не найдено» сегодня случайно одинакова во всех 5 адаптерах (`orElseThrow(NoteNotFoundException)`/`switchIfEmpty(Mono.error(...))`) — не гарантирована ни портом, ни тестом
  3. Реальные расхождения: генерация ID тремя механизмами (JPA — `@GeneratedValue` через Hibernate; JDBC/R2DBC — `DEFAULT RANDOM_UUID()` в `schema.sql`; MongoDB — `UUID.randomUUID()` в мапере); duplicate-key нигде не транслируется ни в одном из 5 адаптеров (сценарий сегодня недостижим — нет unique-constraint кроме PK — но латентный риск, `NoteExceptionHandler` обработает только `NoteNotFoundException`); MongoDB (blocking) `add()` использует `mongoTemplate.insert()` напрямую, минуя repository, в отличие от остальных операций/адаптеров
  4. Одинаковые (не расходящиеся) пробелы во всех 5: `@Transactional` отсутствует везде (`merge()`/`replace()` — read-then-write без атомарности); Bean Validation отсутствует везде (аннотации `@NotNull`/`@NotBlank` на model-классах не расставлены, хотя `spring-boot-starter-validation` подключён точечно)
  5. **Referential integrity между `user-note/` и `user/`·`note/` не проверяется вообще** (найдено 2026-07-24) — `create()` в `UserNoteService` (`data-jpa`) сохраняет `UserNoteEntity` без проверки, что `userId`/`noteId` реально существуют в `user/`/`note/`: ни синхронного вызова порта, ни события, ни constraint (сервисы физически разделены). Там, где проверка вроде есть (`existsByUserId` — проверяет «есть ли уже связка в `user_note`», не «существует ли пользователь»), она обманчива — `UserNotFoundException` там означает «у userId нет заметок», не «пользователя нет». Не перепроверено для jdbc/r2dbc/mongodb/mongodb-reactive `user-note/`. Тот же класс проблемы («нет referential integrity через границу сервиса») встанет и в «Регистрация auth/ ↔ user/» ниже

  Кандидат-решение, не проработан: общий conformance test suite через `java-test-fixtures` — абстрактный JUnit-класс против интерфейса порта, параметризуемый в каждом `data-*`/composition-root модуле своим адаптером; требует заранее провести границу «что обязано совпадать» vs «что законно различается» (пример законного различия — bean-validation автотриггер: Hibernate триггерит, MongoDB/R2DBC/JDBC — нет)
- **Стоимость масштабирования composition-root матрицы** (2026-07-24) — рост числа модулей мультипликативен (сервисы × технологии × вендоры). Два разных вопроса: (1) рост числа модулей — цена уже принятого решения «вендор — граница модуля» (для `note`/`user`; `user-note` отступил от этого с 2026-08-19, см. «Задачи»), откат вернул бы driver bloat; (2) рост стоимости добавления модуля (дублирующийся boilerplate) — можно снижать без изменения топологии, варианты не проработаны (пересмотреть обязательность полной 3×3-симметрии; оценить реальный объём дублирования перед решением, что менять). Эмпирика по времени сборки — см. «Правила» → «Build» → «`clean check` с реальным Docker» (MySQL ~2× медленнее PostgreSQL/MongoDB, H2 без контейнера 9–14с). Не реализовывать до отдельного запроса
- **Область подключения `spring-boot-starter-validation`** — решено 2026-08-01 (атомарный `spring-boot-validation`, только `webmvc`/`webflux`/`data-jpa` × 3 сервиса). Остаточный пункт, **не поднимать и не напоминать до отдельного запроса**: `data-mongodb`/`data-mongodb-reactive` требуют написать и зарегистрировать `ValidatingMongoEventListener`+`LocalValidatorFactoryBean` (Spring Boot не автоконфигурирует), без этого голый стартер там ничего не даёт. R2DBC/JDBC (Spring Data Relational) — ни автотриггера, ни listener-механизма нет вообще, подключать нечего
- **Регистрация `auth/` ↔ `user/`** — Lazy / Sync / Events (Kafka); та же проблема класса «нет referential integrity через границу сервиса», уже реально найденная между `user-note/` и `user/`·`note/` — см. «Поведенческая аналогичность» → п. 5 выше
- **Возврат мутирующего use case** — DTO vs `void`, не проработано
- **`@Transactional` на методах адаптера** — решение зафиксировано, но не реализовано ни в одном адаптере ни одной технологии (~150 файлов). Решить: реализовать по всем адаптерам или снять как устаревшее (Spring Data репозитории и так транзакционны на уровне метода)
- **`user/`: `findByEmail`/`findByUsername` без HTTP-входа** — доведены до всех driven-адаптеров, не выведены в `webmvc`/`webflux`. Варианты: задел под будущий `auth/`, добавить контроллеры сейчас, или убрать как неиспользуемое
- **Javadoc в `package-info.java`** — ни один пакет не содержит package-level Javadoc, только `@NullMarked`; `checkstyle.xml` сейчас исключает javadoc-проверки — включение потребует такого комментария в каждом пакете
- **Composite build на границе сервисов** — каждый сервис мог бы подключаться через `includeBuild(...)` вместо `include(...)`. Ни один сервис не ссылается на модули другого, accessors не пострадали бы, но цена (7 новых `settings.gradle.kts`, ручная агрегация `build`/`check`/`clean`) больше выигрыша без текущего драйвера (независимое CI/версионирование, разъезд по репозиториям)
- **Инструмент миграции БД по адаптерам** (2026-07-15) — справочный обзор кандидатов (Flyway/Liquibase, Mongock/Flamingock, elasticsearch-evolution) вынесен в `docs/db-migration-tools-reference.md`. Ключевая находка: Mongock в maintenance mode, EOL конец 2026, преемник — Flamingock. Выбор не сделан — не реализовывать до отдельного запроса
