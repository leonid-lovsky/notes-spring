## Правила

- **Голый API-стартер не подключается, если есть обёртка (Spring Data и т. п.) для той же технологии — даже если технически обёртка не несёт 100% функционала голого стартера** (2026-08-15, явное решение пользователя, отменяет собственную рекомендацию агента по итогам факт-проверки) — прецедент: `spring-boot-starter-elasticsearch` подключён рядом с `spring-boot-starter-data-elasticsearch` (несёт реальный `elasticsearch-java`-драйвер, которого `data-elasticsearch` транзитивно не тянет, проверено и POM, и Gradle Module Metadata) — пользователь всё равно убрал голый стартер вручную и явно сформулировал общее правило: «не используем голый API при наличии обёртки». Риск (Spring Data Elasticsearch без реального клиента может не заработать в рантайме) осознан пользователем — «проверить при реальном обращении», не превентивным подключением про запас. Это отменяет более узкое обоснование из записи 2026-08-15 «пересматривает правило... но избыточность, доказанную фактами, применять не мешает» — теперь правило шире факта транзитивности: голый API не нужен как класс решений, независимо от того, доказана ли конкретная избыточность фактами по каждой технологии отдельно
- **⚠️ ИСТОЧНИК ИСТИНЫ ДЛЯ SPRING-ФАКТОВ — НЕ MAVEN CENTRAL ПОИСК** [НЕ СОКРАЩАТЬ/НЕ УДАЛЯТЬ — исключение из правила «убирать избыточность», даже при явной задаче уменьшить объём CLAUDE.md] (2026-07-14, резкая реакция пользователя на ошибку): вопрос «существует ли артефакт X» **никогда** не проверять через `search.maven.org` (Solr-индекс отстаёт от реального репозитория, `0 numFound` НЕ значит «не существует» — конкретная ошибка: заявил, что `spring-boot-starter-r2dbc` не существует по 0 результатам поиска, хотя это реальный отдельный от `data-r2dbc` стартер). Источник истины — **Spring Initializr** (`start.spring.io/metadata/client` — реальный список id/name/description), **GitHub spring-projects**, **официальная документация docs.spring.io**. Maven Central годится только для номера версии уже известного, существующего артефакта — не для вопроса о самом его существовании. **`docs/spring-boot-starters-reference.md`** (2026-07-14) — дословная копия со Spring Initializr, лежит в репозитории локально: для вопроса «существует ли стартер X» и «как называется» обращаться сначала туда, не в web-поиск. При выборе/добавлении стартера под конкретную технологию — сверяться по этому файлу, есть ли для неё отдельный `-test`-компаньон (`spring-boot-starter-{tech}-test`), и подключать его вместе с основным, если существует — не пропускать по своему усмотрению (см. прецедент с `spring-boot-starter-r2dbc`/`-jdbc`/`-elasticsearch`, где `-test`-версия изначально была упущена). Также перед добавлением зависимости в Spring Boot модуль — сверяться, нет ли для этой технологии уже готового `spring-boot-starter-*`: если есть, подключать именно его, а не «сырую» внешнюю зависимость напрямую (starter уже несёт нужный BOM-managed набор транзитивных зависимостей и autoconfiguration — обходить его напрямую значит терять то и другое). **Принадлежность к Initializr — определять только буквальным поиском строки артефакта в `docs/spring-boot-starters-reference.md`, никогда рассуждением по форме имени артефакта** (2026-08-02, резкая реакция пользователя на ошибку): конкретная ошибка — заявил, что `org.springframework.boot:spring-boot-docker-compose` «не Initializr-стартер», по неверной логике «раз в имени артефакта нет `-starter-`, значит это core-модуль Boot, а не выбираемая в Initializr зависимость» — вывод по паттерну имени, без единой проверки. У Spring Initializr многие зависимости (Docker Compose Support, Lombok, Actuator и др.) не содержат `-starter-` в имени артефакта, наличие/отсутствие этого подслова в имени не говорит ничего о членстве в Initializr. Строка `developmentOnly 'org.springframework.boot:spring-boot-docker-compose'` при этом дословно уже присутствовала в `docs/spring-boot-starters-reference.md:178` — файл был не прочитан перед утверждением. Правило: любое утверждение вида «X не относится к Initializr»/«X не существует как стартер» — сначала grep по точной строке артефакта в `docs/spring-boot-starters-reference.md`, и только отсутствие там даёт право на такое утверждение (с оговоркой, что файл не абсолютно полон — см. соответствующий пункт правила выше)

- **Перед архитектурным ответом — контрольный список: стандартный паттерн / переформулировка / другой угол / альтернативы** (2026-08-08, обобщено по итогам диалога про единый контракт Controller/Service — см. «Открытые решения» → «Единый контракт Controller/Service/Repository при ResponseEntity-обёртке», где ассистент сначала трижды прошёлся по локальным вариациям (Object-хак / отказ от интерфейса / снятие ограничения), прежде чем распознать типовой случай): прежде чем предлагать вариант решения, явно проверять четыре вопроса, не бросаться к первому найденному через локальный код рецепту — (1) не является ли задача частным случаем известного стандартного паттерна (пример прецедента — «N классов с совпадающими по сигнатуре, имя+параметры, JLS, методами, различающихся типом возврата» → параметрический полиморфизм, как `Optional<T>`/`Comparator<T>`/`CrudRepository<T, ID>`); (2) можно ли переформулировать саму постановку задачи, не размывая заданных пользователем ограничений; (3) можно ли посмотреть на неё с другого угла — начинать рассуждение с абстрактной формы задачи, а не с того, что уже реализовано в репозитории как локальный прецедент; (4) есть ли альтернативные способы решения помимо первого пришедшего в голову. Решения, которые снимают заданное пользователем ограничение ради тривиальности (прецедент — предложение убрать `ResponseEntity` из Controller), предлагать можно, но явно помечая как «меняет постановку задачи», не выдавая за рекомендованный ответ на исходный вопрос. **Чек-лист проходить явно и видимо в самом ответе** (уточнено 2026-08-08, повторный запрос пользователя зафиксировать «способ размышления») — не как молчаливая внутренняя проверка перед выводом готового решения, а как показанные шаги рассуждения; при повторном применении к уже решённому вопросу — не просто повторять прежний вывод, а переискать его заново (пример — единый контракт Controller/Service передуман через рамку Adapter/GoF и уже принятую в проекте driving/driven-симметрию портов, а не просто повторно назван «параметрический полиморфизм»). **Свежий взгляд, не фиксация на уже предложенных вариантах** (уточнено 2026-08-08, третий подряд запрос пользователя зафиксировать способ размышления) — при создании решения смотреть на проблему заново, не ограничиваясь набором вариантов, уже прозвучавших в диалоге (A/B/C/D/F и т. п.) — этот набор не исчерпывающий по умолчанию, промежуточный список — не потолок для дальнейшего поиска
- **Запрещены заглушки как решение задачи** (2026-08-08) — заглушка (placeholder, TODO-затычка, урезанная версия «пока сойдёт») не решает проблему, а избегает её; решение всегда рабочее
- **Запрещён откат к более примитивному варианту ради простоты реализации** (2026-08-08) — если выбранное решение оказывается сложным в реализации, разбираться со сложностью, не понижать задним числом планку уже выбранного варианта — это тоже избегание проблемы, не решение
- **Если проблема возникла — у неё есть причина, и аналогичная возникнет снова** (2026-08-08) — решение должно закрывать причину, а не только конкретное проявление: искать и устранять тот же класс проблемы в остальных местах проекта, где действует та же причина, не ограничиваясь местом обнаружения (прецедент — единый контракт Controller/Service решён не только в `user-note`, где вопрос возник, но и в `note`/`user`, где действовал тот же `Object`-паттерн, см. `docs/decisions-log.md` → «Архитектура» → «Трёхуровневая иерархия портов: `Object`-ковариантность → generic-параметризация»)

- **Кольцевые/ромбовидные зависимости — ВСЕГДА избегать, без исключений, в любом месте проекта** (введено 2026-07-14, ужесточено 2026-07-15, **сделано абсолютным 2026-08-01**): при любой правке convention-плагинов, Gradle project-зависимостей (`projects.*`) или Java-иерархий портов/адаптеров — проверять граф на циклы и на схождение путей (диамант «вида 1» — определение см. в этом же пункте, «Два разных вида схождения — не путать») и устранять его, даже ценой дублирования кода — чистота/ясность/предсказуемость графа важнее объёма copy-paste. Это отменяет более раннюю формулировку «решение оставить/устранить — за пользователем»: пользователь дважды экспериментировал с осознанным принятием диаманта ради устранения дублирования (`spring-cloud-application` дважды — 2026-07-15 и 2026-08-01) и оба раза в итоге откатывал это решение обратно к нулю диамантов — правило зафиксировано на основе этого повторяющегося исхода, не отдельного случая. Сообщать о находке по-прежнему обязательно (что найдено, где), но действие по умолчанию теперь «устранить», а не «спросить». Прецедент устранения без дублирования, когда возможно: `spring-cloud-application` (диамант `spring-cloud`+`spring-boot-application`) устранён заменой на прямой `id("org.springframework.boot")`, так как `spring-boot-application` к тому моменту стал чистым alias без собственной нагрузки — 0 диамант, 0 дублирования. Прецедент устранения ценой дублирования: `spring-boot-actuator` — отдельный атомарный плагин, применяется явно `id(...)` на каждом из 37 bootable-листовых модулей (не встроен вторым родителем ни в `spring-boot-application`, ни в `spring-cloud-application`, хотя это устранило бы необходимость 37 явных `id(...)` ценой диаманта — отклонено). Никаких shared-функций/helper-кода в `build-logic/` для устранения подобных схождений — только композиция через `id(...)`. **Два разных вида схождения — не путать**: вид 1 — диамант внутри самого convention-плагина (файл в `build-logic/` сам в своём `plugins{}` вызывает 2+ `id("com.example.*")`, сходящихся в общем предке) — устранять всегда, без исключений. Вид 2 — листовой модуль (`build.gradle.kts` сервиса) напрямую применяет 2+ convention-плагина, сходящихся в общем предке (например `note/application-h2-jpa` — `spring-boot-application`+`spring-boot-database-h2`; `gateway/application` — `spring-cloud-application`+3 `spring-cloud-*`) — **не диамант для устранения**, а осознанная композиция независимых convention-плагинов в точке использования, ради которой вся система convention-плагинов и построена (решено пользователем 2026-07-15, не поднимать заново без нового явного повода)
- **Convention-плагины — всегда атомарны, один плагин = один концерн/технология** (закреплено как постоянное правило 2026-08-01, до этого — серия точечных решений, см. `docs/decisions-log.md` → «Атомизация базовых плагинов»): не объединять в одном плагине несколько независимых зависимостей/стартеров ради удобства, даже если они сегодня всегда применяются вместе (прецедент — вынос `spring-boot-starter-validation` из `spring-boot` в отдельный `spring-boot-validation`; воссоздание `spring-boot-actuator` из `spring-boot-application`). Если возможность применяется не везде одинаково или концептуально независима — отдельный плагин, композиция через явный `id(...)` в точке использования, не через объединение содержимого
- **Предпочитаем явную композицию неявному наследованию — во всём проекте, не только в convention-плагинах** (закреплено 2026-08-01, обобщает предыдущий пункт и правило про диаманты — все три работают вместе на один результат; область действия расширена пользователем в тот же день с Gradle-плагинов на весь проект целиком): когда модулю/классу/конфигурации нужны 2+ независимые возможности — явное объявление каждой рядом, в точке использования, а не одна возможность, встроенная родителем/зависимостью другой ради экономии строк. Действует одинаково в трёх плоскостях:
  - **Convention-плагины** (где правило впервые сформулировано) — явный `id(...)` для каждой возможности на листе, не встраивание через родителя. Даже если возможность нужна на 100% модулей, где применяется родитель, без единого исключения (как у `spring-boot-actuator`) — это не повод встраивать её через наследование. Отход от композиции — не ради компактности кода, а только когда явной альтернативы физически не существует (прецедент: `spring-boot-docker-compose` — `id("org.springframework.boot")` там не встраивание ради экономии, а техническая необходимость для typed-аксессора `developmentOnly`)
  - **Java-код** — предпочитать композицию наследованию классов везде, где выбор есть (внедрение зависимости/делегирование вместо `extends` ради переиспользования кода); интерфейсная иерархия портов (`{Entity}Interface`→`{Entity}ServiceInterface`/`{Entity}ControllerInterface`, см. «Именование») — контракт, не реализация, этого правила не касается
  - **Настройки/конфигурация** (Spring `application.properties`, профили и т. п.) — явные, отдельные свойства/файлы на концерн, не неявное наследование конфигурации через профили-предки или глубоко вложенные default-механизмы

  Естественное следствие для всех трёх — диамантов/скрытых схождений не возникает вообще, потому что диамант — всегда результат наследования от 2+ путей, а не композиции
- **`.gitattributes` — всегда точная копия шаблона Spring Initializr, ничего сверх неё** (закреплено 2026-08-01): `/gradlew text eol=lf`, `*.bat text eol=crlf`, `*.jar binary` — три строки, без `* text=auto` и любых других добавлений, даже если локальный `core.autocrlf=true` из-за этого выдаёт предупреждения `LF will be replaced by CRLF` при `git add` (сами предупреждения игнорировать — не повод отступать от стандартного шаблона; правильное место фикса — локальный `git config` конкретного контрибьютора, не общий для репозитория файл)
- **Только convention-плагины — листовые модули не применяют ничего напрямую** (проверено и закреплено 2026-07-15): ни один из 39 листовых `build.gradle.kts` (`note`/`user`/`user-note`/`auth`/`registry`/`config`/`gateway`) не должен применять plugin id, не начинающийся с `com.example.*`, и не должен объявлять зависимость иначе как `implementation(projects....)`/`api(projects....)` (project-to-project). Все внешние зависимости, плагины, версии и настройка сборки — только через `build-logic/convention/`. Проверка: `grep -rn 'id("' --include="build.gradle.kts" note user user-note auth registry config gateway | grep -v 'id("com\.example\.'` и аналогично по `dependencies{}`-блокам — оба должны быть пустыми. Прогонять эту проверку при добавлении новой зависимости/плагина в любой листовой модуль
- **После широкого `git checkout`/отката, затрагивающего convention-плагины — сверять число применений грепом, не только зелёный `clean check`** (2026-08-02, найдена и исправлена реальная регрессия — см. CLAUDE.md → «Задачи» → «Завершено 2026-08-02»): `id("com.example.spring-boot-actuator")` был случайно стёрт с 37 листовых модулей широким откатом диамант-эксперимента (`git checkout` затронул больше файлов, чем предполагалось), `./gradlew clean check` при этом оставался зелёным — отсутствие неиспользуемого стартера не ломает компиляцию, только полноту функциональности. После любого `git checkout <commit> -- <files>`/массового отката в `build-logic/` или в `plugins{}`-блоках листовых модулей — сверять `grep -rl 'id("com.example.{id}")' note user user-note auth registry config gateway | wc -l` для каждого затронутого плагина против чисел применений, заявленных в `docs/convention-plugins-graph.md`, не полагаться только на факт успешной сборки
- **Плагины-расширители (`java-library` и подобные) — только там, где реально нужна расширенная конфигурация, не каскадом «на всякий случай»** (введено 2026-07-15): прецедент — `com.example.jspecify` подключал `id("java-library")` только ради `api("org.jspecify")`, и через каскад `base → codequality → jspecify` эта конфигурация просачивалась во все 39 модулей, хотя видимость зависимости на потребителях от `api`/`implementation` не зависела (jspecify достаётся каждому модулю напрямую через собственный каскад `id(...)`, а не через project-to-project зависимость, где `api` реально что-то протаскивает дальше). Исправлено на `id("java")` + `implementation(...)`; `java-library` остался только в `com.example.java-library` (переименован из `com.example.library` 2026-08-01 — id совпадает с именем обёрнутого ядрового Gradle-плагина, см. `docs/decisions-log.md`), применяемом 6 модулями `contract`/`contract-reactive`, где `api(projects.*.domain)` — настоящая публичная сигнатура. При добавлении/правке convention-плагина, если он подключает id, расширяющий базовый (`java-library` поверх `java` и аналоги) — проверять: (1) нужна ли расширенная конфигурация именно этому плагину для собственной декларации зависимостей, или сводится к базовой; (2) не полагаться на то, что зависимость «протекает» api-путём к потребителям, если фактическая топология — каскадное применение `id(...)` внутри одного проекта, а не project-to-project. Проверка: `grep -rln 'id("java-library")'` по `build-logic/convention/` — список плагинов должен совпадать со списком, где реально объявлен `api(...)`
- **Build** — после каждого логического шага: `./gradlew clean check` (быстрее `build`: без `assemble`/`bootJar`) → обновить CLAUDE.md → коммит → пуш; перед коммитом дополнительно `./gradlew clean build` (проверяет и паковку — `bootJar`/`resolveMainClassName`, что `check` не покрывает)
- **⚠️ Sandboxed/remote-агент окружение может не уметь запустить сборку вообще** (2026-07-24, обнаружено при работе через Claude Code on the web; **частично решено** в тот же день, см. апдейт ниже): проект требует Java 25 (`.java-version`), но в некоторых remote execution environment физически установлена только JDK 21, а автозагрузка нужного тулчейна через Gradle toolchain resolver `foojay` (`api.foojay.io`) заблокирована сетевой политикой окружения (`CONNECT tunnel failed, 403` — так же падает и прямой `curl` на `api.foojay.io`/`start.spring.io`, не только Gradle). Дополнено — несколько осей профиля одновременно (`h2/mysql/postgres` + `dev/test/deploy`): подтверждено, Spring поддерживает несколько одновременно активных профилей через запятую (`spring.profiles.active=mysql,dev`), каждый отвечает за свою ось (вендор → datasource, окружение → всё остальное), конфликтующие ключи разрешаются по порядку — последний в списке побеждает; для частых комбинаций — profile groups (`spring.profiles.group.dev-mysql=mysql,dev`).

**Сверено с `docs.spring.io/spring-boot/reference/features/profiles.html`** — уточнения к описанному выше механизму профилей: `spring.profiles.include` добавляется ПЕРЕД `spring.profiles.active` (не просто «расширяет», а в начало списка — важно для порядка перекрытия свойств); `spring.profiles.active`/`-.include`/`-.group` нельзя объявлять внутри профиль-специфичного документа (`application-{profile}.properties` или блока `spring.config.activate.on-profile`) — только в «общем» документе; имя профиля по умолчанию валидируется — только буквы/цифры/`- _ . + @`, начало/конец — буква или цифра (`h2`/`mysql`/`postgresql`/`dev`/`test`/`deploy` без проблем, `spring.profiles.validate=false` снимает ограничение); `spring.profiles.default` — отдельное свойство для переименования дефолтного профиля.

**Как `clean build`/`clean check` соотносится с профилями** — Gradle не знает о Spring-профилях вообще, они резолвятся в рантайме `Environment`, до которого Gradle не добирается: `compileJava`/`bootJar`/`checkstyle` профиль не видят, паковка остаётся нейтральной (все 3 драйвера в jar независимо от профиля). Профиль участвует только в `test`-задаче, через тестовый код (`@ActiveProfiles`/`@ServiceConnection` на конкретном классе) — Gradle просто гоняет все такие классы как обычные JUnit-тесты при каждом `clean check`, без автоматического пропуска тяжёлых по умолчанию.

**Как проверить `clean build` для конкретного профиля** (сверено с `docs.gradle.org/current/userguide/java_testing.html`) — раз паковка от профиля не зависит, это на практике = `clean` + тесты, отфильтрованные/сконфигурированные на нужный профиль: разовый фильтр — `./gradlew clean test --tests "*.MySqlApplicationTests"`; именованная задача на профиль — кастомный `Test`-таск (`val mysqlTest by tasks.registering(Test::class) { useJUnitPlatform { includeTags("mysql") }; systemProperty("spring.profiles.active", "mysql") }`), не подключённый в `tasks.check` — не входит в дефолтный `clean check`/`clean build`, запускается только по имени. Тот же принцип, что вариант (в) из п. 3 выше, только для профиля, не для отдельного модуля.

**Решение по объёму тестовой матрицы** — достаточно тестировать по оси вендора (H2/MySQL/PostgreSQL + MongoDB/MongoDB-reactive — те же 5, что уже есть модулями), без комбинаторики с env-осью (`dev`/`test`/`deploy`) — окружение остаётся конфигурацией запуска, не предметом автотеста, там нет бизнес-логики для проверки.

**Как убедиться, что тест реально гоняется против MySQL/PostgreSQL, а не тихо откатился на H2-fallback** — через ассерт на метаданные реального соединения внутри самого теста, не через факт зелёного `contextLoads()` (он смолчит и на fallback тоже): JDBC/JPA — инжектировать `DataSource`, `connection.getMetaData().getDatabaseProductName()`/`getURL()`; R2DBC — инжектировать `ConnectionFactory`, `ConnectionFactoryMetadata.getName()`. Актуально именно для этих 6 модулей — `testRuntimeOnly("com.h2database:h2")`/`r2dbc-h2` уже подключены как embedded-fallback для голого `contextLoads()` (см. «Завершено 2026-08-18»), и пока на модуле нет `@ServiceConnection`, тест зелёный именно через H2, не через заявленный вендор — такой ассерт на каждом `{Vendor}ApplicationTests` (не на `H2ApplicationTests`) превращает потенциальный тихий откат в явный красный тест.

**Апдейт 2026-08-20, ещё позже (Gradle-«профили», попытка слить JDBC+JPA — отклонена по факт-проверке, project properties как реальный механизм)** — продолжение обсуждения выбора вендора/технологии; только консультация, ничего не реализовано.
- **Идея — разделить `id("com.example.spring-boot-database-{h2,mysql,postgresql}")` и выбирать через Gradle property внутри `plugins{}`** — не работает: сверено с `docs.gradle.org/current/userguide/plugins.html`, блок `plugins{}` декларативный, не читает `project.findProperty()`/`providers.gradleProperty()`, условная логика там не поддерживается в принципе (только `dependencies{}` и обычные task-блоки — обычный Kotlin-код)
- **Идея — тем же способом, что вендор, объединить JDBC+JPA в один модуль, выбор при `bootRun`** — отклонена как качественно другой случай, не масштабирование уже принятого решения по вендору: у вендора один и тот же Java-бин (JPA-репозиторий/маппер) просто подключается к разному `spring.datasource.url` — профиль меняет только конфигурацию, кода не касается. У JDBC/JPA — два физически разных бина (`com.example.note.data.jpa.adapter.NoteService`/`...data.jdbc.adapter.NoteService`), оба реализуют один и тот же порт; если оба одновременно на classpath — `NoUniqueBeanDefinitionException` без ручной разметки `@Profile` прямо в адаптерах, чего в проекте нет нигде (выбор технологии сегодня целиком решается Gradle-модулем/composition-root, не рантайм-условием внутри адаптера) — новый паттерн, не масштаб старого. Рекомендация — не сливать JDBC/JPA тем же способом, что вендор; граница «сливать то, что различается только конфигурацией, оставлять модулем то, что различается кодом» — по этому принципу нынешние 5 модулей (вендор внутри объединён, технология — нет) уже корректная граница
- **Альтернатива — условный выбор project()-зависимости через `dependencies{}` + `-P`** (`dependencies { when (providers.gradleProperty("dbTech")...) { "jpa" -> implementation(projects.userNote.persistence.dataJpa); ... } }`) — реально снимает bean-ambiguity (на classpath физически только одна реализация порта, `@Profile` на адаптерах не нужен), совместимо с действующим правилом «листовые модули — только `project()`-зависимости». Но цена: это выбор на этапе **сборки** (Gradle dependency resolution), не рантайма JVM — один и тот же `.jar` не переключается `--spring.profiles.active` в `java -jar`, для каждой комбинации нужна отдельная сборка с другим `-P`; и `clean check` из корня перестаёт тестировать все комбинации одной командой (один вызов = один `-P` = одна комбинация), в отличие от раздельных модулей, где корневой `check` агрегирует все subprojects автоматически бесплатно. Вывод: три желаемых свойства одновременно («не тащить лишнее в classpath» + «выбор при запуске одним артефактом» + «все комбинации одним `clean check`») ни один из разобранных механизмов не даёт разом — всегда приходится жертвовать одним из трёх
- **Официально подтверждено (`docs.gradle.org/current/userguide/build_environment.html`, `docs.spring.io/spring-boot/gradle-plugin/running.html`)** — Gradle-«профилей» как понятия не существует (сверено дважды, включая более раннюю сверку через blog.gradle.org/migrating_from_maven.html); вместо этого — **project properties**, 4 источника по приоритету (выше побеждает): `-P` в командной строке → `-D` с префиксом `org.gradle.project.` → `gradle.properties` в корне → переменная окружения `ORG_GRADLE_PROJECT_*` (последняя рекомендована для секретов в CI). Официально рекомендованный способ чтения — `providers.gradleProperty("name")` (Provider API, ленивый, совместим с configuration cache), не `project.findProperty()`. Для выбора Spring-профиля на `bootRun` — официально задокументированный способ вообще без Gradle-property: `./gradlew bootRun --args='--spring.profiles.active=mysql'` (`bootRun` — подкласс `JavaExec`, штатно поддерживает `--args`). Короткий алиас через `-P` возможен, но не обязателен — паттерн `tasks.named<BootRun>("bootRun") { systemProperty("spring.profiles.active", providers.gradleProperty("profile").getOrElse("default")) }`, тот же приём, что уже предлагался для отдельной `mysqlTest`-задачи (см. «Апдейт 2026-08-20» выше)
- **Итог**: Gradle project property и Spring-профиль — разные уровни, не конкурируют и не заменяют друг друга. Gradle-property (если используется) решает вопрос сборки — какие зависимости попадут в jar; Spring-профиль решает вопрос рантайма — что из уже упакованного активируется. Смешивать их для одной и той же оси (как в идее выше с JDBC/JPA через `-P`) возможно, но платит потерей «один артефакт, рантайм-переключение»

## Архитектура и структура проекта

**Многомодульная сборка (Gradle)** — схема: путь — назначение:
- `build-logic/settings.gradle.kts` — `include(":convention")`; included build, подключён через `pluginManagement { includeBuild(...) }` в корневом `settings.gradle.kts`
- `build-logic/convention/.../com.example.{name}.gradle.kts` — convention plugins (Kotlin DSL), namespaced id без суффикса `-conventions` (`com.example.spring-boot`, не `-conventions`); полный граф родитель→потомок всех 49 — см. `docs/convention-plugins-graph.md`
- `settings.gradle.kts` — единственный, в корне; `include(":...")` на все subprojects
- `{service}/{module}/build.gradle.kts` — применяет plugin через `id("com.example.{name}")`
- `{service}/{application,domain,persistence,presentation}/{module}/build.gradle.kts` — для `note`/`user`/`user-note` физическое расположение модуля вложено в подпапку по слою (2026-08-01, было плоско `{service}/{module}/`; см. «Именование» → «Группировка модулей по слою в подпапку» и «Открытые решения»/decisions-log за 2026-08-01). Gradle project path остаётся плоским (`:{service}:{module}`, без вложенности) — `settings.gradle.kts` переопределяет `project(":{service}:{module}").projectDir` на новый физический путь; typesafe accessors (`projects.note.domain`, `projects.userNote.dataJpa` и т. п.) не меняются

**Пакеты по сервисам** — путь — package:
- `note/` → `com.example.note`

Ровно один driven-адаптер и ровно один вендорный БД-драйвер на classpath каждого composition root — обе оси (технология адаптера, вендор БД для jpa/jdbc/r2dbc) выражены границей Gradle-модуля, не рантайм-профилем (пересмотр 2026-07-24 — было `spring.profiles.active`, см. `docs/decisions-log.md` → «Архитектура»: профиль выбирает bean в рантайме, но не убирает лишние драйверы из паковки). 11 composition-root модулей на сервис (9 реляционных + 2 Mongo, у Mongo вендорной оси нет) × 3 сервиса = 33. **⚠️ `user-note/` сознательно отступает от этого абзаца с 2026-08-19** (не WIP — см. «Задачи» → «Продолжение 2026-08-19», «Апдейт 2026-08-19, ещё позже») — вендорная ось для JDBC/JPA/R2DBC снова совмещена в одном модуле на технологию (3 драйвера на classpath, driver bloat принят сознательно как меньшее зло по сравнению со сложностью shared test-fixtures); не постоянное решение — пользователь допускает возврат к разделению по вендору специально ради driver bloat в будущем. `note`/`user` физически не тронуты (33-модульная структура сохраняется) — перенос этого выбора на них не вопрос для обсуждения, станет виден по факту правки пользователем.

Формат каждой строки: **элемент** — паттерн — пример.

Осознанно выбрано имя, пересекающееся с реальным `org.springframework.data.domain.Persistable<ID>` — не конфликтует (префикс сущности делает simple name другим), но напоминает: сам маркер в `domain/` остаётся чистым Java без зависимости на `spring-data-commons`, а НАСТОЯЩИЙ `Persistable<ID>` (если понадобится `isNew()`) реализуется отдельно в каждом адаптере — см. `docs/decisions-log.md` → «Архитектура»
- **Composition-root главный класс** (2026-07-23, расширено вендорным префиксом 2026-07-24, порядок частей имени/модуля перевёрнут на «вендор-технология» в тот же день) — `{Service}{Tech}Application` в `application-{tech}/` для Mongo (`NoteMongoApplication`, `NoteMongoReactiveApplication`); `{Service}{Vendor}{Tech}Application` в `application-{vendor}-{tech}/` для jpa/jdbc/r2dbc (`NoteH2JpaApplication`, `NoteMysqlJpaApplication`, `NotePostgresqlJpaApplication`, ...) — вендор всегда явный префикс перед технологией, без неявного «без префикса = H2» (см. `docs/decisions-log.md` → «Вендор БД — граница Gradle-модуля»). Тестовый класс — `...ApplicationTests` по тому же паттерну. До 2026-07-23 было 2 модуля на сервис (`application`/`application-reactive`) без Tech-суффикса

**Tech**: `Jpa` · `Mongo` · `Jdbc` · `R2dbc` · `MongoReactive` (в имени класса — только для `{Tech}MapperContract`/`{Tech}Mapper`/`{Tech}Repository`/`{Tech}Entity`; адаптеры и порт-интерфейсы суффикс технологии в имени не несут — технология различается пакетом/модулем)

**Vendor** (2026-07-24, только для composition-root класса/модуля jpa/jdbc/r2dbc, см. «Composition-root главный класс» выше): `H2` · `Mysql` · `Postgresql` — всегда префикс перед `{Tech}`, порядок `{Vendor}{Tech}` (`H2Jpa`, не `JpaH2`) — пересмотрено в тот же день: изначально был выбран порядок `{Tech}{Vendor}` («технология доступа архитектурно более фундаментальна»), затем перевёрнут по решению пользователя без изменения обоснования самой оси (вендор/технология остаются раздельными осями именования, поменялся только порядок отображения). **Вопрос снят как неактуальный 2026-08-19** — модуль `{Tech}-{Vendor}` физически перестал существовать (5 плоских модулей вместо 11 вложенных вендорных, см. «Задачи» → «Продолжение 2026-08-19» п. 2), сравнивать порядок `{Vendor}{Tech}` vs `{Tech}{Vendor}` больше не с чем; если вендорная ось модуля когда-нибудь вернётся — вопрос открыть заново, не считать прежнее наблюдение решением

**Группировка модулей по слою в подпапку** (2026-08-01, начато пользователем вручную в `user-note/` — `git mv` в новую вложенность, опечатка `pestistence` вместо `persistence`; агент исправил опечатку и применил ту же структуру симметрично к `note/`·`user/`): для всех трёх зрелых сервисов физический путь листового модуля — `{service}/{layer}/{module}/`, где `{layer}` ∈ `application`·`domain`·`persistence`·`presentation` (`domain/domain`, `domain/contract`, `domain/contract-reactive` — все три под `domain/`; `data-*` → `persistence/data-*`; `webmvc`/`webflux` → `presentation/{module}`; все `application-*` → `application/application-*`). Сам Gradle project path (и, следовательно, имя typesafe-accessor) не меняется — остаётся плоским `:{service}:{module}` — только физическая директория переопределена через `project(":{service}:{module}").projectDir` в `settings.gradle.kts` (см. «Архитектура и структура проекта» → «Многомодульная сборка»). Ранее аналогичный, но более узкий вопрос («каталог `data/` на уровне сервиса» — только для `data-*`) обсуждался и было решено оставить плоско (цена реорганизации выше пользы) — это решение пересмотрено данным изменением, которое к тому же шире исходного вопроса (охватывает все 4 слоя, не только `data-*`)

Матрица тестового покрытия — **частично закрыта 2026-07-24**: вариант (A) «отдельный класс на комбинацию» реализован ещё сильнее, чем обсуждалось — не просто явный тестовый класс на вендор внутри общего модуля, а отдельный composition-root модуль на комбинацию (`application-{h2,mysql,postgresql}-{jpa,jdbc,r2dbc}` + `application-mongodb`/`-mongodb-reactive` = 11 модулей/сервис × 3 = 33, см. `docs/decisions-log.md` → «Вендор БД — граница Gradle-модуля»), с ровно одним `*ApplicationTests`-классом на модуль. Вариант (B) (JUnit 5 `@ParameterizedTest`) снят с рассмотрения — противоречил бы уже принятому решению «вендор — граница модуля»; вариант (C) — мета-тест по типу ArchUnit, проверяющий «на каждый вендорный convention-плагин должен существовать application-модуль с соответствующим суффиксом» — остаётся актуальным, зависит от решения по пункту 1
- **Поведенческая аналогичность адаптеров/драйверов** (названо пользователем главной проблемой на пути к зрелости CRUD-модулей, 2026-07-24; **не реализовывать до отдельного запроса**) — нужно следить, что все реализации порта (`contract`/`contract-reactive`) по всей матрице технология×вендор ведут себя одинаково при одинаковом сценарии. Первая версия этого пункта была написана по предположению; ниже — находки после реального чтения кода `note/` (агентами, 2026-07-24; не перепроверялись отдельно для `user/`/`user-note/` — предполагается та же структура по декларируемой симметрии сервисов):
  1. **Порты вообще не специфицируют поведение** — `NoteInterface`/`NoteReactiveInterface` (методы возвращают голый `Object`, без `throws`/`Optional`/`@Nullable`), `NoteServiceInterface`/`NoteServiceReactiveInterface` (сужают тип через `@Override`, но так же без единой Javadoc-строки о поведении). `NoteNotFoundException` существует в `domain/`, но ни разу не упомянут ни в одном из 4 файлов порта — это соглашение адаптеров, а не часть контракта. **2026-08-18** — переосмыслено как осознанное разделение, не пробел: поведенческая спецификация сознательно живёт в тестах application-уровня, порт остаётся чисто структурным контрактом — см. «Задачи» → «Завершено 2026-08-18, ещё позже в тот же день (архитектура тестирования...)»
  2. **Обработка «не найдено» сегодня случайно одинакова во всех 5 адаптерах** (`orElseThrow(NoteNotFoundException)` / `switchIfEmpty(Mono.error(...))`) — но это не проверяется ни портом, ни тестом, значит не гарантировано против будущего дрейфа при правке одного адаптера
  3. **Реально найденные расхождения**: генерация ID тремя разными механизмами для одной и той же операции `add` (JPA — `@GeneratedValue(strategy = GenerationType.UUID)` на стороне приложения через Hibernate, JDBC/R2DBC — `DEFAULT RANDOM_UUID()` на стороне БД в `schema.sql`, MongoDB blocking/reactive — `UUID.randomUUID()` в мапере); duplicate-key нигде не транслируется (ни в одном из 5 адаптеров нет catch/translate для `DataIntegrityViolationException`/`DuplicateKeyException` — сценарий сегодня недостижим, нет unique-constraint кроме PK ни в одной схеме/документе, но это латентный риск: как только появится constraint, поведение разойдётся по технологиям, а `NoteExceptionHandler` в `webmvc`/`webflux` обрабатывает только `NoteNotFoundException` — необработанное упадёт в непрозрачный generic 500); внутренняя асимметрия MongoDB (blocking) — `add()` использует `mongoTemplate.insert(document)` напрямую, минуя `NoteMongoRepository`, тогда как find/delete идут через репозиторий, в отличие от остальных 4 адаптеров, использующих repository-абстракцию единообразно на всех операциях
  4. **Одинаковые (не расходящиеся) пробелы во всех 5** — `@Transactional` отсутствует везде (`merge()`/`replace()` делают read-then-write без атомарности одинаково во всех адаптерах); Bean Validation отсутствует везде (сам `spring-boot-starter-validation` теперь подключён точечно — см. «Задачи» → «Завершено 2026-08-01», но `@NotNull`/`@NotBlank` на model-классах по-прежнему не расставлены)
  5. **Referential integrity между `user-note/` и `user/`·`note/` не проверяется вообще (найдено 2026-07-24, при разборе `UserNoteService`)** — `create()` в `user-note/data-jpa/src/main/java/com/example/usernote/data/jpa/adapter/UserNoteService.java` сохраняет `UserNoteEntity` из запроса без проверки, что `userId`/`noteId` реально существуют в `user/`/`note/`: ни синхронного вызова порта, ни события, ни constraint на уровне БД (три сервиса физически разделены, разные вендоры/технологии на composition-root). Там, где проверка вообще есть (`findByUserId`/`findByNoteId`, бросающие `UserNotFoundException`/`NoteNotFoundException`), она обманчива: `existsByUserId(userId)` вызывает `userNoteJpaRepository.existsByUserId` — проверяет «есть ли уже связка в таблице `user_note`», а не «существует ли пользователь в `user/`»; `UserNotFoundException` там означает «у этого userId пока нет ни одной заметки», не «такого пользователя нет». Не перепроверено отдельно для остальных 4 технологий `user-note/` (jdbc/r2dbc/mongodb/mongodb-reactive) — по декларируемой симметрии кода предполагается тот же паттерн. Напрямую связано с открытым вопросом «Регистрация `auth/` ↔ `user/`» ниже — без выбранного механизма синхронизации между сервисами тот же класс проблемы («нет referential integrity через границу сервиса») встанет и там

  Кандидат-решение, не проработан: общий conformance test suite через `java-test-fixtures` — абстрактный JUnit-класс с тестами против интерфейса порта, параметризуемый в каждом `data-*`/composition-root модуле своим адаптером; компромисс — ещё один общий Gradle-модуль в топологии (тот же тип вопроса, что и в «Стоимость масштабирования composition-root матрицы» ниже), и требует заранее провести границу «что обязано совпадать» vs «что законно различается» (пример законного различия — bean-validation автотриггер: JPA триггерит через Hibernate pre-persist/pre-update, MongoDB не триггерит автоматически, R2DBC/JDBC — ни автотриггера, ни listener-механизма нет вообще), иначе тест либо слишком слабый, либо ломается на законных различиях
- **Стоимость масштабирования composition-root матрицы при добавлении нового адаптера/вендора** (наблюдение пользователя, 2026-07-24) — рост числа composition-root модулей мультипликативен: сервисы × технологии адаптера × вендоры БД (сейчас 3×11 = 33, см. «Архитектура и структура проекта» выше). Любая новая технология адаптера или новый вендор БД умножает число модулей, а не складывает. Два разных вопроса, не путать: (1) рост числа модулей — цена уже принятого решения «вендор — граница модуля» (один драйвер на `bootJar`), откат вернул бы driver bloat, который им и решали; (2) рост стоимости добавления модуля (дублирующийся boilerplate `build.gradle.kts`/`settings.gradle.kts`/main-класс на каждую новую комбинацию) — можно снижать без изменения топологии. Варианты не проработаны: (а) пересмотреть, обязательна ли полная 3×3-симметрия вендорной оси по всем технологиям/сервисам, или часть комбинаций избыточна и не нужна каждому сервису; (б) оценить реальный объём дублирующегося кода в 2–3 существующих composition-root модулях, прежде чем решать, стоит ли вообще что-то менять. Эмпирические цифры по времени сборки (не по коду) для этого пункта — см. «Правила» → «Build» → «`clean check` с реальным Docker — замер времени по вендорам» (2026-07-24: MySQL ~2× медленнее PostgreSQL/MongoDB на модуль, H2 без контейнера — 9–14s). Не реализовывать до отдельного запроса
- **Область подключения `spring-boot-starter-validation`** — решено 2026-08-01 (см. «Задачи» → «Завершено 2026-08-01» → атомарный `com.example.spring-boot-validation`, применяется только на `webmvc`/`webflux`/`data-jpa` × 3 сервиса). Остаточный пункт, отложен по прямому запросу пользователя (2026-08-01) — **не поднимать и не напоминать про него до отдельного запроса**: чтобы осмысленно подключить validation к `data-mongodb`/`data-mongodb-reactive`, сначала нужно написать и зарегистрировать `ValidatingMongoEventListener` (`org.springframework.data.mongodb.core.mapping.event`, требует явного bean `LocalValidatorFactoryBean` — Spring Boot не автоконфигурирует) — сам `spring-boot-starter-validation` без этого кода там ничего не даёт. У R2DBC/JDBC (Spring Data Relational) — ни автотриггера, ни штатного listener-механизма нет вообще, там подключать нечего
- **Порядок методов реализации = порядок объявления в интерфейсе** (п. 8 из 10 личных правил форматирования, остальные 9 реализованы, см. `docs/decisions-log.md` → «Стиль кода») — нужна семантическая привязка к реализуемому интерфейсу, синтаксическому Checkstyle не хватает резолвинга типов. Кандидаты: (1) кастомный Error Prone `BugChecker` (в проекте уже есть `net.ltgt.errorprone`); (2) JUnit-тест на `com.github.javaparser:javaparser-core` сравнивающий порядок методов интерфейс/реализация. Не реализовывать до отдельного запроса
- **Регистрация auth/ ↔ user/** — Lazy / Sync / Events (Kafka); та же проблема класса «нет referential integrity через границу сервиса» уже реально найдена между `user-note/` и `user/`·`note/` — см. «Открытые решения» → «Поведенческая аналогичность адаптеров/драйверов» → п. 5
- **Каталог `data/` на уровне сервиса** — ПЕРЕСМОТРЕНО 2026-08-01, см. «Именование» → «Группировка модулей по слою в подпапку»: реализовано шире исходного вопроса (не только `data-*` → `persistence/data-*`, но и `domain`/`application`/`presentation` — все 4 слоя) по инициативе пользователя. Ранее здесь была рекомендация оставить плоско — цена реорганизации (правка `settings.gradle.kts`) оказалась ниже, чем предполагалось: typesafe-accessors не меняют форму (Gradle project path остался плоским, изменена только физическая `projectDir`)
- **Возврат мутирующего use case** — DTO vs `void`
- **`@Transactional` на методах адаптера** — решение было зафиксировано, но не реализовано ни в одном адаптере ни одной технологии (обнаружено при пересмотре 2026-07-07). Решить: реализовать по всем адаптерам (~150 файлов) или снять как устаревшее (Spring Data репозитории и так транзакционны на уровне метода)
- **`user/`: `findByEmail`/`findByUsername` без HTTP-входа** — доведены до всех driven-адаптеров, не выведены в `webmvc`/`webflux`. Варианты: задел под будущий `auth/`, добавить контроллеры сейчас, или убрать как неиспользуемое
- **Javadoc в `package-info.java`** — ни один пакет не содержит package-level Javadoc, только `@NullMarked`; `checkstyle.xml` сейчас исключает javadoc-проверки — включение потребует такого комментария в каждом пакете
- **Composite build на границе сервисов** — каждый сервис мог бы подключаться через `includeBuild(...)` вместо `include(...)`. Ни один сервис не ссылается на модули другого, так что accessors не пострадали бы, но цена (7 новых `settings.gradle.kts`, ручная агрегация `build`/`check`/`clean`) больше выигрыша без текущего драйвера (независимое CI/версионирование, разъезд по репозиториям)
- **Инструмент миграции БД по адаптерам** (2026-07-15) — справочный обзор кандидатов (Flyway/Liquibase для data-jpa·data-jdbc, обход через blocking JDBC или Flamingock SQL target system для data-r2dbc, Mongock/Flamingock/liquibase-mongodb/Flyway Native Connectors для data-mongodb·data-mongodb-reactive, elasticsearch-evolution для data-elasticsearch) вынесен в `docs/db-migration-tools-reference.md`. Ключевая находка: **Mongock в maintenance mode, официальный EOL — конец 2026 года**, преемник — Flamingock (те же авторы, v1.4.4). Выбор конкретного инструмента не сделан — не реализовывать до отдельного запроса
- **Полная модель Google Docs (совместное редактирование)** (2026-07-23) — набросок требований (доменная модель Document/Revision/Permission/Comment, real-time слой поверх WebSocket/STOMP, OT/CRDT как нерешённое ядро сложности без готового решения в Spring-экосистеме, права доступа поверх Spring Security+OAuth2) вынесен в `docs/google-docs-full-model.md`.
