# notes-spring

Репозиторий показывает эволюцию одного приложения от классического монолита до распределённой конфигурируемой устойчивой системы. Цель — освоить технологии Spring и продемонстрировать владение ими работодателю, пройдя путь от уровня junior до senior и архитектора на стандартных инструментах, без экзотики.

Приложение одно на всех этапах: пользователи, заметки, доступ к заметке по ролям, уведомления с живой лентой через Server-Sent Events и полнотекстовый поиск заметок. Его функциональность и HTTP API задаются на первом этапе; на втором один раз меняется способ аутентификации (HTTP Basic → OAuth 2.0 / OpenID Connect), и дальше контракт не меняется — меняется только внутреннее устройство и инфраструктура вокруг него.

Прежняя попытка проекта сохранена в теге `legacy-2026-11`, её документация — в `docs/archive/` и используется только для справки.

## Этапы

Каждый этап — самостоятельное приложение в своём каталоге. Каталог назван по технологии, которая определяет этап и его архитектуру; если значимы сразу несколько технологий, этап делится на несколько этапов, по одному на технологию. По архитектуре или задаче называются только этапы, где изменение — архитектурный стиль или приём (`monolith`, `microservices`, `saga`, `autoscaling`, `hexagonal`). Подробное описание этапа — в его `README.md`, обоснование всей последовательности — в `docs/adr/0001-evolution-in-stages.md`.

### Как ведётся этап

Развитие итерационное, плавное и по возможности равномерное. Каждая веха — работающее приложение, отдельный проект и отдельный каталог; вех внутри каталога нет. Последовательность каталогов отражает сразу три линии: развитие самого проекта, освоение технологий и рост от уровня junior до senior и архитектора. Каждый этап можно освоить и довести до работающего результата без долгого перерыва; этап, который оказывается заметно крупнее соседних, делится на несколько этапов. Последние этапы требуют уже не новой технологии, а архитектурного решения на основе компромиссов и замеров.

Этапы делаются строго последовательно. Работа над этапом начинается с коммита, который копирует предыдущий каталог, после чего каждое изменение идёт отдельным коммитом — так разница между этапами читается в истории как пошаговый переход.

Каждый этап готов к развёртыванию, тестированию, эксплуатации и показу работодателю и при этом прагматично отражает очередной шаг в навыках и стеке технологий — не больше, чем нужно для этого шага. Этап считается готовым, когда вся система поднимается одной командой, приёмочные тесты и тесты этапа проходят, `README.md` заполнен, а ключевые решения записаны в ADR. Готовый этап замораживается: в нём исправляются только ошибки и уязвимости, зависимости обновляет Dependabot.

Каждый этап — самостоятельная сборка Gradle со своими `settings.gradle.kts` и wrapper; корневой сборки и общего `build-logic` нет. CI устроен так же: конвейер на этап, запускаемый только изменениями в каталоге этапа. GitHub Actions используется на всех этапах; с `06` рядом с ним равноправный Jenkins, с `07` — GitLab CI, все с теми же шагами: они вызывают одни и те же задачи Gradle, поэтому логика сборки не дублируется. С `08` все конвейеры проходят проверку качества SonarQube, с `24` развёртывание в кластер выполняет Argo CD.

Этапы `01`–`21` запускаются через Docker Compose, с `22` — в Kubernetes (k3s), локально и в CI. Каждый этап рассчитан на развёртывание в AWS: Compose-файлы, шаг развёртывания в конвейерах и, с `05`, Terraform готовы, но шаг развёртывания написан и выключен. Его включают, когда начинается поиск работы: живая ссылка на работающую систему ценнее ссылки на код.

### Приёмочные тесты

Каталог `acceptance-tests/` содержит один набор тестов «чёрного ящика» для всех этапов; браузерный интерфейс с `03` он не проверяет — это делают тесты страниц внутри этапа. Он обращается к запущенной системе только по HTTP и доказывает, что поведение, заданное в `01`, не меняется; со `02` меняется только способ аутентификации. Набор не знает технологий реализации: ни фреймворка, ни хранилищ, ни брокера, ни продукта сервера авторизации, ни устройства системы, ни номера этапа. Он знает только адрес системы, учётные данные тестового пользователя, а для защищённой токенами системы — адрес издателя токенов, и публичный API (HTTP, JSON, SSE, OAuth 2.0 / OIDC). Данные создаются и проверяются только через API, асинхронное поведение — ожиданием результата через API. Тесты внутри этапа (модульные, срезы, интеграционные) остаются в этапе и проверяют его технологии. Подробности — `acceptance-tests/README.md`.

## Приоритеты решений

Технические решения принимаются в таком порядке приоритетов:

1. **Автоконфигурация Spring Boot.** Используются стандартные стартеры и свойства. Собственная конфигурация бинов допустима только тогда, когда без неё задача не решается, и причина называется явно.
2. **KISS и DRY.** Если принципы конфликтуют, выбирается вариант, который не ломает автоконфигурацию и при этом избегает дублирования. Если автоконфигурацию сохраняют оба варианта, выбирается более простой.
3. **Стандартные инструменты.** Предпочтение отдаётся тому, что встречается в типовом проекте на Spring.

План покрывает технологии, которые почти всегда требуют в вакансиях Java/Spring. Набор технологий выбирается прагматично, но проект остаётся готовым к альтернативному выбору. Технология подключается через стандартную абстракцию или протокол, если они есть, — Spring Data, Spring Cache, вынос событий Spring Modulith, Micrometer, OpenTelemetry, OAuth 2.0 / OpenID Connect, — поэтому замена на альтернативу (RabbitMQ вместо Kafka, Keycloak вместо `auth-server`, другой поставщик мониторинга) сводится к смене зависимости и настроек, а не к переписыванию кода. Рассмотренные и не включённые технологии с причинами перечислены в ADR 0001.

Копирование кода между этапами — сознательное исключение из DRY: каждый каталог — снимок своего этапа. Внутри этапа DRY действует в полной мере.

Стандарты (RFC, спецификации, документация docs.spring.io) важнее туториалов и важнее предложения пользователя; отступление от стандарта допускается только с названной причиной. Архитектурные решения принимает пользователь: ассистент описывает варианты и даёт рекомендацию.

Факты о Spring — существование стартера, его имя, версия — проверяются по Spring Initializr, docs.spring.io и GitHub spring-projects при старте этапа, а не по памяти и не поиском Maven Central, индекс которого отстаёт.

## Документация

Документация пишется для читателя: связным понятным языком, разделами с вводным текстом, без хроники обсуждения, цитат и пометок «по указанию пользователя». Она фиксирует итог решения и его причину.

Между коммитами существующие записи только правятся на месте, новые записи рядом не добавляются; новая запись появляется только после коммита. Пока нет работающего кода (MVP этапа `01`), решения вносятся в существующие записи и после коммита — план ещё формируется. Для ADR это означает: решение, принятое после последнего коммита, вносится в уже существующую запись, а новая запись ADR создаётся только для решения, принятого после коммита. ADR лежат в `docs/adr/`, по одному решению в файле `NNNN-title.md`.

Общение с пользователем ведётся на русском. Код, настройки, публичные `README.md` и ADR пишутся на английском.

## Код и сборка

Сборка и тесты проходят без ошибок и предупреждений. Отступ — 4 пробела. Промежуточные результаты кладутся в локальные переменные с понятными именами вместо вложенных вызовов. Аббревиатуры в идентификаторах пишутся заглавными буквами, кроме `Id`.

Коммит и пуш выполняются только по явному требованию пользователя; просьбы «делай», «внеси», «поехали» требованием коммита не являются. Команда «Зафиксируй» означает: синхронизировать документацию, сделать коммит и пуш. Дата в документации берётся из команды `date`.
