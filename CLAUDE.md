## Правила

- **Голый API-стартер не подключается, если есть обёртка (Spring Data и т. п.) для той же технологии — даже если технически обёртка не несёт 100% функционала голого стартера** (2026-08-15, явное решение пользователя, отменяет собственную рекомендацию агента по итогам факт-проверки) — прецедент: `spring-boot-starter-elasticsearch` подключён рядом с `spring-boot-starter-data-elasticsearch` (несёт реальный `elasticsearch-java`-драйвер, которого `data-elasticsearch` транзитивно не тянет, проверено и POM, и Gradle Module Metadata) — пользователь всё равно убрал голый стартер вручную и явно сформулировал общее правило: «не используем голый API при наличии обёртки». Риск (Spring Data Elasticsearch без реального клиента может не заработать в рантайме) осознан пользователем — «проверить при реальном обращении», не превентивным подключением про запас. Это отменяет более узкое обоснование из записи 2026-08-15 «пересматривает правило... но избыточность, доказанную фактами, применять не мешает» — теперь правило шире факта транзитивности: голый API не нужен как класс решений, независимо от того, доказана ли конкретная избыточность фактами по каждой технологии отдельно
- **⚠️ ИСТОЧНИК ИСТИНЫ ДЛЯ SPRING-ФАКТОВ — НЕ MAVEN CENTRAL ПОИСК** [НЕ СОКРАЩАТЬ/НЕ УДАЛЯТЬ — исключение из правила «убирать избыточность», даже при явной задаче уменьшить объём CLAUDE.md] (2026-07-14, резкая реакция пользователя на ошибку): вопрос «существует ли артефакт X» **никогда** не проверять через `search.maven.org` (Solr-индекс отстаёт от реального репозитория, `0 numFound` НЕ значит «не существует» — конкретная ошибка: заявил, что `spring-boot-starter-r2dbc` не существует по 0 результатам поиска, хотя это реальный отдельный от `data-r2dbc` стартер). Источник истины — **Spring Initializr** (`start.spring.io/metadata/client` — реальный список id/name/description), **GitHub spring-projects**, **официальная документация docs.spring.io**. Maven Central годится только для номера версии уже известного, существующего артефакта — не для вопроса о самом его существовании. **`docs/spring-boot-starters-reference.md`** (2026-07-14) — дословная копия со Spring Initializr, лежит в репозитории локально: для вопроса «существует ли стартер X» и «как называется» обращаться сначала туда, не в web-поиск. При выборе/добавлении стартера под конкретную технологию — сверяться по этому файлу, есть ли для неё отдельный `-test`-компаньон (`spring-boot-starter-{tech}-test`), и подключать его вместе с основным, если существует — не пропускать по своему усмотрению (см. прецедент с `spring-boot-starter-r2dbc`/`-jdbc`/`-elasticsearch`, где `-test`-версия изначально была упущена). Также перед добавлением зависимости в Spring Boot модуль — сверяться, нет ли для этой технологии уже готового `spring-boot-starter-*`: если есть, подключать именно его, а не «сырую» внешнюю зависимость напрямую (starter уже несёт нужный BOM-managed набор транзитивных зависимостей и autoconfiguration — обходить его напрямую значит терять то и другое). **Принадлежность к Initializr — определять только буквальным поиском строки артефакта в `docs/spring-boot-starters-reference.md`, никогда рассуждением по форме имени артефакта** (2026-08-02, резкая реакция пользователя на ошибку): конкретная ошибка — заявил, что `org.springframework.boot:spring-boot-docker-compose` «не Initializr-стартер», по неверной логике «раз в имени артефакта нет `-starter-`, значит это core-модуль Boot, а не выбираемая в Initializr зависимость» — вывод по паттерну имени, без единой проверки. У Spring Initializr многие зависимости (Docker Compose Support, Lombok, Actuator и др.) не содержат `-starter-` в имени артефакта, наличие/отсутствие этого подслова в имени не говорит ничего о членстве в Initializr. Строка `developmentOnly 'org.springframework.boot:spring-boot-docker-compose'` при этом дословно уже присутствовала в `docs/spring-boot-starters-reference.md:178` — файл был не прочитан перед утверждением. Правило: любое утверждение вида «X не относится к Initializr»/«X не существует как стартер» — сначала grep по точной строке артефакта в `docs/spring-boot-starters-reference.md`, и только отсутствие там даёт право на такое утверждение (с оговоркой, что файл не абсолютно полон — см. соответствующий пункт правила выше)

Решения, снимающие заданное ограничение ради тривиальности (пример — убрать `ResponseEntity` из Controller), предлагать можно, но явно помечая «меняет постановку задачи», не как рекомендованный ответ. **Чек-лист проходить явно и видимо в самом ответе** (уточнено 2026-08-08 и 2026-08-21 — резкая реакция на буквальные ярлыки-вопросы вида «Стандартный паттерн? Да —») — не молчаливая внутренняя проверка, а показанные шаги рассуждения обычной связной прозой, без ярлыков/риторических заголовков на каждый пункт — чек-лист держится в голове, в тексте виден только результат естественным языком; при повторном применении к уже решённому вопросу — переискать заново, не просто повторить вывод (пример — контракт Controller/Service передуман через рамку Adapter/GoF и driving/driven-симметрию портов, не просто снова назван «параметрический полиморфизм»). **Свежий взгляд, не фиксация на уже предложенных вариантах** — набор вариантов, уже прозвучавших в диалоге, не исчерпывающий по умолчанию, не потолок для дальнейшего поиска

Отменяет более раннюю формулировку «решение за пользователем»: пользователь дважды осознанно принимал диамант ради устранения дублирования (`spring-cloud-application`, 2026-07-15 и 2026-08-01) и оба раза откатывал обратно к нулю диамантов — правило зафиксировано по этому повторяющемуся исходу. Прецедент устранения без дублирования: `spring-cloud-application` (диамант `spring-cloud`+`spring-boot-application`) устранён прямым `id("org.springframework.boot")`, т. к. `spring-boot-application` стал чистым alias — 0 диамант, 0 дублирования. Прецедент устранения ценой дублирования: `spring-boot-actuator` — атомарный плагин, явный `id(...)` на каждом из 37 bootable-листьев (не встроен вторым родителем в `spring-boot-application`/`spring-cloud-application`, хотя это устранило бы 37 явных `id(...)` ценой диаманта — отклонено). Никаких shared-функций в `build-logic/` для устранения схождений — только композиция через `id(...)`. **Два вида схождения**: вид 1 — диамант внутри самого convention-плагина (файл в `build-logic/` в своём `plugins{}` вызывает 2+ `id("com.example.*")`, сходящихся в общем предке) — устранять всегда. Вид 2 — лист (`build.gradle.kts` сервиса) применяет 2+ плагина, сходящихся в общем предке (`note/application-h2-jpa` — `spring-boot-application`+`spring-boot-database-h2`; `gateway/application` — `spring-cloud-application`+3 `spring-cloud-*`) — не диамант для устранения, осознанная композиция независимых плагинов в точке использования, ради которой вся система построена (решено 2026-07-15, не поднимать заново без нового повода)
- **Дублирование в коде — стремится к абсолютному нулю, в существующем и будущем коде** (2026-09-06, принцип «принудительное следование спецификации», распространённый с тестов на дублирование кода в целом) — не буквальный ноль (часть повторов навязана фреймворком/архитектурой — прецеденты `UserNoteTestApplication.java`/`build.gradle.kts`, см. «Задачи» → «Активная нить» → «2026-09-06»), а ноль НЕОБЪЯСНЁННОГО дублирования: найденное либо устраняется (перенос в общий модуль/testFixtures), либо явно помечается как оправданное (suppression), не остаётся незамеченным молча. Механизм для будущего кода — build-level детектор копипаста (кандидат PMD CPD, см. «Открытые решения» → «Устранение дублирования кода»), той же природы, что Checkstyle/Spotless/JaCoCo; для существующего — периодический аудит по образцу разбора `application-*` 2026-09-06
- **Convention-плагины — всегда атомарны, один плагин = один концерн/технология** (закреплено как постоянное правило 2026-08-01, до этого — серия точечных решений, см. `docs/decisions-log.md` → «Атомизация базовых плагинов»): не объединять в одном плагине несколько независимых зависимостей/стартеров ради удобства, даже если они сегодня всегда применяются вместе (прецедент — вынос `spring-boot-starter-validation` из `spring-boot` в отдельный `spring-boot-validation`; воссоздание `spring-boot-actuator` из `spring-boot-application`). Если возможность применяется не везде одинаково или концептуально независима — отдельный плагин, композиция через явный `id(...)` в точке использования, не через объединение содержимого
- **Предпочитаем явную композицию неявному наследованию — во всём проекте, не только в convention-плагинах** (закреплено 2026-08-01, обобщает предыдущий пункт и правило про диаманты — все три работают вместе на один результат; область действия расширена пользователем в тот же день с Gradle-плагинов на весь проект целиком): когда модулю/классу/конфигурации нужны 2+ независимые возможности — явное объявление каждой рядом, в точке использования, а не одна возможность, встроенная родителем/зависимостью другой ради экономии строк. Действует одинаково в трёх плоскостях:
  - **Convention-плагины** (где правило впервые сформулировано) — явный `id(...)` для каждой возможности на листе, не встраивание через родителя. Даже если возможность нужна на 100% модулей, где применяется родитель, без единого исключения (как у `spring-boot-actuator`) — это не повод встраивать её через наследование. Отход от композиции — не ради компактности кода, а только когда явной альтернативы физически не существует (прецедент: `spring-boot-docker-compose` — `id("org.springframework.boot")` там не встраивание ради экономии, а техническая необходимость для typed-аксессора `developmentOnly`)
  - **Java-код** — предпочитать композицию наследованию классов везде, где выбор есть (внедрение зависимости/делегирование вместо `extends` ради переиспользования кода); интерфейсная иерархия портов (`{Entity}Interface`→`{Entity}ServiceInterface`/`{Entity}ControllerInterface`, см. «Именование») — контракт, не реализация, этого правила не касается
  - **Настройки/конфигурация** (Spring `application.properties`, профили и т. п.) — явные, отдельные свойства/файлы на концерн, не неявное наследование конфигурации через профили-предки или глубоко вложенные default-механизмы

  Естественное следствие для всех трёх — диамантов/скрытых схождений не возникает вообще, потому что диамант — всегда результат наследования от 2+ путей, а не композиции
- **`.gitattributes` — всегда точная копия шаблона Spring Initializr, ничего сверх неё** (закреплено 2026-08-01): `/gradlew text eol=lf`, `*.bat text eol=crlf`, `*.jar binary` — три строки, без `* text=auto` и любых других добавлений, даже если локальный `core.autocrlf=true` из-за этого выдаёт предупреждения `LF will be replaced by CRLF` при `git add` (сами предупреждения игнорировать — не повод отступать от стандартного шаблона; правильное место фикса — локальный `git config` конкретного контрибьютора, не общий для репозитория файл)

Все внешние зависимости, плагины, версии и настройка сборки — только через `build-logic/convention/`. Проверка (список сервисов сузился до `user-note` — `note`/`user`/`auth`/`registry`/`config`/`gateway` удалены из репозитория, см. «Задачи» → «Статус по сервисам»; вернуть остальные в список, если сервисы вернутся): `grep -rn 'id("' --include="build.gradle.kts" user-note | grep -v 'id("com\.example\.'` и аналогично по `dependencies{}`-блокам — оба должны быть пустыми. - **После широкого `git checkout`/отката, затрагивающего convention-плагины — сверять число применений грепом, не только зелёный `clean check`** (2026-08-02, найдена и исправлена реальная регрессия — см. - **Плагины-расширители (`java-library` и подобные) — только там, где реально нужна расширенная конфигурация, не каскадом «на всякий случай»** (введено 2026-07-15): прецедент — `com.example.jspecify` подключал `id("java-library")` только ради `api("org.jspecify")`, и через каскад `base → codequality → jspecify` эта конфигурация просачивалась во все 39 модулей, хотя видимость зависимости на потребителях от `api`/`implementation` не зависела (jspecify достаётся каждому модулю напрямую через собственный каскад `id(...)`, а не через project-to-project зависимость, где `api` реально что-то протаскивает дальше). **Целевая картина (согласована 2026-08-31, вечер; порядок работы уточнён 2026-09-04) — сверху вниз:**
1. `user-note` — одно приложение с одним поведением. Описывается один раз (максимум два: sync/reactive — и только из-за конфликта webmvc/webflux на classpath). Всё остальное — сменная реализация. **Уточнение 2026-09-04**: граница sync/reactive (как и вендорная граница) — чисто техническая, вынужденная сборкой (`WebApplicationType.deduceFromClasspath()`, driver bloat), не поведенческая — для потребителя API (и для порт-теста через `WebTestClient`/`TestRestTemplate` на реальном порту, см. п.1 ниже) разницы нет вообще, контракт один. Та же логика, что уже привела к «HTTP-контракт один на все 5 модулей» — распространяется и на смысл самого разделения sync/reactive: оно существует ради компилятора/classpath, не ради разного поведения.
2. Абстракция = порт (`UserNoteInterface`/`…Reactive`) + `application-core`(`-reactive`) (общий `@SpringBootApplication` + тест поведения на порт в `testFixtures`) + convention-плагин `com.example.user-note-application`(`-reactive`) — **возникает по ходу TDD, не выносится заранее** (пересмотрено 2026-09-04, см. выше).
3. Конкретные composition-root различаются **ТОЛЬКО составом classpath**. Каждый `application-X` = «плагин абстракции + плагин адаптера», ни своей Java, ни своего теста — это целевое состояние ПОСЛЕ TDD, не стартовая точка.
4. Ось адаптеров = SQL vs non-SQL. SQL: один адаптер на модель доступа (`jdbc`/`jpa`/`r2dbc`) покрывает все SQL-вендоры, вендор = профиль. Non-SQL (Cassandra/Couchbase/Neo4j/Elasticsearch/DynamoDB/Redis/Mongo/in-memory): каждый вендор — свой адаптер и свой модуль. sync/reactive удваивает каждый, где драйвер позволяет.
5. Тесты — та же архитектура, что код: один тест на порт, параметризован, гоняется против каждой реализации; реализация удовлетворяет тест, тест не зависит от реализации. **Два уровня, не один** (уточнено 2026-09-04, см. п.1 ниже): тест на порт (service+persistence, без HTTP) и E2E-тест через HTTP (тоже кандидат на shared testFixtures — HTTP-контракт не должен зависеть от технологии персистенции). **Почему один и тот же тест на N реализаций — доказательство «разницы нет для конечного пользователя», а не просто совпадение** (обсуждено 2026-09-04): рассмотрена и отклонена альтернатива — differential testing (гонять одну последовательность операций против пары реализаций и сверять вывод байт-в-байт, без явных assert-ов; так тестируют компиляторы, где оракул писать дорого). Отклонено для этого домена: (1) CRUD-сущность — оракул пишется руками легко, не тот случай; (2) differential ловит только **расхождение** между реализациями — общий баг, одинаковый во всех пяти (например в самом контракте порта), differential не найдёт, а explicit-assert найдёт, если он нарушает спецификацию; (3) N-парных сравнений растёт комбинаторно с числом модулей, один прогон общего теста — линейно. Единственная реальная дыра conformance-подхода — ловит только то, что явно assert-ит автор теста (неучтённое расхождение вроде порядка полей JSON/формата таймстампа может остаться незамеченным) — принята как цена, оправданная простотой домена; differential остаётся кандидатом на будущее, если домен усложнится (не сейчас).
6. Это корневая идея проекта, рекурсивно: hexagonal в коде + convention-плагины на уровне системы — и та же связка абстракция/реализация/DIP на слое composition-root.
7. Порядок работы (пересмотрено 2026-09-04): (1) TDD против порта, код по слоям вниз, абстракция появляется по ходу → (2) compose для dev runtime.

1. **Полный TDD против порта — тест написан НА АБСТРАКЦИИ, не на реализации, порт и абстракция выводятся ПО ХОДУ, не заранее** (объединяет прежние п.0+п.1, пересмотрено 2026-09-04) — тест поведения **один**, зависит **только от `UserNoteInterface` / `UserNoteReactiveInterface`** (не от `DataSource`/`MongoTemplate`), параметризован технологией и вендором (`@ParameterizedTest`/`@ActiveProfiles` по профилям), гоняется против каждого из 5 модулей. Конкретный адаптер модуля удовлетворяет контракт абстракции — реализация подставляется под тест, не наоборот. `getDatabaseProductName()`/`buildInfo`-ассерты и любые `abstract`-пробы удаляются — это связанность абстракции с реализацией. **К тестам — те же паттерны проектирования и та же архитектура, что к коду приложения** (принципиальное требование пользователя, не деталь оформления). sociable/classicist-стиль, реальный Spring-контекст, Testcontainers (принцип — «Завершено» → «2026-08-18, архитектура тестирования»). От тестов — реальный доменный/persistence/presentation код (нижние слои, идём вниз).
   - **Два уровня теста, оба на composition-root, оба — кандидаты на shared testFixtures** (обсуждено 2026-09-04): (а) **тест на порт** — `@Autowired UserNoteInterface`, проверяет service+persistence, минуя контроллер; (б) **E2E-тест через HTTP** — отдельный, не то же самое, ловит то, что порт-тест не видит (маппинг JSON, `@Valid`, `NoteExceptionHandler`→`ProblemDetail`, HTTP-статусы). Рекомендация по механике E2E: `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate` (webmvc) / `WebTestClient` (webflux) на реальном порту — **не** `@AutoConfigureMockMvc`/`@AutoConfigureWebTestClient`-in-container (тот не гоняет через реальный сокет, тот же компромисс, что и мок, только тоньше — противоречит уже принятому sociable/classicist-принципу). Оба уровня — максимум 2 варианта каждый (sync/reactive), как и порт-тест — не отдельная новая абстракционная задача, тот же `application-core`.
   - **Уточнение того же вечера — E2E не удваивается на sync/reactive, порт-тест удваивается** (пользователь поймал ошибку в исходной рекомендации). Порт-тест — максимум 2 варианта, механически неустранимо: `UserNoteInterface.add(...)` возвращает `UserNote`, `UserNoteReactiveInterface.add(...)` — `Mono<UserNote>`, разные Java-типы, один тестовый метод не годится для обоих без блокирующего/реактивного моста (убивает смысл теста реактивного пути). E2E/HTTP-тест — **один**, не два: при `@SpringBootTest(webEnvironment = RANDOM_PORT)` и `WebTestClient.bindToServer().baseUrl("http://localhost:"+port)` (или `TestRestTemplate`) клиент работает поверх реального сокета через HTTP — ему не важно, blocking или reactive сервер на другом конце, это чистый протокол. Различие sync/reactive у тест-клиента существует только в in-container-режиме (`@AutoConfigureMockMvc`↔`DispatcherServlet`, `@AutoConfigureWebTestClient`↔`WebHandler` напрямую, без сокета) — который уже отвергнут выше в пользу настоящего HTTP. Итог: HTTP-контракт (JSON/статусы) один на все 5 модулей, один E2E-тест-класс их все покрывает.
   - **Форма самого теста — один сценарный метод («flow»), не россыпь независимых assert-ов** (обсуждено 2026-09-04, вопрос пользователя «как протестировать, что у пользователя один user flow вне зависимости от технологии» — про форму теста, не про механику расшаривания, изначально понято неверно). «Один user flow» доказывается не тем, что пять реализаций проходят похожие, но раздельные `@Test`-методы (`addThenFindByIdReturnsSameUserNote()`, `removeThenExistsByIdReturnsFalse()` и т. п. по отдельности) — а тем, что это буквально **один сценарный метод** (условно `userManagesTheirNoteEndToEnd()`), описывающий реальную последовательность действий пользователя (создал → прочитал → изменил → удалил → убедился, что удалено) целиком в одном потоке, лежащий в `testFixtures`, прогоняемый целиком против каждого из 5 модулей. Сам факт «это один метод, не пять» и делает идею «один flow» видимой в коде теста, а не только в механизме его расшаривания (testFixtures byte-identical class — гарантия, что тест не разъедется, но не про форму самого сценария).
   - **Организация проверки API при нескольких composition root** (обсуждено 2026-09-04, вопрос пользователя «как организовать проверку API при наличии нескольких composition root» — финальная точка длинного разбора, начатого с «один API, одни результаты», прошедшего через мехнику testFixtures/форму теста/black-box). У проекта нет одного работающего приложения с переключаемой начинкой — 5 отдельных composition root, 5 отдельных `main()`, 5 независимо собранных графов объектов. «Один API» — не факт про единый процесс, а контракт, который каждый composition root обязан реализовать по отдельности; доказывается не одним прогоном, а N прогонами одного и того же теста без изменений. Конкретная организация:
     - Тест физически лежит в `application-core`/`testFixtures` (порт-тест на `UserNoteInterface`) и `application-core-reactive`/`testFixtures` (на `UserNoteReactiveInterface`) — **2 копии, не 5**, по числу типов порта, не по числу composition root
     - Каждый из 5 `application-X/build.gradle.kts` подхватывает нужный набор не копированием, а зависимостью — convention-плагин `com.example.user-note-application`(`-reactive`) сам тянет `testImplementation(testFixtures(project(":user-note:application-core"[-reactive])))`; лист выбирает только, какой convention-плагин применить (sync/reactive), тест наследуется автоматически
     - Прогон по всем N сразу — уже существующий `./gradlew clean check --continue` из корня: Gradle сам находит все `include(...)`-модули `settings.gradle.kts` и гоняет их `test`-таски независимо; ничего специального «раннера по composition root» писать не нужно, это прямое следствие уже выбранной multi-module-структуры. `--continue` обязателен именно здесь — без него сборка остановится на первом расхождении, не покажет, разошёлся один composition root или несколько
     - E2E-тест (технологически-агностичен, см. `WebTestClient`/`RANDOM_PORT` выше) не обязан жить в 2 местах как порт-тест — либо маленькая общая fixtures-зависимость на оба `-core`, либо 2 копии одного маленького сценарного класса (цена дублирования мала, отдельный третий shared-модуль ради одного класса не оправдан)
   - Механику расшаривания тестов (testFixtures + convention-плагин / test-jar) выбрать по ходу, когда появится реальный контент для расшаривания — не заранее.

### Активная нить: переписывание `user-note/application/` (хронология, новое сверху)

- **2026-09-06, философский разбор дня — «принудительное следование спецификации» доведено до практического предела; итоговый 5-слойный стек + аудит дублирования `application-*`** — сжатая хронология длинного диалога (полная цепочка рассуждений не расписана — суть сохранена): вопрос «в чём смысл ООП/SOLID, если нельзя написать один принудительный тест на абстракцию» разобран через формальное определение LSP (Barbara Liskov — подтип заменяем без изменения желательных свойств; единственный практический способ ПРОВЕРИТЬ это — прогнать одинаковый тест над всеми реализациями, то есть «один тест, обязательный для каждой» — операциональный смысл LSP, не надстройка над ним; необычна не идея — индустриальный стандарт TCK/Testcase Superclass, см. запись 2026-09-05 ниже — а требование её ПОЛНОЙ механической принудительности вместо конвенционной/сертификационной, как у реальных TCK, материализовавшееся здесь из-за сознательного архитектурного выбора — 5 реальных взаимозаменяемых composition-root реализаций разом, не 1+моки). Кажущееся противоречие «порт не знает адаптеров» vs «где-то нужно знание ВСЕХ адаптеров, чтобы принудить исполнение» разрешено введением третьей, отдельной от обоих сущности-медиатора — той же роли, что DI-контейнер играет для бинов (знает и интерфейс, и все реализации, но ни один не знает другого), поднятой с уровня JVM-процесса на уровень build-графа; уточнение пользователя «SOLID на уровне Gradle-модулей» опознано как принципы компонентов Роберта Мартина (ADP/SDP/SAP) — медиатор обязан жить на корневом уровне (`settings.gradle.kts` и так легитимно знает про все модули), не внутри `application-core` (иначе даже рефлексивное сканирование дало бы модулю абстракции структурную осведомлённость об адаптерах, нарушение ADP). По прямому запросу «минимум нестандартного кода» медиатор пересмотрен как избыточный для цели «принудительно»: leaf-purity + бандлинг main+test одним `dependencies{}`-блоком в convention-плагине + штатный `./gradlew clean check --continue` (резолюция таска по всем подпроектам — штатное поведение Gradle) закрывают почти всё без единой новой строки кода; governance-часть («нельзя смержить без прогона») — GitHub required status check на существующий workflow, не новый код. ## Архитектура и структура проекта

**Многомодульная сборка (Gradle)** — схема: путь — назначение:
- `build-logic/settings.gradle.kts` — `include(":convention")`; included build, подключён через `pluginManagement { includeBuild(...) }` в корневом `settings.gradle.kts`
- `build-logic/convention/.../com.example.{name}.gradle.kts` — convention plugins (Kotlin DSL), namespaced id без суффикса `-conventions` (`com.example.spring-boot`, не `-conventions`); полный граф родитель→потомок всех 49 — см. `docs/convention-plugins-graph.md`
- `settings.gradle.kts` — единственный, в корне; `include(":...")` на все subprojects
- `{service}/{module}/build.gradle.kts` — применяет plugin через `id("com.example.{name}")`
- `{service}/{application,domain,persistence,presentation}/{module}/build.gradle.kts` — для `note`/`user`/`user-note` физическое расположение модуля вложено в подпапку по слою (2026-08-01, было плоско `{service}/{module}/`; см. «Именование» → «Группировка модулей по слою в подпапку» и «Открытые решения»/decisions-log за 2026-08-01). Gradle project path остаётся плоским (`:{service}:{module}`, без вложенности) — `settings.gradle.kts` переопределяет `project(":{service}:{module}").projectDir` на новый физический путь; typesafe accessors (`projects.note.domain`, `projects.userNote.dataJpa` и т. п.) не меняются

**Пакеты по сервисам** — путь — package:
- `note/` → `com.example.note`
- `user/` → `com.example.user`
- `user-note/` → `com.example.usernote` (не `user.note`!)

**Слои внутри сервиса** (зависимость → куда смотрит; физические пути — для `note`/`user`/`user-note`, сгруппированы по подпапке слоя с 2026-08-01) — схема: путь — роль — зависимость:
- `domain/domain/` — records·enums·exceptions — чистая Java, без зависимостей на инфраструктуру
- `domain/contract/` — sync port interfaces → `domain/domain/` (api)
- `domain/contract-reactive/` — reactive port interfaces → `domain/domain/` (api)·reactor-core (implementation)
- `presentation/webmvc/` — driving adapter sync → `domain/contract/`
- `presentation/webflux/` — driving adapter reactive → `domain/contract-reactive/`
- `persistence/data-jpa/` — driven adapter JPA → `domain/contract/`
- `persistence/data-jdbc/` — driven adapter JDBC → `domain/contract/`
- `persistence/data-r2dbc/` — driven adapter R2DBC → `domain/contract-reactive/`
- `persistence/data-mongodb/` — driven adapter MongoDB → `domain/contract/`
- `persistence/data-mongodb-reactive/` — driven adapter Mongo reactive → `domain/contract-reactive/`

- `application/application-{h2,mysql,postgresql}-jdbc/` — composition root (sync) → presentation/webmvc + persistence/data-jdbc
- `application/application-{h2,mysql,postgresql}-r2dbc/` — composition root (reactive) → presentation/webflux + persistence/data-r2dbc
- `application/application-mongodb/` — composition root (sync) → presentation/webmvc + persistence/data-mongodb
- `application/application-mongodb-reactive/` — composition root (reactive) → presentation/webflux + persistence/data-mongodb-reactive

Ровно один driven-адаптер и ровно один вендорный БД-драйвер на classpath каждого composition root — обе оси (технология адаптера, вендор БД для jpa/jdbc/r2dbc) выражены границей Gradle-модуля, не рантайм-профилем (пересмотр 2026-07-24 — было `spring.profiles.active`, см. `docs/decisions-log.md` → «Архитектура»: профиль выбирает bean в рантайме, но не убирает лишние драйверы из паковки). 11 composition-root модулей на сервис (9 реляционных + 2 Mongo, у Mongo вендорной оси нет) × 3 сервиса = 33. **⚠️ `user-note/` сознательно отступает от этого абзаца с 2026-08-19** (не WIP — см. «Задачи» → «Продолжение 2026-08-19», «Апдейт 2026-08-19, ещё позже») — вендорная ось для JDBC/JPA/R2DBC снова совмещена в одном модуле на технологию (3 драйвера на classpath, driver bloat принят сознательно как меньшее зло по сравнению со сложностью shared test-fixtures); не постоянное решение — пользователь допускает возврат к разделению по вендору специально ради driver bloat в будущем. `note`/`user` физически не тронуты (33-модульная структура сохраняется) — перенос этого выбора на них не вопрос для обсуждения, станет виден по факту правки пользователем.

**Внутренняя структура driven-адаптера** (пример `data-jpa/`; одинаково для всех технологий) — пакет — классы:

Осознанно выбрано имя, пересекающееся с реальным `org.springframework.data.domain.Persistable<ID>` — не конфликтует (префикс сущности делает simple name другим), но напоминает: сам маркер в `domain/` остаётся чистым Java без зависимости на `spring-data-commons`, а НАСТОЯЩИЙ `Persistable<ID>` (если понадобится `isNew()`) реализуется отдельно в каждом адаптере — см. `docs/decisions-log.md` → «Архитектура»
- **Composition-root главный класс** (2026-07-23, расширено вендорным префиксом 2026-07-24, порядок частей имени/модуля перевёрнут на «вендор-технология» в тот же день) — `{Service}{Tech}Application` в `application-{tech}/` для Mongo (`NoteMongoApplication`, `NoteMongoReactiveApplication`); `{Service}{Vendor}{Tech}Application` в `application-{vendor}-{tech}/` для jpa/jdbc/r2dbc (`NoteH2JpaApplication`, `NoteMysqlJpaApplication`, `NotePostgresqlJpaApplication`, ...) — вендор всегда явный префикс перед технологией, без неявного «без префикса = H2» (см. `docs/decisions-log.md` → «Вендор БД — граница Gradle-модуля»). Тестовый класс — `...ApplicationTests` по тому же паттерну. До 2026-07-23 было 2 модуля на сервис (`application`/`application-reactive`) без Tech-суффикса

**Tech**: `Jpa` · `Mongo` · `Jdbc` · `R2dbc` · `MongoReactive` (в имени класса — только для `{Tech}MapperContract`/`{Tech}Mapper`/`{Tech}Repository`/`{Tech}Entity`; адаптеры и порт-интерфейсы суффикс технологии в имени не несут — технология различается пакетом/модулем)

**Vendor** (2026-07-24, только для composition-root класса/модуля jpa/jdbc/r2dbc, см. «Composition-root главный класс» выше): `H2` · `MySQL` · `PostgreSQL` — всегда префикс перед `{Tech}`, порядок `{Vendor}{Tech}` (`H2Jpa`, не `JpaH2`) — пересмотрено в тот же день: изначально был выбран порядок `{Tech}{Vendor}` («технология доступа архитектурно более фундаментальна»), затем перевёрнут по решению пользователя без изменения обоснования самой оси (вендор/технология остаются раздельными осями именования, поменялся только порядок отображения). **Вопрос снят как неактуальный 2026-08-19** — модуль `{Tech}-{Vendor}` физически перестал существовать (5 плоских модулей вместо 11 вложенных вендорных, см. «Задачи» → «Продолжение 2026-08-19» п. 2), сравнивать порядок `{Vendor}{Tech}` vs `{Tech}{Vendor}` больше не с чем; если вендорная ось модуля когда-нибудь вернётся — вопрос открыть заново, не считать прежнее наблюдение решением

**Группировка модулей по слою в подпапку** (2026-08-01, начато пользователем вручную в `user-note/` — `git mv` в новую вложенность, опечатка `pestistence` вместо `persistence`; агент исправил опечатку и применил ту же структуру симметрично к `note/`·`user/`): для всех трёх зрелых сервисов физический путь листового модуля — `{service}/{layer}/{module}/`, где `{layer}` ∈ `application`·`domain`·`persistence`·`presentation` (`domain/domain`, `domain/contract`, `domain/contract-reactive` — все три под `domain/`; `data-*` → `persistence/data-*`; `webmvc`/`webflux` → `presentation/{module}`; все `application-*` → `application/application-*`). Сам Gradle project path (и, следовательно, имя typesafe-accessor) не меняется — остаётся плоским `:{service}:{module}` — только физическая директория переопределена через `project(":{service}:{module}").projectDir` в `settings.gradle.kts` (см. «Архитектура и структура проекта» → «Многомодульная сборка»). Ранее аналогичный, но более узкий вопрос («каталог `data/` на уровне сервиса» — только для `data-*`) обсуждался и было решено оставить плоско (цена реорганизации выше пользы) — это решение пересмотрено данным изменением, которое к тому же шире исходного вопроса (охватывает все 4 слоя, не только `data-*`)

## Открытые решения

- **Устранение дублирования кода — план на будущее, не реализовано** (2026-09-06, см. правило «Дублирование стремится к нулю» выше) — варианты: (а) рекомендовано — PMD CPD как Gradle-таск в `check`, порог по токенам + suppression-файл; версия не сверена по памяти, проверить перед реализацией; (б) SonarQube duplication-metrics — отклонено, избыточно ради одной метрики (сознательно вне CI/build, только SonarLint в IDE); (в) аудит без build-гейта — отклонено, полагается на память. Не реализовывать до отдельного запроса
- **Единый источник истины для версий (Docker-образы, Java) во всех окружениях** (2026-08-21, из «версия Docker-образа для Testcontainers vs реальный запуск» — техническое решение для `JDBC` там же; здесь вопрос шире, по всему проекту; **решение — в следующей сессии, здесь только исследование**) — для Java проблема уже решена: `.java-version` (`21`) читают Gradle (`com.example.java.gradle.kts` через `providers.fileContents(...)`) и `.github/workflows/gradle.yml` (`actions/setup-java@v4` с `java-version-file`) — один файл, два читателя, ни одной второй копии числа. Для **Docker-образов** готового моста нет — факт устройства экосистемы: Docker Compose нативно интерполирует `${VAR}` из `.env` в `image:`; Testcontainers-Java — нет, тег только явным Java-аргументом конструктора, `ImageNameSubstitutor`-крюк для точечного тега deprecated. GitHub Actions читает версию сама только через `services:`-блок (в проекте не используется — Testcontainers стартует изнутри Gradle `test`, наследует то же, что Gradle). Kubernetes не используется — вопрос гипотетический, паттерн на будущее — Kustomize `images:`/Helm `values.yaml`. Варианты: (а) зеркалировать `.java-version`-паттерн — общий `.env`/`docker-versions.properties`, Gradle читает `providers.fileContents(...)`, прокидывает в `test`-таск, `compose.yaml` читает тот же `.env` нативно — **рекомендовано**, прямое расширение уже работающего паттерна; (б) Gradle version catalog — отклонён, официально не для произвольных строк вроде тега образа, легитимен только для версий Java-библиотек (`mysql-connector-j` и т. п.); (в) Renovate `customManagers` с группировкой PR — дополняет (а), не заменяет, нужен только если копии всё равно остаются (тег в `compose.yaml` vs версия драйвера — два разных числа); (г) mise/asdf `.tool-versions` — отклонён, не про теги образов внешних сервисов. Ничего не реализовано, ждёт решения пользователя

- **Симметрия ArchUnit + стратегия покрытия матрицы адаптер×драйвер тестами** (2026-07-23; **не реализовывать до отдельного запроса**) — два вопроса:
  1. ArchUnit нигде не подключён (упомянут только в `docs/tech-glossary.md`). Кандидат на автоматизацию правил, сегодня проверяемых вручную грепом (расслоение hexagonal, запрет plugin id/зависимостей в обход `com.example.*`). Технический риск, не исследован: ArchUnit сканирует скомпилированные классы через reflection — в multi-module Gradle это либо один агрегирующий тестовый модуль с зависимостью на все 39 модулей (широкое схождение путей, качественно отличное от разобранных диамантов), либо отдельный Gradle-таск, компонующий classpath вручную
  2. Матрица тестового покрытия — вариант (A) «отдельный класс/модуль на комбинацию» реализован для `note`/`user` (33 composition-root модуля, один `*ApplicationTests` на модуль); **для `user-note` этот инвариант больше не действует с 2026-08-19** (5 объединённых модулей, вендор внутри — см. «Задачи» → «Активная нить»). Вариант (B) `@ParameterizedTest` снят как противоречащий тогдашнему «вендор — граница модуля»; вариант (C) — мета-тест по типу ArchUnit («на каждый вендорный плагин должен существовать application-модуль») — зависит от решения по пункту 1, актуальность для `user-note` пересмотреть заново после изменения 2026-08-19
  3. **Дополнено 2026-09-05** (консультация, «Активная нить» → «2026-09-05») — вариант (C) выше сформулирован конкретнее как один из 4 слоёв гарантии «реализация реально протестирована»: мета-тест графа сборки закрывает только «тест вообще не заведён для нового модуля»; отдельно нужен JaCoCo `jacocoTestCoverageVerification` (byte-code-доказательство, что код реализации реально исполнился, не просто что тест существует) — оба дополняют, не заменяют друг друга
- **Поведенческая аналогичность адаптеров/драйверов** (названо пользователем главной проблемой на пути к зрелости CRUD-модулей, 2026-07-24; **не реализовывать до отдельного запроса**) — реализации порта по матрице технология×вендор должны вести себя одинаково при одинаковом сценарии; находки по факту чтения кода `note/` (не перепроверялись отдельно для `user/`/`user-note/`, предполагается та же структура):
  1. Порты не специфицируют поведение (голый `Object`, без `throws`/`Optional`/`@Nullable`/Javadoc) — **2026-08-18 переосмыслено как осознанное разделение**: спецификация поведения сознательно живёт в тестах application-уровня, порт остаётся чисто структурным контрактом
  2. Обработка «не найдено» сегодня случайно одинакова во всех 5 адаптерах (`orElseThrow(NoteNotFoundException)`/`switchIfEmpty(Mono.error(...))`) — не гарантирована ни портом, ни тестом
  3. Реальные расхождения: генерация ID тремя механизмами (JPA — `@GeneratedValue` через Hibernate; JDBC/R2DBC — `DEFAULT RANDOM_UUID()` в `schema.sql`; MongoDB — `UUID.randomUUID()` в мапере); duplicate-key нигде не транслируется ни в одном из 5 адаптеров (сценарий сегодня недостижим — нет unique-constraint кроме PK — но латентный риск, `NoteExceptionHandler` обработает только `NoteNotFoundException`); MongoDB (blocking) `add()` использует `mongoTemplate.insert()` напрямую, минуя repository, в отличие от остальных операций/адаптеров
  4. Одинаковые (не расходящиеся) пробелы во всех 5: `@Transactional` отсутствует везде (`merge()`/`replace()` — read-then-write без атомарности); Bean Validation отсутствует везде (аннотации `@NotNull`/`@NotBlank` на model-классах не расставлены, хотя `spring-boot-starter-validation` подключён точечно)
  5. **Referential integrity между `user-note/` и `user/`·`note/` не проверяется вообще** (найдено 2026-07-24) — `create()` в `UserNoteService` (`data-jpa`) сохраняет `UserNoteEntity` без проверки, что `userId`/`noteId` реально существуют в `user/`/`note/`: ни синхронного вызова порта, ни события, ни constraint (сервисы физически разделены). Там, где проверка вроде есть (`existsByUserId` — проверяет «есть ли уже связка в `user_note`», не «существует ли пользователь»), она обманчива — `UserNotFoundException` там означает «у userId нет заметок», не «пользователя нет». Не перепроверено для jdbc/r2dbc/mongodb/mongodb-reactive `user-note/`. Тот же класс проблемы («нет referential integrity через границу сервиса») встанет и в «Регистрация auth/ ↔ user/» ниже
