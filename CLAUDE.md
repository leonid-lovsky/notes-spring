# notes-spring

Репозиторий показывает эволюцию одного приложения от классического монолита до распределённой конфигурируемой устойчивой системы. Цель — освоить технологии Spring и продемонстрировать владение ими работодателю, пройдя путь от уровня junior до senior на стандартных инструментах, без экзотики.

Приложение одно на всех этапах: пользователи, заметки, доступ к заметке по ролям, уведомления с живой лентой через Server-Sent Events и полнотекстовый поиск заметок. Его функциональность и HTTP API задаются на первом этапе и дальше не меняются — меняется только внутреннее устройство.

Прежняя попытка проекта сохранена в теге `legacy-2026-11`, её документация — в `docs/archive/` и используется только для справки.

## Этапы

Каждый этап — самостоятельное приложение в своём каталоге. Он начинается как копия предыдущего и добавляет ровно одно архитектурное изменение, вызванное проблемой предыдущего этапа. Подробное описание этапа — в его `README.md`, обоснование всей последовательности — в `docs/adr/0001-evolution-in-seven-stages.md`.

| Каталог | Изменение | Ключевые инструменты | Уровень |
|---|---|---|---|
| `01-monolith` | база | Gradle, Spring MVC, Data JPA, PostgreSQL, Flyway, Security + OAuth2 (сервер авторизации `auth-server` на Spring Authorization Server), Thymeleaf, MapStruct, OpenAPI, Actuator, Testcontainers; GitHub Actions, SonarQube Cloud, AWS (EC2, ECR, IAM) | junior |
| `02-modulith` | границы модулей, события в процессе | Spring Modulith, журнал публикаций событий, поиск в Elasticsearch; Jenkins наравне с GitHub Actions | middle |
| `03-event-driven` | уведомления — отдельный сервис | Kafka, вынос событий Modulith, трассировка OpenTelemetry; GitLab CI | middle+ |
| `04-microservices` | все модули — сервисы | Gateway (вход, передача токена), Config Server, Eureka, Resilience4j, Spring Cloud Contract, сага, Redis (сессии и кэш), AWS Secrets Manager | senior |
| `05-kubernetes` | платформа вместо Spring Cloud | k3s на EC2, Helm, Argo CD, Terraform (вся инфраструктура AWS), автомасштабирование, Gatling | senior |
| `06-hexagonal` | порт хранилища там, где появляется вторая реализация | Spring Data JDBC (PostgreSQL, MySQL, H2 профилем), Spring Data MongoDB, контрактный тест порта | senior |
| `07-reactive` | второй веб-стек для сервиса уведомлений | WebFlux, реактивное хранилище, SSE; версия MVC и версия WebFlux выбираются значением Helm | senior |

### Как ведётся этап

Этапы делаются строго последовательно. Работа над этапом начинается с коммита, который копирует предыдущий каталог, после чего каждое изменение идёт отдельным коммитом — так разница между этапами читается в истории как пошаговый переход.

Этап готов, когда приложение работает на сервере, приёмочные тесты и тесты этапа проходят, `README.md` заполнен, а ключевые решения записаны в ADR. Готовый этап замораживается: в нём исправляются только ошибки и уязвимости, зависимости обновляет Dependabot.

Каждый этап — самостоятельная сборка Gradle со своими `settings.gradle.kts` и wrapper; корневой сборки и общего `build-logic` нет. CI устроен так же: конвейер на этап, запускаемый только изменениями в каталоге этапа. GitHub Actions используется на всех этапах; с `02` рядом с ним равноправный Jenkins с теми же шагами — оба вызывают одни и те же задачи Gradle, поэтому логика сборки не дублируется. GitLab CI добавляется в `03`, Argo CD — в `05`. Все этапы размещаются в AWS: этапы `01`–`04` запускаются локально и на EC2 через Docker Compose, с `05` — в Kubernetes (k3s на EC2).

План покрывает технологии, которые почти всегда требуют в вакансиях Java/Spring; что сознательно не включено и почему — в `docs/adr/0001-evolution-in-seven-stages.md`.

### Приёмочные тесты

Каталог `acceptance-tests/` содержит один набор тестов «чёрного ящика» для всех этапов. Он обращается к развёрнутой системе только по HTTP и доказывает, что поведение, заданное в `01`, не меняется. Набор не знает технологий реализации: ни фреймворка, ни хранилищ, ни брокера, ни продукта сервера авторизации, ни устройства системы, ни номера этапа. Он знает только адреса системы и издателя токенов, учётные данные тестового пользователя и публичный API (HTTP, JSON, SSE, OAuth 2.0 / OIDC). Данные создаются и проверяются только через API, асинхронное поведение — ожиданием результата через API. Тесты внутри этапа (модульные, срезы, интеграционные) остаются в этапе и проверяют его технологии. Подробности — `acceptance-tests/README.md`.

## Приоритеты решений

Технические решения принимаются в таком порядке приоритетов:

1. **Автоконфигурация Spring Boot.** Используются стандартные стартеры и свойства. Собственная конфигурация бинов допустима только тогда, когда без неё задача не решается, и причина называется явно.
2. **KISS и DRY.** Если принципы конфликтуют, выбирается вариант, который не ломает автоконфигурацию и при этом избегает дублирования. Если автоконфигурацию сохраняют оба варианта, выбирается более простой.
3. **Стандартные инструменты.** Предпочтение отдаётся тому, что встречается в типовом проекте на Spring.

Копирование кода между этапами — сознательное исключение из DRY: каждый каталог — снимок своего этапа. Внутри этапа DRY действует в полной мере.

Стандарты (RFC, спецификации, документация docs.spring.io) важнее туториалов и важнее предложения пользователя; отступление от стандарта допускается только с названной причиной. Архитектурные решения принимает пользователь: ассистент описывает варианты и даёт рекомендацию.

Факты о Spring — существование стартера, его имя, версия — проверяются по Spring Initializr, docs.spring.io и GitHub spring-projects при старте этапа, а не по памяти и не поиском Maven Central, индекс которого отстаёт.

## Документация

Документация пишется для читателя: связным понятным языком, разделами с вводным текстом, без хроники обсуждения, цитат и пометок «по указанию пользователя». Она фиксирует итог решения и его причину.

Между коммитами существующие записи только правятся на месте, новые записи рядом не добавляются; новая запись появляется только после коммита. Для ADR это означает: решение, принятое после последнего коммита, вносится в уже существующую запись, а новая запись ADR создаётся только для решения, принятого после коммита. ADR лежат в `docs/adr/`, по одному решению в файле `NNNN-title.md`.

Общение с пользователем ведётся на русском. Код, настройки, публичные `README.md` и ADR пишутся на английском.

## Код и сборка

Сборка и тесты проходят без ошибок и предупреждений. Отступ — 4 пробела. Промежуточные результаты кладутся в локальные переменные с понятными именами вместо вложенных вызовов. Аббревиатуры в идентификаторах пишутся заглавными буквами, кроме `Id`.

Коммит и пуш выполняются только по явному требованию пользователя; просьбы «делай», «внеси», «поехали» требованием коммита не являются. Команда «Зафиксируй» означает: синхронизировать документацию, сделать коммит и пуш. Дата в документации берётся из команды `date`.
