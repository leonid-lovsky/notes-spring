# 01 · Monolith

Level: junior. Status: in progress.

## Change

The baseline: a classic layered Spring Boot application with server-rendered pages and one relational database management system (DBMS), PostgreSQL or MySQL, the kind of application a junior writes first. A person creates, reads, edits and deletes notes in a browser. The model of a user with its invariants is laid down here as well, so that the schema is designed from the start for a move to another DBMS and to an identity provider; sign-in arrives in 06. Everything else arrives one step per stage.

## Why

Every later stage is measured against a working, tested, conventional Spring application, so this stage contains only what such an application cannot work without.

## Tools

- Application: Gradle (Groovy DSL), Spring Boot starters with auto-configuration, Spring MVC with Thymeleaf. A note has an auto-increment primary key used inside the database, a unique UUID that identifies it everywhere outside the storage layer and is created with `UUID.randomUUID()`, and its content as text, which 03 renders as Markdown; the content may be empty but never `null`. A user has the same two keys and a unique username. The entities keep their own invariants in their constructors, so no service or controller can bypass them: a `null` value is rejected by `Objects.requireNonNull`, and a username is converted to lowercase with `Locale.ROOT`, independent of the language of the machine, and rejected with an `IllegalArgumentException` unless it starts with a Latin letter, continues with Latin letters, digits and single hyphens, does not end with a hyphen and is at most 32 characters long. No standard defines a username, so the rule is the one that both GitHub (letters, digits and single hyphens, not at the edges, at most 39 characters) and Linux (`useradd`: a lowercase letter first, then lowercase letters, digits, underscores and hyphens, at most 32 characters) accept; the application, not a collation of the DBMS, decides that `Bob` and `bob` are the same user. The user schema that Spring Security ships for `JdbcUserDetailsManager` is the reference for users, and the stage deviates from it in three points: the table is `user` rather than `users`, because the names of the tables are singular; the key is an own `id` rather than the username, because other tables refer to a user only by the application's key, which survives the move of sign-in to an identity provider in 37 and 41; and the username is a `varchar(32)` with case normalized by the application rather than `varchar_ignorecase(50)`, a type that only H2 knows. Forms follow Post/Redirect/Get, and the message about the result survives the redirect as a flash attribute in the `HttpSession`. The stage keeps the `.gitignore` and `.gitattributes` that Spring Initializr generates, next to those at the root of the repository: they stay as generated and do not conflict with the root files.
- Data: Spring Data JPA on Hibernate with PostgreSQL or MySQL, whose server runs in a Docker container. The DBMS is selected by a profile, `postgresql` or `mysql`; `postgresql` is the default profile (`spring.profiles.default`). Each profile file, `application-postgresql.properties` or `application-mysql.properties`, holds the connection to the `notes` database on the server of its DBMS and the Spring Boot SQL initialization platform of that DBMS, and Spring Boot auto-configures the `DataSource` and Hibernate detects the dialect from that connection, so the code does not depend on the DBMS. The schema is written by hand for each DBMS, in `schema-postgresql.sql` and `schema-mysql.sql`; Spring Boot SQL initialization runs the script of the selected DBMS at every start (`spring.sql.init.mode=always`, `spring.sql.init.platform`), and Hibernate only validates the entities against it (`spring.jpa.hibernate.ddl-auto=validate`). Every name is in lowercase and always quoted, so that `user`, a reserved word of SQL, is a valid table name: Hibernate quotes every name it generates (`hibernate.globally_quoted_identifiers`) and also quotes keywords (`hibernate.auto_quote_keyword`), which is redundant while every name is quoted but keeps reserved words safe if global quoting is switched off, and the scripts quote every name with the quotes of their DBMS, double quotes in PostgreSQL and backticks in MySQL. The scripts differ where the DBMS do: MySQL has no `uuid` type, so the UUID is stored as `binary(16)`, the type Hibernate maps it to on MySQL. The content of a note is practically unlimited in length in both DBMS: `text` on PostgreSQL and `longtext` on MySQL, whose `text` holds only 64 KB. Both DBMS keep their default string comparison, although it differs: the default collation of MySQL, `utf8mb4_0900_ai_ci`, ignores case and accents, while PostgreSQL compares strings exactly. Wherever text is compared, the behaviour the application requires is fixed by tests that run against every DBMS and prove the results are exactly the same; the way to achieve it is chosen when such a comparison appears. Until the first release the `notes` databases hold only local test data, so the script always describes the current schema: a change is made in the script and the entity, and the table is dropped by hand to be created again at the next start; migrations are needed only once a released database holds data that must be kept; services are `@Transactional`. `spring.jpa.open-in-view` is set to `false`, against the default `true` that Spring Boot keeps for compatibility and warns about at startup: the `EntityManager` lives only inside a transaction of a service, so every query is made by a service and none during the rendering of a page, and a service loads the associations a page needs with `@EntityGraph` or `JOIN FETCH` instead of hidden lazy queries from the template, one per row.
- Tests: JUnit, Mockito, slice tests and page tests with MockMvc. The tests run against the selected DBMS, on a server in a container that Testcontainers starts for them, the same DBMS the application runs on rather than an imitation of it, so the build needs Docker running but not the local servers. `TestcontainersConfiguration` is the one Spring Initializr generates with PostgreSQL, MySQL and Testcontainers selected: it declares each container as a bean with `@ServiceConnection`, from which Spring Boot takes the URL and the credentials, and each bean belongs to the profile of its DBMS, so only the container of the selected DBMS starts. `./gradlew check` runs the tests once against every supported DBMS: the standard `test` task keeps its default behaviour and runs against the default DBMS, and the build registers a task such as `testMySQL` for each other DBMS of its list, with the profile of that DBMS. Each such task is named and described after the DBMS it tests against, because that is what it checks; the profile is only how the DBMS is selected. The build takes the default DBMS from `spring.profiles.default` in `application.properties`, so any supported DBMS can become the default by a change of that one setting, and the build adapts without a change. Reading the application settings from the build is not a standard Gradle practice; it is chosen because no other way runs the tests against every DBMS exactly once in one command while keeping the default `test` task, and the usual alternative, one DBMS per run selected by a parameter with a CI matrix, needs CI, which arrives in 24. The images are pinned to `postgres:18` and `mysql:9.7`, the current long-term support release of MySQL, the same as in the `docker run` commands below, instead of the generated `latest` tags, which change without a change of the code. The tests use Testcontainers only: the application itself always runs against a real server of its DBMS, so the `TestNotesApplication` that Spring Initializr generates for `bootTestRun` is not kept. Each image is declared in two places and kept equal by hand, as recorded in [ADR 0001](../docs/adr/0001-evolution-in-stages.md).
- Run: the server of each DBMS is started once by hand with Docker, without Docker Compose, which comes in 21, and is restarted later with `docker start notes-postgres` or `docker start notes-mysql`; then `./gradlew bootRun` connects to PostgreSQL, and `./gradlew bootRun --args='--spring.profiles.active=mysql'` to MySQL, with the URL and credentials set in the profile file. These settings serve local development only: the connection leaves the profile files for Docker Compose support in 21, and the configuration and secrets of the test and production environments come from the environment in 22.

```
docker run -d --name notes-postgres -e POSTGRES_DB=notes -e POSTGRES_USER=notes -e POSTGRES_PASSWORD=notes -p 5432:5432 -v notes-postgres:/var/lib/postgresql postgres:18
docker run -d --name notes-mysql -e MYSQL_DATABASE=notes -e MYSQL_USER=notes -e MYSQL_PASSWORD=notes -e MYSQL_RANDOM_ROOT_PASSWORD=yes -p 3306:3306 -v notes-mysql:/var/lib/mysql mysql:9.7
```

## Open questions

A question moves into the sections above once it is decided.

- Equal names of the test tasks for every DBMS: `testPostgreSQL` next to `testMySQL` whichever DBMS is the default, the task of the default DBMS only depending on the standard `test` task, so that no DBMS runs twice. Not critical now.
- Editing and deleting from a form, which sends only `GET` and `POST`: separate `POST` endpoints such as `POST /notes/{id}/delete`, or the hidden method filter of Spring MVC (`spring.mvc.hiddenmethod.filter.enabled`, off by default).
- A taken username: for now only the unique constraint of the schema rejects it, with a `DataIntegrityViolationException` whose message depends on the DBMS; a clear rejection is needed at the latest in 07, when visitors create accounts.

## Known warnings

The warnings are ordered by how critical they are and resolved in that order; a resolved warning is removed.

1. Gradle declares no toolchain repository. The local Java 25 toolchain was installed by auto-provisioning, which Gradle has deprecated and which fails from Gradle 10; a clean machine does not find the toolchain. Resolved in 24, the first stage that builds on a clean machine.
2. Mockito attaches itself to the test JVM as an agent, and the JVM reports the dynamic agent loading and limits class data sharing. The warnings come from the default behaviour of the tools and are accepted, as recorded in [ADR 0001](../docs/adr/0001-evolution-in-stages.md).

## Proof

- The tests pass on PostgreSQL and on MySQL that Testcontainers starts, with the local servers stopped.
- `bootRun` starts the application against the PostgreSQL or MySQL server in its container.
